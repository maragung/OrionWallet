# Changelog

All notable changes to Orion Wallet will be documented in this file.

## [Unreleased]

### Added

- **`wallet_signTransfer` — sign a plain OCT transfer** (`src/connect/typed-data.ts`, `src/connect/rpc-handler.ts`, `src/sdk/WalletProvider.ts`) — a dApp can now ask for a native transfer directly: `provider.signTransfer({ to, amount, message? })` opens an approval prompt and returns the signed transaction together with the `nonce`, `amountRaw`, `ou` and `hash` that went into it. Nothing is broadcast; the wallet still signs only. Until now the only signing method that could move OCT was `signContract`, so a site had to disguise a transfer as a contract call — and `op_type` is *inside* the canonical JSON that gets signed, so rewriting it on the result yields a transaction whose signature no longer verifies, after showing the user a prompt describing an operation that was never made. The amount may be a decimal OCT string (`"1.5"`) or raw base units (`amountRaw`), converted by the same `parseAmountRaw` the Send form uses, and `ou` defaults to the wallet's recommended fee for that size. Gated behind the new **`signTransfer`** capability and permission scope.
- **`previewTransfer()`** (`src/connect/typed-data.ts`) — resolves a transfer request into the exact `{ to, amountRaw, ou }` that will be signed, without signing anything. The approval prompt and `signNativeTransfer` both go through it, so the fee on screen is the fee in the signature by construction rather than because two code paths happen to agree. It is also where a request dies: an invalid address, a non-integer `amountRaw`, a non-positive amount, a malformed fee or a send-to-self fails with `INVALID_PARAMS` **before** any prompt opens, instead of asking the user to approve something that cannot be signed.
- **`wallet_ping` — ask whether the wallet is still there, without disturbing anyone** (`src/connect/rpc-handler.ts`, `src/sdk/WalletProvider.ts`) — `provider.ping()` answers `{ pong, v, connected, locked, capabilities, origin, ts }`; `provider.isAlive()` wraps it and never throws. The three outcomes are the three different repairs a dApp needs: a rejection means the channel itself is gone and the transport must be rebuilt, `connected: false` means reconnect, and `locked: true` means wait rather than fire a request that pops a PIN prompt behind the user's back. It is answered while the wallet is locked (it is in `UNLOCK_EXEMPT_METHODS` alongside `wallet_disconnect`), it deliberately does **not** call `requireSession` — a probe must be able to report "the port is alive but your session is gone" rather than expiring the session it was asked about — it does not refresh the idle TTL, it never raises a prompt, and it never raises the wallet window (`focus` defaults off for this method, and the provider will not auto-reconnect on its behalf, which would open a popup nobody asked for and destroy the very answer being requested). Default timeout is 4 s, because a liveness check that waits out the full request timeout is not a liveness check. Gated behind the new **`ping`** capability.
- **`toNodeWireTx` / `buildNodeWireJson` are now SDK exports** (`src/sdk/wire-tx.ts`) — the rules for turning a wallet-signed transaction into the JSON the node accepts: the recipient is `to_` with a trailing underscore (the node's `of_yojson` requires it and rejects `to` as `Malformed JSON`, the least informative possible answer to a one-character naming difference), the local-only `hash` is dropped, and key order follows `Transaction.to_yojson`. Sign-only means the dApp submits, so every integrator needed this and every integrator was rediscovering it from a rejected submit. `src/tx/builder.ts`'s `buildTxJson` now delegates here, so the wallet and every dApp share one implementation instead of two that can drift; unknown keys are passed through and appended rather than dropped, since silently discarding a field the signature covers produces an invalid submit.
- **Approval prompts lead with what you are agreeing to** (`src/connect/approval-ui/ApprovalPrompt.tsx`) — every prompt now opens with a plain-language summary of the fields that decide the answer, and keeps the verbatim payload one click behind **▸ Show raw payload**. A transfer shows the amount as a headline, then To / Fee / Nonce / Memo; a contract call shows program, method, what it sends, the fee, the nonce, the resolved operation and its arguments one per row; an approval shows program, method, spender, limit and expiry — with **No limit set by the site** and **Never** spelled out, because those are the two dangerous answers and a missing field used to render as nothing at all; typed data shows domain, primary type and the message fields. The old prompts were a `JSON.stringify` dump, which looks rigorous and reads as noise: the fields that matter are buried among the ones that never change, so in practice people approve without reading. The raw view still exists — for typed data and contract args it is sometimes the only complete answer — it just is not the default. **Escape** now rejects, and the summary rows middle-truncate long addresses instead of wrapping over four lines.
- **`src/connect/attention.ts` — one attention signal, torn down when the request is answered** — focus the popup once, chime only when the window is actually in the background, and flash the document title (`🔔 Action needed`) until the request is answered. The title flash is the part that reliably works: it survives autoplay policy, an ignored `focus()` and a minimised window, because it shows up in the taskbar and the tab strip. Used for approval prompts and for the unlock gate, since a locked wallet with a dApp request parked behind it is exactly as much "your turn" as a prompt is.
- **The unlock screen says who is waiting and why** (`src/components/UnlockWallet.tsx`, `src/connect/ConnectApp.tsx`) — a new `notice` prop, driven by the popup's `unlockPrompt` state, renders `<origin> is waiting for your wallet. Unlock to answer its request — you will still be asked to approve anything it wants signed.` above the PIN field. An unexplained PIN prompt has the same shape as a phishing prompt, and the correct instinct when facing one of those is to close the window — so without this, the safest user behaviour was also the one that lost the request. Passkey unlock moved **above** the PIN field with an `or use your PIN` divider and now takes the primary button, and the PIN field no longer autofocuses when a passkey exists: one tap should not be the option you have to go looking for, under a field that stole the caret on mount.
- **A published SDK bundle** (`npm run build:sdk`, `vite.config.sdk.ts`, `tsconfig.sdk.json`, `vercel.json`) — `npm run build` now also emits `dist/sdk/orion-wallet-sdk.mjs`, an IIFE build, generated `.d.ts` files and a `package.json`, served with `Access-Control-Allow-Origin: *` and `Cross-Origin-Resource-Policy: cross-origin` so a dApp can integrate with no build step at all: `await import('https://orionwallet.vercel.app/sdk/orion-wallet-sdk.mjs')`. `src/sdk/index.ts` also exports what an integrator actually needs and previously had to re-declare — `MIN_PROTOCOL_VERSION`, `ORION_METHODS`, `ORION_METHOD_PREFIX`, `SUPPORTED_METHODS`, `canonicalizeMethod`, `WALLET_CAPABILITIES`, the `WireError` type, and the new transfer/ping parameter and result types.
- **Per-call request options** (`src/sdk/WalletProvider.ts`) — `provider.request(method, params, { timeoutMs, focus })` for callers that need a different deadline or that must not raise the wallet window. Previously both were provider-wide, so a 4-second liveness probe and a 60-second signing request could not coexist.
- **Docs for the two new methods** — `docs/DEVELOPER.md` gains `wallet_signTransfer` and `wallet_ping` in the namespace table, a **Sending OCT: `signTransfer`** section (including how to submit the result with `toNodeWireTx` over `octra_submit`, and why rewriting `op_type` cannot work), and a **Liveness: `ping`** section with the result/repair table and the reason `wallet_connect` must not be used as a probe. `docs/USER_GUIDE.md` gains **Reading a signing prompt** — what the summary rows mean, that Reject holds keyboard focus and Escape rejects, that the wallet signs without sending, and that an unlock prompt which does not name the site waiting for it is a reason to close the window.
- **39 unit tests over the paths this touched** — `tests/unit/connect-ping-transfer.test.ts` (ping answers while locked without calling `requestUnlock`, reports `connected: false` before a session exists, opens no approvals, and does not extend the idle TTL; transfer signs `op_type: 'standard'` that verifies against the canonical JSON, prompt detail matching the signed values field for field, decimal and raw amounts, default and explicit fee, memo carried into `message`, seven `INVALID_PARAMS` cases that each assert no prompt was opened, rejection, suspend-behind-unlock, `WALLET_LOCKED`, `UNAUTHORIZED`), `tests/unit/sdk-wire-tx.test.ts` (the `to_` rename, the dropped `hash`, exact key order, unknown-key passthrough, and `buildNodeWireJson === buildTxJson` as an anti-drift guard), `tests/unit/sdk-inject.test.ts` (no `Window` augmentation in the shipped source, the announcement event, and not clobbering an extension that already owns `window.octra`), and `tests/unit/approval-transfer-summary.test.tsx` (the transfer summary's rendered rows, the resolved fee, and the raw payload appearing only after the toggle is clicked).
- **Custom networks in the connect popup and over the SDK** (`src/wallet/networks.ts`, `src/sdk/protocol.ts`) — a network the user added under **Settings → ⚙️ General → Custom Networks** is now a first-class choice everywhere. The `/connect` popup's selector lists it beside the presets, labelled `(custom)`, so a site can be connected on a private node without leaving the popup; an id whose definition was deleted mid-session renders as `(unknown)` instead of a blank `<select>`. dApps get two new reads — `wallet_getNetworkInfo` and `wallet_getNetworks` (both namespaces) — plus `networkInfo` on the connect reply, on the `networkChanged` event, and as a sync `provider.networkInfo()` getter. Gated behind the new **`customNetworks`** capability so a dApp can feature-detect rather than guess.
- **`NetworkInfo`, the wire projection of a network** — `id`, `name`, `explorerUrl`, `icon`, `custom`. `rpcUrl` and `relayerUrl` are deliberately **not** in it: a user-added network is usually a private endpoint (LAN address, tunnel, a provider URL with the key in the query string), and connecting to a site should not disclose where the user's node lives. Nothing is lost — reads are proxied by the wallet and transactions never leave the wallet UI. There is still no `wallet_switchNetwork`; switching stays in the wallet's own UI, and dApps find out via `networkChanged`.
- **Recovery-phrase backup check at creation** (`src/wallet/mnemonic-quiz.ts`) — creating a wallet no longer opens it. The user must retype **3 words picked at random** (CSPRNG with rejection sampling, so the low indices a lazy backup remembers are not favoured) before the wallet activates. Case- and whitespace-insensitive, retryable, with **Show Phrase Again** — the point is proof the phrase left the screen, not a spelling test.
- **Contacts / address book** (`src/components/AddressBookPanel.tsx`, `contacts` object store) — address, name, optional note, under **Settings → 📇 Contacts**. The Send form offers saved payees in a **📇 Contacts…** picker, labels a pasted address that matches one, and can save a new one inline with **＋ Save to contacts**. A recognised name is a far better address check than reading base58. CSV export included.
- **QR scanning for the recipient** (`src/components/QrScanner.tsx`, `src/wallet/payment-uri.ts`) — **📷 Scan** in the Send form reads a code with the device camera, decoded in-page with `BarcodeDetector` and never uploaded. Parses `octra:<addr>[?amount=]` and a bare address, and prefills the amount when the code carries one. **Receive** can request an amount, encoding the same URI in its QR code; with no amount it stays a bare address for maximum scanner compatibility.
- **Passkey unlock** (`src/wallet/passkey.ts`, `passkey-unlock` object store) — optional biometric/security-key unlock via the WebAuthn **PRF** extension with `userVerification: 'required'`. `sha256("orion-passkey-unlock-v1" || prf)` seals the serialized wallet with AES-256-GCM; only the credential ID, salt, IV and ciphertext are stored, so the record is inert without a verified gesture on that authenticator. **PRF is required, never degraded** — registration throws and stores nothing rather than keeping a readable key. It seals the wallet, not the PIN: exporting keys, revealing the phrase, changing the PIN and deriving accounts all still require the PIN. A stale credential fails closed (record deleted, PIN required); a *dismissed* prompt deliberately keeps the record so a cancelled gesture cannot silently disable the feature.
- **Watch-only accounts** (`src/wallet/watch-only.ts`) — track an address with no keystore, added under **Settings → 👥 Accounts → 👁 Watch Address**. Balance, history and CSV export work; switching to one needs no PIN because there is nothing to decrypt. `assertCanSign` guards the send, encrypt, stealth, contract and dApp-request paths and throws naming both the action and the fix, so the invariant holds at the API boundary rather than in the UI. Fails closed by construction: any secret key that is not a full 64-byte Ed25519 key is refused even without the flag, and the flag survives `serializeWallet`/`deserializeWallet`.
- **CSV export** (`src/utils/csv.ts`) — **⤓** in History exports the loaded rows (time, hash, type, from, to, direction, amount, fee, status); Contacts exports the whole list. Deliberately exports what is on screen rather than re-fetching, so one click cannot become a silent 20k-row download — "Load more" first to widen it. RFC 4180 quoting with CRLF lines, a BOM on the download so spreadsheets read UTF-8 correctly, and a formula-injection guard that prefixes any cell starting with `=`, `+`, `-`, `@`, tab or CR.
- **Plaintext (http) RPC endpoint policy** (`src/wallet/endpoint-policy.ts`) — non-loopback `http://` endpoints now require explicit per-origin consent (`Settings.allowedInsecureOrigins`), with a **Trust `origin`** button and a removable trusted list in **Settings → Network**. One pure function decides, so the store, the UI and the tests cannot disagree. It reports the most fundamental blocker first — mixed content, then CSP, then consent — so the user is never told to fix the allowlist when the browser is the one refusing.
- **Loopback in `connect-src`** — `http://localhost:*`, `http://127.0.0.1:*` and `http://[::1]:*` are allowed outright: that traffic never leaves the machine. Consent is per origin (scheme + host + port), so `http://127.0.0.1.evil.com` is not loopback and trusting one port does not trust another.
- **`VITE_ALLOW_HTTP_ENDPOINTS=1` build flag** (`vite.config.ts`) — appends `http:` to `connect-src` at build time for self-hosters with a plain-http node. A meta-tag CSP cannot be widened at runtime, which is why this is a build flag and not a setting; user consent still applies on top.
- **`Settings.rpcProxyUrl`** — optional proxy the RPC URL is appended to, percent-encoded. The endpoint is then judged by the proxy's scheme, since that is what the browser connects to. Fixes the no-TLS and no-CORS cases; the UI says to run your own, because the proxy sees every request.
- **`⚠️ Insecure RPC` header badge** (`src/components/Layout.tsx`) — shown when the configured endpoint is unusable, and clicking it opens Settings → Network. A blocked endpoint still constructs an `RpcClient` on purpose: refusing to would leave the user unable to reach Settings to fix it.
- **`RpcClient.unreachableHint`** — appends the endpoint verdict to a bare "Failed to fetch", so the error says what to fix. Applied only to a thrown `TypeError`, never to a real server error or a timeout.
- **Unlock session that survives a page reload** (`src/wallet/unlock-session.ts`) — the unlocked wallet is sealed with AES-256-GCM and split across two stores: the ciphertext in `sessionStorage` (scoped to one tab, dropped when it closes) and the key in IndexedDB as a non-extractable `CryptoKey`. Neither half is usable alone. The session rotates on every restore, and `createdAt` is carried through so refreshing cannot extend the absolute cap.
- **Idle auto-lock** (`src/hooks/useAutoLock.ts`) — real user activity (pointer, keyboard, wheel, touch) refreshes the idle window; the wallet locks itself once it elapses, so the 30-minute rule holds in a tab that is never reloaded, not only on refresh.
- **Settings → Security → Session & Auto-Lock** — "Stay unlocked after a page refresh" (`keepUnlocked`) and "Auto-lock after inactivity" (`autoLockMinutes`: 5/15/30/60/never). Both apply to the session already open, not just the next unlock.
- **"Restoring your session…" screen** (`src/components/SessionRestoring.tsx`) — shown while a session is reopened, so a reload no longer flashes the PIN screen on the way back into the wallet.
- **`unlock-session-keys` object store** — IndexedDB `DB_VERSION` 5 (additive migration). Holds only the sealing key; orphans left by a tab that closed without locking are pruned by age.
- **`aesGcmSeal` / `aesGcmOpen` / `generateAesGcmKey`** in `src/crypto/aes.ts` — AES-GCM helpers that accept a `CryptoKey` or raw bytes, so the session works in insecure contexts too (without the non-extractability guarantee).
- **Docs** — "Locking and unlocking" in `docs/USER_GUIDE.md` (what a refresh, a tab close, and 🔒 each do) and "Unlock session" in `docs/SECURITY.md` (what is persisted, the two-halves split, what it does _not_ defend against, and how to opt out). Also in `USER_GUIDE.md`: "Contacts (address book)", "Watch-only accounts", "Unlocking with a passkey", "Network settings" (nodes without HTTPS, the RPC proxy, and what the ⚠️ badge means), the real creation flow with its word check, and troubleshooting for the insecure-RPC badge, the camera, and a missing passkey button. In `SECURITY.md`: "Passkey unlock", "Watch-only accounts", "Plaintext (http) RPC endpoints", the updated CSP listing, three new threat-model rows, and three new contributor invariants. For custom networks: "Adding your own network" in `USER_GUIDE.md` (the form, where the network then shows up, and what a dApp can see of it), "Networks, including the user's own" in `DEVELOPER.md`, and "What a dApp learns about a custom network" in `SECURITY.md` with the sent/withheld field table.

### Fixed

- **A contract-call prompt hid the one field it was about to sign** (`src/connect/rpc-handler.ts`) — `signContract` fetched the nonce *after* the user approved, and never put it in the prompt, so the user authorised a transaction with a field they were never shown and the prompt could not be compared against the result. The nonce is now resolved before the approval opens and rendered as a row, for both `signContract` and the new `signTransfer`; the same reordering means a nonce fetch that fails now fails before the user is interrupted rather than after they have approved.
- **Any approval prompt could be blanked by the payload it was displaying** (`src/connect/approval-ui/ApprovalPrompt.tsx`) — `JSON.stringify` ran unguarded in the render path over dApp-supplied values, so a `bigint` argument (`TypeError: Do not know how to serialize a BigInt`) or a circular reference threw during render and took the prompt down with it: a request the user could neither read nor reject, and a promise the dApp waits out to a timeout. All payload rendering now goes through a `safeJson` helper that stringifies bigints, replaces cycles with `[circular]`, and falls back to `String(value)` rather than throwing.
- **A stolen keystroke could sign a transaction** (`src/connect/approval-ui/ApprovalPrompt.tsx`) — the popup pulls focus when a prompt appears, and **Approve** was the button that had it, so an Enter or a Space aimed at whatever the user was typing a moment earlier landed on the confirm action. Reject is what takes focus now, and Escape rejects too: the accidental outcome is the safe one, and approving requires a deliberate click or a Tab. The `raw` (untagged) message-signing scheme also gets an explicit warning in the prompt, since that is the one scheme whose signature is not domain-separated.
- **The prompt chime went silent after about six prompts, then kept stealing focus for a second afterwards** (`src/connect/ConnectApp.tsx`, `src/connect/attention.ts`) — each prompt constructed an `AudioContext` and never closed it. Browsers cap them per page (Chrome allows roughly six), so every later prompt threw inside a `try {}` and made no sound at all — the alert stopped working precisely for the user who used the wallet most. It also beeped when the popup was already the focused window, startling people about a prompt they were reading. Alongside it, `window.focus()` was retried at 0, 100, 300, 600 and 1000 ms, three times over for the three code paths that raise a prompt; repeating the call does not make a browser more likely to comply, it just means that if the user tabbed away to copy an address, the popup ripped focus back out from under them up to a second later, mid-keystroke. Replaced by the single `requestAttention()` signal above, which also cleans up — the title used to be left flashing after the request had already been answered.
- **The `/connect` popup logged six internal values every 100 ms in production** (`src/connect/ConnectApp.tsx`) — the handoff deferral loop retries while a prompt is on screen, and each pass wrote a `[handoff]` line, so a user who took ten seconds to read a prompt got a hundred of them. The trace is genuinely useful when debugging the handoff, so it stays behind `import.meta.env.DEV`; what shipped was a scrolling wall of internal state that drowned out anything the user might actually have needed to report.
- **Two impatient Enters in the PIN field burned two of the five unlock attempts** (`src/components/UnlockWallet.tsx`) — PBKDF2 runs for seconds and Enter is the fastest way to start it, but nothing marked an unlock as in progress, so a second Enter spent another `recordPinAttempt` slot on a PIN that was already being checked. Two keystrokes, two attempts, and the 30-second lockout arrives after three real tries. Unlock is now re-entrant-guarded, the buttons and the field disable while it runs, and the button shows `Unlocking…` so there is a reason not to press it again.
- **Unlock showed half a second of invented progress, and reported failures twice** (`src/components/UnlockWallet.tsx`) — the progress modal listed four stages, two of which were marked done the instant they appeared (`PVAC WASM loading in background`, `Connecting in background`), with 500 ms of `setTimeout` inserted between the steps so the fake progress would be visible. Unlock now takes exactly as long as the cryptography takes and describes the two things that really happen (`Checking your PIN`, `Opening your wallet`). Failures were also raised twice — once in the modal that was already open and already showing which step failed, and again as a toast on top of it, two copies of one problem with two different dismiss behaviours. Empty-PIN and lockout complaints moved from toasts to a field-level `role="alert"` message wired up with `aria-invalid`/`aria-describedby`, which clears as soon as the user types, and the success toast now names the wallet that opened instead of announcing the wallet's own background loading. The static **PIN requirements** box was dropped from the unlock screen: it describes what a PIN must satisfy when you *create* one, which is not a thing anyone can act on while trying to get back in.
- **`declare global` in the SDK broke the typecheck of any dApp that also supports the Octra extension (TS2717)** (`src/sdk/inject.ts`) — augmenting `Window` from a library is a land grab: `window.octra` is already typed by the extension's own provider, and TypeScript refuses to merge two `Window` declarations that give one property different types. Because the package entry point imports this module, the error hit builds that never call `injectWalletProvider` at all. The globals are written through a local cast now, and a dApp that wants them typed declares that once, itself, with a type covering every provider it supports — the only place that decision can be made correctly. `tests/unit/sdk-inject.test.ts` asserts the shipped source stays free of `Window` augmentation, and the published `dist/sdk/types/*.d.ts` are checked for the same.
- **The demo dApp could only load the SDK from a dev server** (`public/demo/dapp.html`) — it imported `/src/sdk/index.ts`, which exists in a `vite dev` checkout and nowhere in `dist/`, so the reference integration was broken on the deployed site — the one place a prospective integrator would look at it. It now tries the published bundle first and falls back to the TypeScript source, and its capability list includes `signTransfer`, `ping` and `customNetworks`.
- **The auto-fix pipeline did not build the thing dApps load** (`scripts/autofix.mjs`) — its build step ran `vite build` for the app only, so a change that broke the published SDK bundle (a bad export, or a type error under `tsconfig.sdk.json`'s stricter view) passed typecheck, lint, tests and build, and only failed later in `npm run build` at release time. The step now runs the SDK bundle and its declaration build as well.
- **`vite.config.sdk.ts` was outside every typecheck** (`tsconfig.node.json`) — added to the `include` list, so the config that produces the published bundle is type-checked like the other three.
- **CI failed on every commit: 73 tests across 9 files could not use WebCrypto on Node 20** (`tests/unit/setup.ts`, `.github/workflows/ci.yml`) — jsdom builds its window in a second JS realm and vitest copies that realm's globals onto `globalThis`, so a `Uint8Array` made by app code (or handed back by jsdom's `TextEncoder`) is a foreign object to Node. Node's WebCrypto brand-checks every `BufferSource` against its own realm and Node 20 rejects the lot — `Failed to execute 'importKey' on 'SubtleCrypto': 2nd argument is not instance of ArrayBuffer, Buffer, TypedArray, or DataView` — while Node 22 and newer accept cross-realm views. That is why the suite was green on every development machine and red on CI, which pins Node 20, for months: PIN derivation, wallet encryption, the unlock session, passkeys, stealth addresses and the browser seal all failed there. The test setup now re-wraps each subtle.* argument (including the buffers inside an algorithm dictionary — `iv`, `salt`, `info`, `additionalData`) as a Node-realm view, leaving `CryptoKey` objects untouched. A browser has one realm, so nothing here was a defect in the wallet; the shim belongs to the test environment. The CI matrix now runs Node 20 **and** 22 so a version-specific break of this kind cannot hide again.
- **The PVAC probe made four tests depend on the host's network** (`tests/unit/helpers/pvac-glue.ts`, `tests/unit/pvac.test.ts`, `tests/unit/wallet-store.test.ts`) — `loadPvacModule` HEAD-probes `<origin>/wasm/pvac.js` to tell "never compiled" from "blocked by CSP". Nothing serves that path under test, but the outcome differed per machine: a CI runner refuses the connection at once, whereas a machine with any service on the jsdom origin's port accepts it and never answers, so the request hung until the test timed out. The probe is now stubbed, and the PVAC status assertions poll for a settled state instead of sleeping a fixed 500 ms, which also removes a flake under load.
- **The top-bar network dropdown could not switch network** (`src/components/NetworkSwitcher.tsx`, `src/components/AccountPicker.tsx`, `src/hooks/useAnchoredMenu.ts`, `src/store/wallet-store.ts`) — three faults, each enough on its own. The menu was positioned inside the header's action row, which is `overflow: hidden` at phone widths so that a long account name truncates instead of widening the row: the menu opened, was laid out, was even clickable from a script — and was painted nowhere, so tapping the pill on a phone did nothing at all. `.app-header` is also a stacking context of its own, so a menu inside it could not rise above a toast in the same top-right corner however large its `z-index`, and a toast takes pointer events: on a desktop the click meant for **MAINNET** landed on the *Wallet created* toast instead, which does nothing when clicked. And the click handler skipped the switch whenever the store held no settings — one failed read at boot was enough to cause that for the life of the page, with the pill showing `DEVNET` no matter what was stored. Both header menus now render through a portal as a viewport-anchored `fixed` layer above toasts (new `--z-dropdown`), clamped to stay on screen, and dismissed by an outside pointer-down or Escape (the portal means a `contains()` check on the trigger would otherwise close the menu on its own rows). The switch itself moved into the store as `switchNetwork`, which reads settings back when they are missing, retries a transient storage failure, and merges the four endpoint fields with `patchSettings` so it cannot revert what the language switcher or the Settings panel wrote meanwhile.
- **A failed IndexedDB open poisoned every later attempt, so the wallet could neither read its accounts nor create new ones** (`src/wallet/storage.ts`) — an open request cannot be cancelled, so the request abandoned at the timeout stayed queued in the browser and each retry issued a *second* request that queued behind the first: one failure guaranteed all the rest, and `IndexedDB open timed out. If the wallet is open in another tab, close it and try again.` surfaced at "Deriving HD keypair" while creating a wallet. Retries now attach to the single in-flight request, so the moment the blocking tab closes the pending attempt resolves on its own. Nothing handled `versionchange` either, so a second wallet document (another tab, or the `/connect` popup) on an older `DB_VERSION` blocked the upgrade indefinitely — the connection now steps aside when another document needs to upgrade, and reopens if the browser terminates it. The "does this database exist?" probe and the one-time legacy migration are bounded as well, so neither can stall start-up, and a blocked upgrade fails immediately instead of spending the retries on an outcome that cannot change. `WALLET_READ_TIMEOUT_MS` is derived from the open budget (`DB_OPEN_BUDGET_MS`) so a read can no longer time out while the open beneath it is still retrying.
- **A failed read was reported as "you have no wallet"** (`src/components/UnlockWallet.tsx`, `src/components/AccountPicker.tsx`, `src/connect/ConnectApp.tsx`) — the unlock screen's probe swallowed the error and rendered *No stored wallet found*, and both account pickers blanked their list, so a storage hiccup looked exactly like data loss and pushed the user towards **Create New Wallet** — the one action that can overwrite the keystore they still had. All three now say the read failed, keep any list they had already loaded, and offer **↻ Try again**, which drops the stale connection before retrying.
- **Switching network in the main window never told connected dApps** — `networkChanged` was only ever emitted by the connect popup, but sessions are handed off to the main window when that popup closes, so in practice the event fired almost never: a dApp connected before a switch kept reporting the old network indefinitely. `Layout.tsx` now emits to every adopted handler when the top-bar network pill changes.
- **The connect popup had its own hardcoded network list** — it carried two presets with a stale mainnet RPC (`https://mainnet.octrascan.io/rpc` instead of `https://octra.network/rpc`) and could not see user-added networks at all. It now reads the same `allNetworks()` list as the main window, so the two can no longer drift.
- **Switching network in the popup patched only `rpcUrl`** — the explorer and relayer stayed pointed at the previous network, so links and stealth transfers went to the wrong place. All four endpoint fields are patched together now, matching `NetworkSwitcher`.
- **A torn-down SDK session kept reporting its last network** — `clearSession` cleared the address but not the cached network, so `networkInfo()` could answer for a session that no longer existed. It now clears all three network fields alongside the address.
- **Reloading the page asked for the PIN again mid-session** — the unlocked wallet lived only in the Zustand store, so any refresh dropped it and rendered the unlock screen even seconds after unlocking. The wallet now resumes from the sealed session; the PIN is required only once the session has genuinely ended (explicit lock, tab closed, 30 minutes idle, or the 8-hour cap). `/connect` popups resume the same way instead of re-prompting during a live session.
- **E2E lock button selector** — `tests/e2e/wallet-unlock.spec.ts` and `pvac-auto-load.spec.ts` clicked `button[aria-label="Lock"]`, which never matched the rendered `aria-label="Lock wallet"`.
- **`clearIndexedDB` left the tab's session behind** — the E2E helper now clears `sessionStorage` as well, so a "clean state" reload cannot come back unlocked.
- **Stale transpiled configs came back, and silently froze `vite.config.ts`** — 0.1.0 deleted `vite.config.js` and friends but not the thing that emits them: `tsconfig.node.json` had `composite: true` and no `outDir`, so any `tsc -b` wrote `vite.config.js` next to the `.ts` source, and Vite resolves the `.js` sibling **first**. The regenerated copy predated every config change since, which is how the new CSP build flag appeared to do nothing. Emit for that project now goes to `node_modules/.tmp/tsconfig-node/`, where it cannot shadow a source file.
