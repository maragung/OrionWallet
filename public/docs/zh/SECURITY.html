它无法防护的威胁

请对以下这些情况保持清醒的认识：

  • 设备被攻破。恶意软件、键盘记录器或恶意的浏览器扩展能够在您输入 PIN 码时将其读取，并从内存中提取已解密的密钥。
  • 丢失恢复助记词。不存在任何找回机制。没有人能够恢复它。
  • 钓鱼攻击。如果您在假冒网站上输入了恢复助记词，资金便会丢失。Orion Wallet 在初始设置之后绝不会再向您索要助记词。
  • RPC 节点被攻破。恶意节点可能提供虚假余额或扣留交易。但它无法伪造签名或窃取密钥。
  • 对 npm 依赖项或托管服务提供商的供应链攻击。
  • 在钱包处于解锁状态时对已解锁设备的物理访问。

PIN 码处理

PIN 码绝不会以任何形式被持久化。它在解锁时派生出解密密钥，
随后即被丢弃。不存在"记住我的 PIN 码"——这是刻意的设计。因此，忘记的
PIN 码只能通过从恢复助记词恢复来解决。

解锁会话

PIN 码不会被持久化，但解锁的结果会被持久化，其存续时间与会话相同：
刷新页面绝不能把用户重新丢回 PIN 码界面。src/wallet/unlock-session.ts
会用 AES-256-GCM 密封已解密的钱包，并将其拆分到两个存储中：

分片存放位置存续时间
密文（orion:unlock-session）sessionStorage仅限单个标签页。该标签页关闭即消失
密封密钥IndexedDB 的 unlock-session-keys，作为不可导出的 CryptoKey锁定时删除；孤立项按存在时长清理

任何一个分片单独都无法使用。IndexedDB 在标签页关闭后依然存在，但其中不含密文；
sessionStorage 持有密文却没有密钥，而且第二个标签页或另一来源都无法读取
它。该密钥以 extractable: false 生成，因此本来源可以使用它，但其
字节无法被读出——无论是我们自己的代码，还是任何设法在页面中运行的东西都不行。
会话在每次恢复时都会轮换（新密钥、新 nonce），并将 createdAt
向前传递，从而使刷新无法延长绝对上限。

过期：空闲 30 分钟（可配置，autoLockMinutes；设为 0 可禁用）以及自最初解锁起的8 小时
绝对上限。两者都会在恢复时被强制执行，而空闲窗口还会由 useAutoLock 实时强制执行，
因此一个一直开着的标签页会自行锁定。

它无法防护的情形——坦诚地说：

  • 标签页内的脚本执行。在活动会话期间于页面中运行的代码可以请求浏览器解密会话，然后用密钥进行签名，其做法与钱包完全相同。它无法窃取密封密钥，因此这种攻破止步于该标签页；它不会变成一个可在别处使用的被盗密钥。
  • 设备被攻破。与上文威胁模型中所述相同：本地恶意软件可以同时读取 IndexedDB 和 sessionStorage。
  • 不安全的上下文。在没有 crypto.subtle 的情况下（纯 http://，见下文），密封密钥会退回为 IndexedDB 中的原始字节，不可导出性保证随之丧失。但拆分与过期机制仍然有效。

若要完全退出该功能，请关闭 Settings → Security → Stay unlocked after a page refresh
（keepUnlocked: false）。不会写入任何内容，并且每次重新加载都会要求输入 PIN 码——这正是
该功能存在之前的行为。一次显式的锁定（🔒）会立即销毁两个分片。

通行密钥解锁

该功能是可选的、默认关闭且属于附加性质：它是打开既有钱包的第二种方式，绝不
用于替代 PIN 码。src/wallet/passkey.ts。

注册会创建一个平台凭据，其 userVerification: 'required'，并启用
WebAuthn 的 PRF 扩展。PRF 会向页面提供一个由凭据和一个已存储的 32 字节盐值派生出的
机密，浏览器只有在用户完成验证后才会生成它。钱包取 sha256("orion-passkey-unlock-v1" || prf) 作为一个 AES-256 密钥，
用 AES-256-GCM 密封序列化后的钱包，将该密钥清零，并把密封后的数据块存入 IndexedDB，
紧邻凭据 ID 和盐值存放。

已存储未存储
凭据 ID、PRF 盐值、IV、钱包的密文PRF 输出、派生密钥、PIN 码、任何明文密钥材料

值得坦白说明的一些后果：

  • PRF 是必需的，绝不降级。如果认证器不支持它，注册就会抛出异常且不存储任何内容。另一种做法——把一个可读的密钥与密文一同保存——会使该记录能够自我解密，这比不提供此功能更糟。
  • 该记录本身是惰性的。如果没有在该认证器上完成一次成功的、经用户验证的操作，就无法从磁盘上的内容派生出密钥。
  • 它密封的是钱包，而非 PIN 码。PIN 码仍然是唯一能够导出密钥、显示助记词、更改 PIN 码或派生账户的凭据。因此通行密钥解锁无法被用来提权到这些操作，而且所存储的记录泄露的信息严格少于存储 PIN 码会泄露的信息。
  • 与 PIN 码解锁采用相同的会话模型。通行密钥解锁产生的解锁会话完全相同，具有相同的空闲上限和绝对上限；它不会延长其中任何一个。
  • 限定于该设备和浏览器。它绑定到来源的 rpId 并存储在本地。它不属于钱包导出的一部分，也不是从恢复助记词派生的。
  • 过期的凭据会安全失败（fail closed）。如果解密失败——凭据被轮换或重新注册、设备被恢复——则该记录会被删除，并要求输入 PIN 码。而被取消或超时的操作被刻意设计为不删除它，因此一次被取消的提示无法悄无声息地禁用此功能。
  • 对仅观察账户拒绝启用。没有可供密封的密钥材料。

它无法防护的情形保持不变：设备被攻破，以及活动会话中的
脚本执行，与上文解锁会话的情况完全相同。它确实消除了一处真实的暴露面——
即每次解锁时都要输入并可能被观察到的 PIN 码。

仅观察账户

账户可以仅凭地址添加，而无需密钥库。其不变式是：这样的账户永远无法签名，
并且该约束是在签名实际发生之处强制执行的，而非在 UI 中：assertCanSign（src/wallet/watch-only.ts）会被
发送、加密、隐身、合约以及 dApp 请求等路径调用，并在抛出异常时同时指明操作与修复方法。

它在设计上就是安全失败的：该检查会拒绝任何私钥不是完整 64 字节 Ed25519 密钥的钱包，
因此即便 watchOnly 标志不知何故丢失，被截断或缺失的密钥也会被拒绝。该标志会通过 serializeWallet/deserializeWallet 传递，
因此从解锁会话恢复的钱包仍然是仅观察的。

随机性

所有与安全相关的值都通过 src/crypto/random.ts 使用 crypto.getRandomValues。

src/sdk/protocol.ts 中的 makeId 带有一个 Math.random 回退。它仅用于
消息关联 ID，绝不用于安全值，并且已如此注明。请勿将其
重用于挑战值、nonce、密钥或盐值。

浏览器安全态势

Content-Security-Policy

在 index.html 中设置：

default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; font-src 'self' data:;
connect-src 'self' https: http://localhost:* http://127.0.0.1:* http://[::1]:*;
frame-src 'self' https:; worker-src 'self' blob:; object-src 'none';
base-uri 'self'; form-action 'self';

其中有三项条目值得解释：

  • 'wasm-unsafe-eval' 是 PVAC FHE 模块所必需的。没有它，Chromium 会阻止 WebAssembly.instantiate()。它仅允许 WebAssembly 编译——它并不会重新启用 JavaScript 的 eval()。
  • 用于样式的 'unsafe-inline' 是那段绘制前的关键 CSS 所需要的，以避免出现无样式内容闪烁（flash of unstyled content）。它仅适用于样式，绝不适用于脚本。
  • connect-src 中的环回地址让本地运行的节点得以使用，而无需将策略整体放宽到明文。发往 localhost / 127.0.0.0/8 / [::1] 的流量永远不会离开本机，因此线路上没有任何可供拦截的内容。

明文（http）RPC 端点

通过纯 http:// 传输的其他任何内容默认都会被拒绝，而 src/wallet/endpoint-policy.ts
是唯一做出该判定的地方。它是一个仅依赖 URL 加上一个显式上下文的纯函数，
因此存储、Settings UI 与测试之间不会对何为允许产生分歧。

会有三重相互独立的阻断器生效，而判定结果会首先指出其中最根本的那一个，
这样当混合内容才是真正原因时，用户就绝不会被告知去修改允许列表：

阻断器由谁强制执行如何解除
混合内容由浏览器无条件执行无法解除。请使用 TLS 或代理
Content-Security-Policy随产品发布的 meta 标签 CSP使用 VITE_ALLOW_HTTP_ENDPOINTS=1 重新构建
用户同意设置中的 allowedInsecureOrigins在 Settings → Network 中 Trust（信任）该来源

关于该设计的一些说明：

  • CSP 是一个 meta 标签，因此它无法在运行时被放宽——没有任何设置能够授予这一点，这正是它是一个构建标志的原因。VITE_ALLOW_HTTP_ENDPOINTS=1 只会在构建时把 http: 追加到 connect-src，除此之外别无其他；在此之上仍然需要用户同意。
  • 同意是按来源给出的——即协议、主机和端口。它不是主机名匹配，也不是 URL 前缀匹配，因此信任 http://node.lan:8080 并不会信任该主机上的另一个端口，而 http://127.0.0.1.evil.com 也不会被当作环回地址。
  • 区块浏览器 URL 是豁免的，因为它们始终只是 <a href> 导航，而非 fetch 请求。connect-src 和混合内容对它们都不适用。relayerUrl 会被存储但从不被 fetch。只有 rpcUrl 受此策略约束。
  • 被阻断的端点仍然会刻意地构建一个 RpcClient：拒绝构建它会使用户无法进入 Settings 去修复它。取而代之，其原因会以标题栏中的一个 ⚠️ Insecure RPC 徽标以及 RpcClient.unreachableHint 的形式呈现，后者只会被追加到被抛出的 TypeError 上——绝不会追加到真正的服务器错误或超时上，因为那会产生误导。
  • rpcProxyUrl 会把该决策转移到代理上：端点将依据代理自身的协议来判定，因为那才是浏览器实际连接的对象。代理会看到每一个请求，因此 UI 建议运行你自己的代理。它无法接触密钥或进行签名。

明文 RPC 既是机密性也是完整性上的暴露面——路径上的节点可以读取
每一次查询并篡改回复——但它不是密钥泄露层面的暴露面：签名是在本地
产生的，而且钱包不会把它收到的任何内容验证进密钥材料中。

COOP/COEP 在整个应用范围内为 same-origin / require-corp，并在 /connect 上
以 unsafe-none 覆盖，从而使审批弹窗能够与其打开者交换 MessagePort。

dApp 连接安全

当一个站点请求连接时：

  1. 弹窗会醒目地显示发起请求的来源。
  2. 用户必须显式批准；对于新来源不存在静默连接。
  3. 批准仅限于该来源，并按来源持久化。
  4. 签名操作始终需要确认，即便对于受信任的站点也是如此。

"Trust this site" 仅会抑制针对只读请求（余额、账户、
网络）的提示。它绝不会授予静默签名。

可以在 Settings → Connected Sites 下查看并撤销连接。

dApp 能了解到关于自定义网络的哪些信息

用户手动添加的网络对已连接的站点是可见的（wallet_getNetworkInfo、
wallet_getNetworks 以及 networkChanged 事件），因为 dApp 若不知道自己处于哪个网络，
就无法渲染出正确的区块浏览器链接或链标签。经由网络传输的那条记录是一个刻意划定的子集：

发送保留（不发送）
id、name、explorerUrl、icon、customrpcUrl、relayerUrl

这些端点之所以被保留而不发送，是因为用户添加的网络通常是私有的——一个局域网
地址、一条隧道、一个把 API 密钥放在查询字符串里的付费提供商 URL。连接到某个
站点不应当泄露用户节点所在的位置，也不应当交出一个带凭据的 URL。这不会损失任何
功能：读取会经由钱包代理，交易也由钱包构建并广播，因此 dApp 从不需要自行访问 RPC。

有两点后果值得了解：

  • 自定义网络的名称由用户自行选定，并会展示给 dApp。若以某个个人标识来命名网络，就会把该标识泄露给你连接的每一个站点。
  • wallet_getNetworks 会暴露你已配置多少个网络。这是一个较小的指纹识别暴露面，之所以接受它，是为了让 dApp 能够提供"切换到 X"这样的引导。

任何 dApp 都无法更改网络。不存在 wallet_switchNetwork 方法；切换只发生在
钱包自己的 UI 中，dApp 事后通过 networkChanged 得知。

依赖状态

生产依赖：零已知漏洞（npm audit --omit=dev）。

开发依赖在 vitest、vite、esbuild 及相关包中带有安全公告。
剩余的每一项修复都需要一次大版本升级（vite 5→8、vitest 2→4），而这有破坏
构建的风险。这些包属于构建工具——它们不会随产品发布给用户，也无法影响

这是一个刻意的权衡，并会在每次发布时重新评估。运行 npm audit --omit=dev 即可
确认所发布的暴露面保持干净。

面向用户的指南

应当做

  • 将恢复助记词离线保存在纸上，并存放于不止一个地点
  • 发送前逐字核对收款地址
  • 在每一次 dApp 连接提示中核实来源
  • 使用新地址时先发送一笔小额测试金额
  • 保持浏览器和操作系统更新

切勿

  • 在初始设置之后于任何网站上输入恢复助记词
  • 以数字形式存储助记词——不要截图、云端笔记或聊天消息
  • 分享你的私钥或 .oct 备份文件
  • 在共享或不受信任的计算机上使用持有真实资金的钱包

面向贡献者

不得削弱的、对安全敏感的不变式：

  • 对每一条入站 postMessage 进行来源校验
  • 所有安全值均使用 CSPRNG；makeId 不算其中之一
  • localStorage、sessionStorage、日志或错误消息中不得存放机密
  • 不使用 innerHTML 或 dangerouslySetInnerHTML
  • PIN 码绝不持久化
  • 通行密钥解锁需要 PRF；绝不退回到存储一个可读的密钥
  • assertCanSign 守护每一条签名路径——仅观察账户绝不允许签名
  • 明文端点策略保持集中在 endpoint-policy.ts 中；不得在别处进行临时的 URL 检查
  • 规范化 JSON 保持逐字节精确——签名依赖于它

任何触及密码学、密钥处理、存储或连接流程的改动，都应在 pull request 中
明确予以说明。
