环境搭建

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps 是必需的：ESLint 9 与 @eslint/js 10 声明了相互冲突的 peer
版本范围。vercel.json 使用了相同的标志，因此 CI 与本地安装保持一致。

推荐使用 Node 20+。

架构

纯客户端；没有后端。数据以单一方向流动：

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

设计约束

规范化 JSON 必须做到字节精确。src/tx/canonical-json.ts 精确地复现了
nlohmann::json 的键排序与格式。签名是在这些字节之上计算的，
因此任何偏差都会产生一个被网络拒绝的签名。请勿"整理"这个
序列化器。

命名：产品与协议之分。"Orion Wallet" 是产品名。octra_* RPC 方法、
oct 地址前缀、OCT 代币符号，以及 "Octra Network" 都是协议标识符，
绝不可重命名。

构建系统

TypeScript 配置文件是唯一可信来源：

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
不要为这些文件添加 .js 同名副本。Vite 会优先解析 vite.config.js 而非
vite.config.ts，因此一个陈旧的转译副本会悄悄遮蔽真正的配置，而对
.ts 文件的编辑则毫无作用。那三个文件名已列入 .gitignore。
eslint.config.js 是真正的扁平配置，是有意保留的。

仅仅忽略它们本身还不够，因为没有任何东西能阻止它们被创建：
tsconfig.node.json 是一个 composite 项目，这会强制发出声明文件，而在没有
outDir 的情况下，任何 tsc -b 都会把 vite.config.js 直接写在源代码旁边。这已发生过两次。
该项目的输出现在会写入 node_modules/.tmp/tsconfig-node/，在那里它无法遮蔽
任何东西。如果您向该项目添加配置文件，请不要改动 outDir。

环境变量标志

标志作用
VITE_ALLOW_HTTP_ENDPOINTS=1在构建时向 connect-src CSP 指令追加 http:，使自托管的构建版本能够访问纯 http 的 RPC 节点。按来源的用户同意仍然适用——参见 src/wallet/endpoint-policy.ts

仅在构建时设置。它由 vite.config.ts 中的 allowHttpEndpointsCsp 插件读取，
并会改写 index.html；它没有运行时效果，因为 meta 标签形式的 CSP 一旦文档被解析
就无法再放宽。

HTTP 头

COOP/COEP 设置为 same-origin / require-corp（为将来的 WASM 线程化预留），
并在 /connect 上以 unsafe-none 覆盖，以便弹窗的 postMessage + MessagePort
传递能够正常工作。开发环境的头位于 vite.config.ts 中；生产环境的头位于 vercel.json 中。
请保持两者同步。

Content-Security-Policy

在 index.html 中定义。script-src 必须包含 'wasm-unsafe-eval'——否则 Chromium 会拒绝
WebAssembly.instantiate()，而这正是当初导致 PVAC 模块悄无声息加载失败的原因。
该指令仅允许 WebAssembly 编译；它不会重新启用
JavaScript 的 eval()。

connect-src 为 'self' https: 外加环回地址（http://localhost:*、http://127.0.0.1:*、
http://[::1]:*），因此本地运行的节点可以工作，而无需在总体上开放明文。任何
其他通过 http:// 的访问都由 src/wallet/endpoint-policy.ts 把关，它是唯一进行
裁决的地方——一个关于 URL 加显式上下文的纯函数，因此 store、设置界面
和测试之间不可能出现分歧。请勿在别处添加临时的 URL 检查。会有三道相互独立的
拦截（混合内容 → CSP → 用户同意），而裁决会最先报告最
根本的那一道，因此当真正拒绝的是浏览器时，用户绝不会被告知去修改白名单。

PVAC WASM 流水线

构建

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py 是必需的，因为在没有硬件 AES（AES-NI 或
ARM 加密扩展，而 WebAssembly 并不提供）的情况下，PVAC 会硬性 #error 报错。该补丁添加了一个可移植的
软件实现，其结果逐位相同，但速度大约慢 5–10 倍。它是增量式的：
硬件路径保持不变，并会写入一个 .hpp.bak 备份。

加载

src/pvac/wasm-bridge.ts 分三步加载该模块：

  1. 探测（Probe） — 对胶水代码 URL 发起 HEAD 请求，从而把"未构建"（404）与"被 CSP 拦截"区分开来。没有这一步，两者都会表现为完全相同、无从分辨的不透明导入失败。
  2. 导入（Import） — 带 /* @vite-ignore */ 对一个绝对 URL 执行动态 import()。它必须是绝对路径：裸模块说明符无法解析，而 ./wasm/pvac.js 会相对于 /assets/ 解析并返回 404。
  3. 校验（Verify） — 在换入该桥接之前，断言全部 13 个必需的 _pvac_* 导出都存在。早期的构建版本遗漏了序列化函数，破坏了加密/解密，而节点仅将其报告为"malformed transaction"。

失败会被归类为 PvacFailureReason：not-built、csp-blocked、
missing-exports、init-failed、unknown。每一种都对应设置中
显示的一个具体补救措施。失败时单例 promise 会被重置，因此 ↻ Reload PVAC 可以重试，
而不是重放一个已缓存的拒绝结果。

内存规则

该 C API 采用手动内存管理。每一个 _malloc 都需要一个 _free；每一个 serialize_* 都会返回一个
必须用 _pvac_free_bytes 释放的缓冲区。来自 keygen/enc_* 的句柄需要
与之匹配的 _pvac_free_*。请使用 try/finally——其写法参见 WasmPvacBridge。

状态管理

使用 Zustand，位于 src/store/wallet-store.ts。它持有钱包、RPC 客户端、设置、PVAC
状态、toast 提示，以及全局加载标志。

全局加载标志（isLoading）会驱动一个全屏模糊遮罩，且仅保留给整个应用级别的
过渡，例如钱包解锁。分面板的工作必须改用
usePanelLoading——见下文。

错误处理

src/components/ErrorBoundary.tsx 在 Layout.tsx 中包裹每一个面板，并以当前激活的
标签页作为 key，使被触发的边界在导航时重置；此外在 main.tsx 的根部还有一个边界。

这比看上去更重要。index.html 中包含：

#root:empty::before { content: 'Loading Orion Wallet…'; }

如果没有边界，任何渲染期抛出的异常都会让 React 18 卸载整棵树，#root
变为空，于是该回退内容便会渲染——产生一个看似永远卡在加载中的空白页面。
边界会让外壳保持存活，并显示一张可重试的错误卡片。

由此带来的后果：在渲染期间调用的函数不得因输入格式错误而抛出异常。
src/tx/builder.ts 中的 formatAmount 接受 unknown 并降级为一个占位符，
因为 RPC 响应和本地交易缓存都未经过 schema 校验。请在渲染不受信任的行之前
先对其进行规范化——HistoryView 展示了这一写法。

加载状态

对于面板范围内的工作，请使用 usePanelLoading（src/hooks/usePanelLoading.ts）：

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

然后渲染 <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />。

有两个特性很重要：该模态框是可关闭的（工作会在后台继续，因此
缓慢的网络绝不会困住用户），并且状态写入以 isMounted() 为前提，
因此中途导航离开不会让模态框卡在屏幕上。

存储与迁移

通过 idb 使用 IndexedDB，数据库为 orion-wallet，版本 6。各存储在
src/wallet/storage.ts 的 OBJECT_STORES 数组中统一声明；请在那里添加新的存储，以便创建与
迁移保持一致——该数组同时驱动 wipeEverything()，因此在别处添加的存储
会在一次清除后残留下来。

迁移只能是增量式的：递增 DB_VERSION，向数组追加条目，并在新条目旁的注释中
记录版本号。现有存储绝不会被重命名或删除。
迄今的版本：v2 SDK 存储、v3 OCS01 代币、v4 oct:// 书签、v5
unlock-session-keys、v6 contacts + passkey-unlock。

品牌更名迁移

把数据库从 webcli-react 重命名，会使每一个现有钱包成为孤儿，因为
IndexedDB 是按数据库名称来划分数据范围的。migrateLegacyDatabase 会在首次
启动时把所有存储向前复制。它具有以下特性：

  • 幂等 — 一旦目标数据库中已有任何钱包便会跳过
  • 非破坏性 — 旧数据库保持完好，以便回滚
  • 非致命 — 失败会被记录，绝不抛出；迁移中的 bug 绝不可阻塞启动

请记住，E2E 辅助工具中的 clearIndexedDB 必须删除两个数据库，否则
迁移会把旧数据又原样复制回来，"干净状态"便不再干净。

钱包 SDK

src/sdk/ 是面向 dApp 的 provider；src/connect/ 是在
/connect 提供的审批弹窗。

该钱包同时响应两个等价的命名空间：

wallet_signMessageorion_wallet_signMessage签署一条普通消息
wallet_signTypedDataorion_wallet_signTypedData签署结构化数据

以便现有的集成继续工作。

src/sdk/protocol.ts 中的 canonicalizeMethod 会在分发之前，把每一个方法名归约为其规范的
wallet_* 形式，因此两个命名空间绝不会彼此失去同步。

连接生命周期

握手（每个会话一次）：

  1. dApp 调用 provider.connect() → PopupTransport 打开 /connect?v=1&rid=…&origin=…
  2. 钱包渲染 ConnectApp，用户按需解锁
  3. 钱包通过 window.postMessage 发送 hello + MessagePort，并经过来源校验
  4. dApp 通过该端口回传 challenge（防重放）
  5. ConnectHandler 校验 ack，提供 CONNECT RPC → 返回地址、账户、网络

连接之后：

  • 弹窗可以关闭，但 MessagePort 仍保持打开——它独立于窗口
  • 会话会持久保存在 IndexedDB（sdk-sessions）中，带有空闲 + 绝对 TTL
  • 读取类方法（getBalance、getAccounts）在会话期内静默进行
  • 签名类方法始终会弹出一个新的审批提示

针对"连接能用，别的都不能用"的修复：

最初 PopupTransport.isConnected() 检查的是 popup.closed，因此审批窗口关闭之后的
每一次调用都会以"Transport is not connected"失败。现在它只检查
端口，而端口的存活时间长于弹窗。钱包会在审批之后关闭弹窗，但
连接保持存活。

权限模型

连接时：仅授予只读作用域（viewAccounts、viewBalance、viewNetwork）。

签名作用域（signMessage、signContract 等）会在首次
成功批准时惰性授予。在此修复之前，它们不在 DEFAULT_PERMISSIONS 之中，
分发器会在提示能够出现之前就以 UNAUTHORIZED 拒绝每一次签名调用——
这正是该症状的第二个根因。

现在：

  • 权限检查允许未被授予的签名作用域继续进入审批提示
  • 批准后，grantPermission 会将该作用域持久化到会话中
  • 后续调用会跳过权限检查，但仍然需要批准——授予一个作用域只是记录了用户同意该 dApp 可以发起请求

撤销是显式的：revokePermission 会把该作用域从 permissions 中移除，并将其记录到
deniedPermissions 中，分发器会对其直接拒绝。

安全性不变式

请勿削弱以下各项：

  • 对每一条入站 postMessage 进行来源校验（PopupTransport.ts、rpc-handler.ts）
  • 防重放：CSPRNG 挑战值 + dApp nonce + 每会话单调递增的 nonce。makeId 仅用于消息关联，绝不可用作安全值
  • 权限是按来源划分的，持久化在 sdk-sessions 中，并显式地授予/撤销
  • MessagePort 的独立性：该端口的存活时间长于弹窗。一旦被转移，钱包便可以关闭审批窗口而不会中断连接
  • 被禁止的方法在客户端（WalletProvider）和钱包端（rpc-handler）都会被拒绝，因此交易执行绝不会逃逸到 SDK 中，即便通过底层的 request() 逃生舱口也不行
  • localStorage 只保存一个会话恢复提示（地址、网络）——绝不保存机密

dApp 集成

快速开始

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

会话管理

Orion 会话会在空闲 30 分钟后或达到绝对 8 小时后过期。SDK 提供了
内置的会话健康检查和自动重连：

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

网络（包括用户自建的网络）

用户可以在 Settings → Network 中添加自己的网络（自己的节点、devnet 分叉、
付费 RPC）。这些网络是一等公民：它们会与预设一同出现在连接弹窗的选择器中，
并且已连接的 dApp 也能看到它们。

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

在依赖上述任何功能之前，请先针对 customNetworks 能力进行特性检测——较旧的
钱包构建版本只会响应裸的 wallet_getNetwork，其返回的是一个 id 字符串。

NetworkInfo 刻意不携带 rpcUrl，也不携带 relayerUrl。用户自建的
网络往往是私有端点——一个局域网地址、一条隧道、一个把 API 密钥放在查询字符串里的
提供商 URL——把它交给用户连接的每一个站点都会泄露其基础设施。dApp 并不需要它：每一次
读取都经由钱包（wallet_getBalance 及同类方法），而执行绝不会离开钱包 UI。经由网络
传输的只是 dApp 合理需要的信息——它正在与哪个网络通信、所有者是否是手动添加的
（custom），以及在何处链接一笔交易（explorerUrl）。

不存在 wallet_switchNetwork。切换始终留在钱包自己的 UI 中——弹窗的
选择器或主窗口的网络标签（network pill）——这与"状态变更绝不由 dApp 发起"的规则一致。
需要切换到另一网络的 dApp 会请求用户进行切换，然后等待 networkChanged。

networkChanged 会从可能发生切换的两个位置发出：连接弹窗和主窗口。
当弹窗关闭时，会话会移交给主窗口，因此当大多数用户触碰网络标签时，弹窗早已消失——
Layout.tsx 会向被接管的处理器发出事件，从而不会让已连接的 dApp 显示过期的网络。

有两个相互独立的类实现了 WalletHost——src/connect/host.ts（主窗口）以及
src/connect/ConnectApp.tsx 中的一个内联 host（弹窗）。向该接口新增的任何内容都必须
在两者中都实现，此外还要更新 tests/unit/connect-handler.test.ts 中的测试夹具。

被禁止的方法

SDK 会在这些方法到达传输层之前于本地将其拦截。钱包还会在服务端
再次检查，因此交易执行绝不会逃逸：

  • wallet_sendTransaction / sendTransaction
  • wallet_broadcastTransaction / broadcastTransaction
  • wallet_transfer / transfer
  • wallet_swap / swap
  • wallet_bridge / bridge

会话管理

Orion Wallet 的会话由 SDK 自动管理。会话会在以下情况后过期：

  • 空闲超时：30 分钟无活动
  • 绝对超时：自连接起 8 小时

dApp 可以随时检查会话健康状况：

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

当会话过期时，钱包会发出一个 sessionExpired 事件。dApp 应当
监听该事件并提示用户重新连接：

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

会话恢复是自动处理的——钱包会将会话提示保存在
IndexedDB 中，因此过期后重新连接无需用户重新导入其钱包。

E2E 提示：在相信满屏的 Playwright 失败之前，请先检查机器，而不是 diff。
有两种环境限制会产生看起来与真正回归一模一样的失败：

  • 临时空间。Chromium 会把每个浏览器配置文件放在 TMPDIR（默认 /tmp）之下。如果
    该文件系统已满——当 /tmp 是一个与其他进程共享的小型 tmpfs 时很容易发生——
    上下文会在启动时崩溃，无关的测试会在数毫秒内失败，或者一直挂起到 30 秒
    超时。请先执行 df -h /tmp；在一个宽裕的文件系统上以 TMPDIR=$HOME/.cache/e2e-tmp 重新运行，
    同样的测试用例便会从超时变为在约 4 秒内通过。
  • 内存。每个 worker 大约需要 2 GB 空闲内存。内存耗尽时，Chromium 会在测试
    进行到一半时被杀掉，Playwright 会报告 Target crashed；请以 --workers=1 重新运行。

playwright.config.ts 设置了 reuseExistingServer: !isCI，因此端口 4173 上遗留的
npm run preview 会被静默复用——包括从另一个检出目录启动的实例。在比较两棵
代码树时，请在两次运行之间杀掉该监听进程（ss -lptn | grep 4173），否则第二次
运行测试的其实是第一次的构建。

修复缺陷时，请添加一个记录该失败模式的测试，而不仅仅是修复本身。
tests/unit/history-view.test.ts 和 error-boundary.test.tsx 就遵循了这一点：
每个测试都点明了它所要防止复发的症状。

已知问题

开发依赖安全公告。npm audit 会报告 vitest、vite、esbuild 及相关包中的
漏洞。剩余的每一项修复都需要一次大版本升级（vite 5→8、vitest 2→4）。
这些仅属于构建工具，并不会随产品发布给用户；生产环境的审计结果是干净的。参见
SECURITY.html。

storage.ts 分块警告。构建过程会警告 storage.ts 同时被静态导入和
动态导入，因此无法被拆分到它自己的 chunk 中。这是无害的，但它确实意味着
HistoryView 和 WalletExportImport 中的动态导入不会带来任何代码分割的收益。

软件 AES 性能。WASM AES 回退实现比原生实现慢 5–10 倍。繁重的 PVAC
操作会阻塞主线程；将它们移入 Web Worker 是合乎逻辑的下一步。
