Configurazione

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps è obbligatorio: ESLint 9 e @eslint/js 10 dichiarano intervalli di
peer dependency in conflitto. vercel.json usa la stessa opzione, quindi CI e installazioni
locali combaciano.

È consigliato Node 20+.

Puramente lato client; non esiste un backend. I dati scorrono in una sola direzione:

React components  (src/components/)
       │  read state, dispatch actions
       ▼

       │
       ▼

       │

       ├──► PVAC FHE     (src/pvac/)     WebAssembly

Vincoli di progettazione

Il JSON canonico deve essere byte-esatto. src/tx/canonical-json.ts riproduce
l'ordinamento delle chiavi e la formattazione di nlohmann::json esattamente. Le firme sono
calcolate su questi byte, quindi qualsiasi deviazione produce una firma che la rete rifiuta. Non
"sistemare" questo serializzatore.

Nomi: prodotto contro protocollo. "Orion Wallet" è il prodotto. I metodi RPC octra_*,
il prefisso di indirizzo oct, il ticker OCT e "Octra Network" sono identificatori di
protocollo e non devono mai essere rinominati.

Sistema di build

I file di configurazione TypeScript sono l'unica fonte di verità:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
Non aggiungere equivalenti .js per questi. Vite risolve vite.config.js prima di
vite.config.ts, quindi una copia transpilata obsoleta oscura silenziosamente la configurazione reale e le
modifiche al file .ts non hanno effetto. Quei tre nomi di file sono in .gitignore.
eslint.config.js è una vera flat config ed è tenuto di proposito.

Ignorarli non bastava da solo, perché nulla impediva che venissero creati:
tsconfig.node.json è un progetto composite, che forza l'emissione delle dichiarazioni, e senza un
outDir qualsiasi tsc -b scriveva vite.config.js proprio accanto al sorgente. È successo due volte.
L'emissione di quel progetto ora va in node_modules/.tmp/tsconfig-node/, dove non può oscurare
nulla. Se aggiungi un file di configurazione a quel progetto, lascia stare il outDir.

Flag di ambiente

FlagEffetto
VITE_ALLOW_HTTP_ENDPOINTS=1Aggiunge http: alla direttiva CSP connect-src al momento della build, così una build self-hosted può raggiungere un nodo RPC in http semplice. Il consenso dell'utente per origine continua comunque ad applicarsi — vedi src/wallet/endpoint-policy.ts

Impostata solo al momento della build. Viene letta in vite.config.ts dal plugin
allowHttpEndpointsCsp e riscrive index.html; non ha alcun effetto a runtime, perché una CSP
tramite meta tag non può essere ampliata una volta che il documento è stato analizzato.

Header

COOP/COEP sono impostati a same-origin / require-corp (riservati per il futuro threading WASM),
con override unsafe-none su /connect perché funzionino il postMessage del popup e il
trasferimento del MessagePort. Gli header di sviluppo vivono in vite.config.ts; quelli di produzione in vercel.json.
Mantieni i due sincronizzati.

Content-Security-Policy

Definita in index.html. script-src deve includere 'wasm-unsafe-eval' — Chromium rifiuta
WebAssembly.instantiate() senza di esso, che è esattamente ciò che faceva fallire silenziosamente il
caricamento del modulo PVAC. Quella direttiva consente solo la compilazione di WebAssembly; non
riabilita eval() di JavaScript.

connect-src è 'self' https: più il loopback (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*) così un nodo eseguito in locale funziona senza aprire il plaintext in generale. Qualsiasi
altra cosa su http:// è regolata da src/wallet/endpoint-policy.ts, che è l'unico posto che
decide — una funzione pura dell'URL più un contesto esplicito, così lo store, la UI di Settings e i test
non possono essere in disaccordo. Non aggiungere controlli URL ad hoc altrove. Si applicano tre blocchi
indipendenti (mixed content → CSP → consenso dell'utente) e il verdetto riporta prima quello più
fondamentale, così all'utente non viene mai detto di sistemare l'allowlist quando è il browser a rifiutare.

La pipeline PVAC WASM

Compilazione

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py è necessaria perché PVAC si ferma con un #error se manca l'AES
hardware (AES-NI o estensioni crittografiche ARM), che WebAssembly non offre. La patch aggiunge
un'implementazione software portabile, bit-identica ma circa 5–10× più lenta. È additiva: i
percorsi hardware restano intatti e viene scritto un backup .hpp.bak.

Caricamento

src/pvac/wasm-bridge.ts carica il modulo in tre passaggi:

  1. Sonda — HEAD sull'URL della colla (glue), così "non compilato" (404) è distinguibile da
    "bloccato dalla CSP". Senza questo, entrambi emergono come un identico fallimento di importazione opaco.
  2. Import — import() dinamico di un URL assoluto con /* @vite-ignore */. Deve essere
    assoluto: uno specifier nudo non si risolve e ./wasm/pvac.js si risolve rispetto a
    /assets/ e dà 404.
  3. Verifica — asserisci che esistano tutte le 13 esportazioni _pvac_* richieste prima di
    sostituire il bridge. Le build precedenti omettevano le funzioni di serializzazione, il che rompeva
    cifratura/decifratura in un modo che il nodo riportava solo come "malformed transaction".

I fallimenti sono classificati come PvacFailureReason: not-built, csp-blocked,
missing-exports, init-failed, unknown. Ciascuno corrisponde a un rimedio concreto mostrato in
Settings. La promise singleton viene azzerata in caso di fallimento, così ↻ Reload PVAC può
riprovare invece di ripetere un rifiuto in cache.

Regole di memoria

L'API C è a memoria manuale. Ogni _malloc richiede un _free; ogni serialize_* restituisce un
buffer che deve essere rilasciato con _pvac_free_bytes. Gli handle da keygen/enc_* richiedono
il corrispondente _pvac_free_*. Usa try/finally — vedi WasmPvacBridge per il pattern.

Gestione dello stato

Zustand, in src/store/wallet-store.ts. Possiede il wallet, il client RPC, le impostazioni, lo
stato PVAC, i toast e il flag di caricamento globale.

Il flag di caricamento globale (isLoading) guida un overlay di sfocatura a schermo intero ed è
riservato solo alle transizioni dell'intera app, come lo sblocco del wallet. Il lavoro per
singolo pannello deve usare usePanelLoading — vedi sotto.

Gestione degli errori

src/components/ErrorBoundary.tsx avvolge ogni pannello in Layout.tsx, con chiave basata sulla
scheda attiva così un boundary scattato si azzera alla navigazione, più un boundary alla radice in main.tsx.

Questo conta più di quanto sembri. index.html contiene:

#root:empty::before { content: 'Loading Orion Wallet…'; }

Senza un boundary, qualsiasi throw in fase di render fa smontare a React 18 l'intero albero, #root
diventa vuoto e viene mostrato quel fallback — producendo una pagina bianca che sembra bloccata in
caricamento per sempre. Il boundary mantiene vivo lo shell e mostra una scheda di errore con retry.

Conseguenza: le funzioni chiamate durante il render non devono lanciare eccezioni su input malformati.
formatAmount in src/tx/builder.ts accetta unknown e degrada a un segnaposto,
perché né le risposte RPC né la cache locale delle transazioni sono validate da uno schema. Normalizza
le righe non fidate prima di renderizzarle — HistoryView mostra il pattern.

Stati di caricamento

Usa usePanelLoading (src/hooks/usePanelLoading.ts) per il lavoro con ambito di pannello:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

Poi renderizza <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />.

Due proprietà contano: il modal è chiudibile (il lavoro continua in background, quindi una rete
lenta non intrappola mai l'utente) e le scritture di stato sono condizionate da isMounted(), così
allontanarsi a metà operazione non può lasciare un modal bloccato a schermo.

Archiviazione e migrazioni

IndexedDB tramite idb, database orion-wallet, versione 6. Gli store sono dichiarati una sola
volta nell'array OBJECT_STORES in src/wallet/storage.ts; aggiungine di nuovi lì, così creazione
e migrazione restano coerenti — quell'array guida anche wipeEverything(), quindi uno store aggiunto
altrove sopravvivrebbe a una pulizia.

Le migrazioni sono solo additive: incrementa DB_VERSION, accoda all'array e annota la
versione in un commento accanto alle nuove voci. Gli store esistenti non vengono mai rinominati o eliminati.
Le versioni finora: v2 store SDK, v3 token OCS01, v4 segnalibri oct://, v5
unlock-session-keys, v6 contacts + passkey-unlock.

La migrazione del rebrand

Rinominare il database da webcli-react avrebbe orfanizzato ogni wallet esistente, poiché
IndexedDB limita i dati per nome del database. migrateLegacyDatabase copia tutti gli store in avanti al
primo avvio. È:

  • idempotente — saltata una volta che la destinazione contiene un wallet
  • non distruttiva — il database legacy resta intatto per il rollback
  • non fatale — i fallimenti vengono registrati, mai lanciati; un bug di migrazione non deve bloccare l'avvio

Ricorda che clearIndexedDB negli helper E2E deve eliminare entrambi i database, altrimenti
la migrazione ricopia subito i dati legacy e lo "stato pulito" non è pulito.

Wallet SDK

src/sdk/ è il provider rivolto alle dApp; src/connect/ è il popup di approvazione servito su
/connect.

Ciclo di vita della connessione

Handshake (una volta per sessione):

  1. La dApp chiama provider.connect() → PopupTransport apre /connect?v=1&rid=…&origin=…
  2. Il wallet renderizza ConnectApp; l'utente sblocca se necessario
  3. Il wallet invia hello + MessagePort via window.postMessage, con validazione dell'origine
  4. La dApp risponde con challenge sul port (anti-replay)
  5. ConnectHandler verifica l'ack, serve l'RPC CONNECT → restituisce indirizzo, account e rete

Dopo la connessione:

  • Il popup può chiudersi, ma il MessagePort resta aperto — è indipendente dalla finestra
  • La sessione persiste in IndexedDB (sdk-sessions) con TTL di inattività e assoluto
  • I metodi di lettura (getBalance, getAccounts) sono silenziosi per la sessione
  • I metodi di firma aprono sempre un nuovo prompt di approvazione

La soluzione al sintomo «la connessione funziona, ma nient'altro funziona»:

In origine PopupTransport.isConnected() controllava popup.closed, quindi ogni chiamata dopo
la chiusura della finestra di approvazione falliva con "Transport is not connected". Ora controlla
solo il port, che sopravvive al popup. Il wallet chiude il popup dopo l'approvazione, ma la
connessione resta viva.

Modello dei permessi

Al momento della connessione: solo scope di sola lettura (viewAccounts, viewBalance,
viewNetwork).

Gli scope di firma (signMessage, signContract, ecc.) sono concessi lazy al primo
successo di approvazione. Prima del fix erano assenti da DEFAULT_PERMISSIONS e il dispatcher
rifiutava ogni chiamata di firma con UNAUTHORIZED prima che il prompt potesse apparire —
la seconda causa principale del sintomo.

Ora:

  • Il controllo dei permessi consente agli scope di firma non concessi di procedere al prompt di approvazione
  • All'approvazione, grantPermission persiste lo scope nella sessione
  • Le chiamate successive saltano il controllo dei permessi ma richiedono comunque l'approvazione — concedere uno scope registra solo che l'utente accetta che la dApp possa chiedere

La revoca è esplicita: revokePermission rimuove lo scope da permissions e lo registra
in deniedPermissions, che il dispatcher rifiuta del tutto.

Invarianti di sicurezza

Non indebolire questi punti:

  • Validazione dell'origine su ogni postMessage in ingresso (PopupTransport.ts, rpc-handler.ts)
  • Anti-replay: challenge CSPRNG + nonce della dApp + nonce monotono per sessione. makeId è
    solo per la correlazione dei messaggi e non deve mai essere usato come valore di sicurezza
  • Permessi per origine, persistiti in sdk-sessions e concessi o revocati esplicitamente
  • Indipendenza del MessagePort: il port sopravvive al popup. Una volta trasferito, il wallet può
    chiudere la finestra di approvazione senza spezzare la connessione
  • Metodi proibiti rifiutati sia lato client (WalletProvider) sia lato wallet
    (rpc-handler), così l'esecuzione di transazioni non può mai sfuggire all'SDK nemmeno tramite
    l'escape hatch request() di basso livello
  • localStorage contiene solo un indizio per il ripristino della sessione (indirizzo, rete) — mai segreti

Integrazione con le dApp

Avvio rapido

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

Gestione della sessione

Le sessioni di Orion scadono dopo 30 minuti di inattività o 8 ore assolute. L'SDK fornisce
controlli di salute della sessione integrati e la riconnessione automatica:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

Reti, incluse quelle personali dell'utente

Un utente può aggiungere la propria rete in Settings → Network (il proprio nodo, un fork di devnet, un
RPC a pagamento). Quelle reti sono di prima classe: compaiono nel selettore del popup di connessione
accanto alle preimpostazioni e una dApp connessa può vederle.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

Rileva la funzionalità tramite la capability customNetworks prima di fare affidamento su una
qualsiasi di queste cose — le build più vecchie del wallet rispondono solo al nudo
wallet_getNetwork, che restituisce una stringa id.

NetworkInfo non porta volutamente né rpcUrl né relayerUrl. Una rete aggiunta
dall'utente è spesso un endpoint privato — un indirizzo LAN, un tunnel, un URL di provider con la chiave
API nella query string — e consegnarlo a ogni sito a cui l'utente si connette farebbe trapelare la sua
infrastruttura. Una dApp non ne ha bisogno: ogni lettura passa attraverso il wallet
(wallet_getBalance e simili) e l'esecuzione non lascia mai la UI del wallet. Ciò che attraversa
il filo è ciò di cui una dApp ha legittimamente bisogno — a quale rete sta parlando, se il proprietario
l'ha aggiunta a mano (custom) e dove collegare una transazione (explorerUrl).

Non esiste wallet_switchNetwork. Il cambio resta nella UI del wallet — il selettore del popup
o la pillola di rete della finestra principale — in coerenza con la regola che i cambi di stato non
originano mai da una dApp. Una dApp che ha bisogno di un'altra rete chiede all'utente di cambiare, poi
attende networkChanged.

networkChanged viene emesso da entrambi i punti in cui può avvenire il cambio: il popup di
connessione e la finestra principale. Le sessioni vengono passate alla finestra principale quando il popup
si chiude, quindi quando la maggior parte degli utenti tocca la pillola di rete il popup è ormai sparito —
Layout.tsx emette verso gli handler adottati, così una dApp connessa non resta a mostrare una rete
obsoleta.

Due classi indipendenti implementano WalletHost — src/connect/host.ts (finestra principale) e un
host inline in src/connect/ConnectApp.tsx (popup). Qualunque cosa aggiunta all'interfaccia va
implementata in entrambe, oltre che nel fixture in tests/unit/connect-handler.test.ts.

Metodi proibiti

L'SDK blocca questi metodi localmente prima che raggiungano il transport. Il wallet li
ricontrolla anche lato server, così l'esecuzione di transazioni non può mai sfuggire:

  • wallet_sendTransaction / sendTransaction
  • wallet_broadcastTransaction / broadcastTransaction
  • wallet_transfer / transfer
  • wallet_swap / swap
  • wallet_bridge / bridge

Gestione della sessione

Le sessioni di Orion Wallet sono gestite automaticamente dall'SDK. Le sessioni scadono dopo:

  • Timeout di inattività: 30 minuti di inattività
  • Timeout assoluto: 8 ore dalla connessione

La dApp può controllare la salute della sessione in qualsiasi momento:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

Quando una sessione scade, il wallet emette un evento sessionExpired. La dApp dovrebbe
ascoltare questo evento e chiedere all'utente di riconnettersi:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

Il ripristino della sessione è gestito automaticamente — il wallet conserva l'indizio della sessione in
IndexedDB, quindi riconnettersi dopo la scadenza non richiede all'utente di reimportare il wallet.

Test

npm test                 # 676 unit tests, 56 files
npm run test:coverage    # V8 coverage, 60% threshold
npm run test:e2e         # 7 Playwright specs (needs npm run build first)
npm run autofix          # typecheck → format → lint --fix → test → build
npm run check            # same, read-only (CI)

I test unitari girano sotto jsdom con fake-indexeddb. I test dei componenti usano
renderToStaticMarkup invece di una libreria di test del DOM — vedi
tests/unit/processing-modal.test.tsx.

WebAuthn non ha un'implementazione jsdom, quindi tests/unit/passkey.test.ts installa un
FakeAuthenticator che modella l'estensione PRF (incluso un authenticator che ne è privo,
un prompt ignorato e un segreto ruotato). Asserisce ciò che il record archiviato non deve
contenere, che è la proprietà che conta davvero.

Nota E2E: prima di credere a un muro di fallimenti di Playwright, controlla la macchina, non la diff.
Due limiti ambientali producono fallimenti che sembrano esattamente regressioni reali:

  • Spazio temporaneo. Chromium mette ogni profilo del browser sotto TMPDIR (/tmp di default). Se
    quel filesystem è pieno — facile quando /tmp è una piccola tmpfs condivisa con altri processi —
    i context muoiono all'avvio e test non correlati falliscono in millisecondi, o restano appesi al timeout
    di 30 s. Prima df -h /tmp; rilancia con TMPDIR=$HOME/.cache/e2e-tmp su un filesystem
    capiente e le stesse spec passano dal timeout al successo in ~4 s.
  • Memoria. Circa 2 GB di memoria libera per worker. Quando finisce, Chromium viene ucciso
    a metà test e Playwright riporta Target crashed; rilancia con --workers=1.

playwright.config.ts imposta reuseExistingServer: !isCI, quindi un npm run preview
rimasto sulla porta 4173 viene riusato silenziosamente — incluso uno avviato da un checkout diverso.
Quando confronti due alberi, uccidi il listener tra le esecuzioni (ss -lptn | grep 4173) o la seconda
esecuzione testerà la build del primo.

Quando sistemi un bug, aggiungi un test che documenta la modalità di fallimento, non solo il fix.
tests/unit/history-view.test.ts e error-boundary.test.tsx seguono questa regola: ognuno nomina
il sintomo che impedisce di ripresentarsi.

Checklist di rilascio

  1. npm run autofix — deve essere completamente verde
  2. npm run test:e2e contro una npm run build fresca
  3. npm audit --omit=dev — la produzione deve riportare zero vulnerabilità
  4. Verifica che PVAC si carichi in una preview di produzione (npm run preview), non solo in dev
  5. Testa il percorso di migrazione da una build pre-rebrand con dati di wallet esistenti

Problemi noti

Avvisi sulle dependency di sviluppo. npm audit riporta vulnerabilità in vitest, vite, esbuild
e pacchetti correlati. Ogni fix rimanente richiede un aggiornamento major (vite 5→8, vitest 2→4).
Sono solo strumenti di build e non arrivano agli utenti; le audit di produzione sono pulite. Vedi
SECURITY.html.

Avviso di chunking di storage.ts. La build avverte che storage.ts è importato sia
staticamente sia dinamicamente, quindi non può essere diviso in un proprio chunk. Innocuo, ma significa
che le importazioni dinamiche in HistoryView e WalletExportImport non offrono alcun
beneficio di code-splitting.

Prestazioni dell'AES software. Il fallback AES in WASM è 5–10× più lento del nativo. Le operazioni
PVAC pesanti bloccano il thread principale; spostarle in un Web Worker è il prossimo passo logico.
