GitHub: github.com/maragung/OrionWallet — โค้ดต้นฉบับ ประเด็นปัญหา และเวอร์ชันเผยแพร่
รายงานช่องโหว่: GitHub Security Advisories

สถานะการตรวจสอบ

Orion Wallet ยังไม่ผ่านการตรวจสอบความปลอดภัยโดยบุคคลที่สามที่เป็นอิสระ

การออกแบบเชิงการเข้ารหัสเป็นไปตามการ implement ต้นฉบับ octra-labs/webcli และ
พรีมิทีฟมาจากไลบรารีที่ผ่านการตรวจสอบอย่างดี แต่การผสานรวมเองยังไม่ถูกตรวจสอบ
โปรดชั่งน้ำหนักสิ่งนั้นก่อนจัดเก็บมูลค่าจำนวนมาก

การรายงานช่องโหว่

อย่าเปิด issue สาธารณะสำหรับปัญหาด้านความปลอดภัย

จงรายงานเป็นการส่วนตัวถึงผู้ดูแล โดยรวมถึง:

  • คำอธิบายของปัญหาและผลกระทบของมัน
  • ขั้นตอนในการจำลองปัญหา
  • เวอร์ชันหรือ commit ที่ได้รับผลกระทบ
  • แนวทางแก้ไขที่แนะนำ (ถ้ามี)

โปรดให้เวลาที่สมเหตุสมผลสำหรับการแก้ไขก่อนการเปิดเผยต่อสาธารณะ การรายงานเป็นที่ยินดี
และจะได้รับการให้เครดิต เว้นแต่คุณต้องการให้เป็นอย่างอื่น

โมเดลภัยคุกคาม

สิ่งที่ Orion Wallet ป้องกัน

ภัยคุกคามมาตรการป้องกัน
คีย์รั่วไปยังเซิร์ฟเวอร์ไม่มีแบ็กเอนด์ คีย์ไม่เคยออกจากเบราว์เซอร์
การขโมยคีย์สโตร์ขณะอยู่นิ่งAES-256-GCM, คีย์ที่สร้างจาก PIN ผ่าน PBKDF2
คำขอจาก dApp ที่เป็นอันตรายสิทธิ์ต่อ origin พร้อมพร้อมท์ขออนุมัติที่ชัดเจน
การปลอมแปลงข้อความข้าม originorigin ถูกตรวจสอบบนข้อความขาเข้าทุกครั้ง
การเล่นซ้ำข้อความchallenge จาก CSPRNG และ nonce ต่อเซสชัน
XSS ผ่านมาร์กอัปที่ถูกฉีดไม่มี innerHTML / dangerouslySetInnerHTML; CSP จำกัดแหล่งที่มา
ข้อมูล RPC ที่ผิดรูปแบบทำให้แอปพังการทำข้อมูลให้เป็นปกติเชิงรับบวกกับ error boundaries
วลีกู้คืนที่ไม่เคยถูกเขียนเก็บจริงการสร้างถูกคุมด้วยการพิมพ์คำสุ่ม 3 คำซ้ำ
การเซ็นจากบัญชีที่ไม่มีคีย์assertCanSign ปฏิเสธที่ขอบเขต API ไม่ใช่แค่ใน UI
การดักฟังการจราจร RPC อย่างเงียบ ๆเอนด์พอยต์ plaintext ต้องมีการยินยอมต่อ origin อย่างชัดเจน

สิ่งที่มันไม่สามารถป้องกันได้

จงชัดเจนกับตัวเองเกี่ยวกับสิ่งเหล่านี้:

  • อุปกรณ์ที่ถูกบุกรุก. มัลแวร์, คีย์ล็อกเกอร์ หรือส่วนขยายเบราว์เซอร์ที่ไม่เป็นมิตรสามารถอ่าน PIN ขณะที่คุณพิมพ์และดึงคีย์ที่ถูกถอดรหัสจากหน่วยความจำได้
  • วลีกู้คืนที่หายไป. ไม่มีกลไกกู้คืน ไม่มีใครสามารถคืนมันได้
  • ฟิชชิง. หากคุณป้อนวลีกู้คืนบนไซต์ปลอม เงินจะหายไป Orion Wallet ไม่เคยขอวลีของคุณหลังการตั้งค่า
  • โหนด RPC ที่ถูกบุกรุก. โหนดที่ไม่ประสงค์ดีสามารถเสิร์ฟยอดคงเหลือเท็จหรือระงับธุรกรรมได้ มันไม่สามารถปลอมลายเซ็นหรือขโมยคีย์ได้
  • การถูกบุกรุกในซัพพลายเชน ของ dependency npm หรือผู้ให้บริการโฮสติ้ง
  • การเข้าถึงทางกายภาพ ต่ออุปกรณ์ที่ปลดล็อกอยู่พร้อมกับ wallet ที่ปลดล็อกแล้ว

salt, nonce, จากนั้นเป็น ciphertext AES-GCM พร้อมแท็กตรวจสอบความถูกต้อง

การจัดการ PIN

PIN ไม่ถูกจัดเก็บถาวร ในรูปแบบใด ๆ มันใช้สร้างคีย์ถอดรหัสตอนปลดล็อก
แล้วก็ถูกทิ้ง ไม่มี "จดจำ PIN ของฉัน" — โดยการออกแบบ ดังนั้น PIN ที่ลืม
จึงแก้ได้ด้วยการกู้คืนจากวลีกู้คืนเท่านั้น

เซสชันการปลดล็อก

PIN ไม่ถูกจัดเก็บถาวร แต่ผลลัพธ์ของการปลดล็อกถูกเก็บไว้ ตราบที่เซสชันยังคงอยู่:
การรีเฟรชหน้าต้องไม่โยนผู้ใช้กลับไปที่หน้าจอ PIN src/wallet/unlock-session.ts
ผนึก wallet ที่ถูกถอดรหัสด้วย AES-256-GCM แล้วแบ่งมันข้ามสอง store:

ส่วนที่ไหนอายุการใช้งาน
Ciphertext (orion:unlock-session)sessionStorageหนึ่งแท็บ หายไปเมื่อแท็บนั้นปิด
Sealing keyIndexedDB unlock-session-keys, เป็น CryptoKey แบบ non-extractableถูกลบเมื่อล็อก; ลูกกำพร้าถูกตัดทิ้งตามอายุ

ไม่มีครึ่งใดใช้ได้ตามลำพัง IndexedDB อยู่รอดเมื่อแท็บปิดแต่ไม่มี ciphertext;
sessionStorage ถือ ciphertext แต่ไม่มีคีย์ และแท็บที่สองหรือ origin อื่นไม่สามารถอ่าน
มันได้ คีย์ถูกสร้างด้วย extractable: false ดังนั้น origin นี้จึงสามารถใช้มันได้ แต่
ไบต์ของมันไม่สามารถถูกอ่านออกมา — ไม่ใช่โดยโค้ดของเราเอง และไม่ใช่โดยอะไรก็ตามที่
รันได้ในหน้าเพจ เซสชันหมุนเวียน (คีย์ใหม่, nonce ใหม่) ทุกครั้งที่กู้คืน และพา createdAt
ไปข้างหน้า เพื่อให้การรีเฟรชไม่สามารถขยายเพดานแบบสัมบูรณ์ได้

การหมดอายุ: ไม่มีการใช้งาน 30 นาที (ปรับได้, autoLockMinutes; 0 ปิดมัน) และ
เพดานแบบสัมบูรณ์ 8 ชั่วโมง นับจากการปลดล็อกครั้งแรก ทั้งสองถูกบังคับใช้ตอนกู้คืน
และช่วงไม่มีการใช้งานยังถูกบังคับใช้แบบเรียลไทม์โดย useAutoLock ดังนั้นแท็บที่ปล่อย
ค้างไว้จะล็อกตัวเอง

สิ่งที่มันไม่ได้ป้องกัน — ส่วนที่ตรงไปตรงมา:

  • การรันสคริปต์ในแท็บ. โค้ดที่รันในหน้าเพจระหว่างเซสชันที่ยังมีชีวิตอยู่สามารถขอให้
    เบราว์เซอร์ถอดรหัสเซสชันแล้วเซ็นด้วยคีย์ เหมือนกับที่ wallet ทำเป๊ะ มันไม่สามารถ
    ลักลอบส่งคีย์ผนึกออกไปได้ ดังนั้นการถูกบุกรุกจบลงที่แท็บ; มันไม่กลายเป็นคีย์ที่ถูกขโมย
    ซึ่งใช้ที่อื่นได้
  • อุปกรณ์ที่ถูกบุกรุก. ไม่เปลี่ยนจากโมเดลภัยคุกคามข้างต้น: มัลแวร์ในเครื่องสามารถอ่าน
    IndexedDB และ sessionStorage ร่วมกันได้
  • คอนเทกซ์ที่ไม่ปลอดภัย. หากไม่มี crypto.subtle (plain http:// ดูด้านล่าง) คีย์ผนึก
    จะถอยไปเป็นไบต์ดิบใน IndexedDB และการรับประกันแบบไม่สามารถแยกออกได้ก็สูญเสียไป
    การแบ่งและการหมดอายุยังคงมีผล

เพื่อเลือกไม่ใช้ทั้งหมด ให้ปิด Settings → Security → Stay unlocked after a page refresh
(keepUnlocked: false) จะไม่มีอะไรถูกเขียน และทุกการโหลดซ้ำจะถาม PIN — พฤติกรรม
ก่อนที่ฟีเจอร์นี้จะเกิดขึ้น การล็อกอย่างชัดแจ้ง (🔒) ทำลายทั้งสองครึ่งทันที

การปลดล็อกด้วย passkey

เป็นทางเลือก, ปิดโดยค่าเริ่มต้น และเป็นแบบเพิ่มเติม: มันเป็นวิธีที่สองในการเปิด wallet ที่มีอยู่
ไม่ใช่สิ่งแทนที่ PIN src/wallet/passkey.ts

การลงทะเบียนสร้าง platform credential ด้วย userVerification: 'required' และ
ส่วนขยาย WebAuthn PRF PRF ให้หน้าเพจได้ secret ที่สร้างจาก credential และ
salt 32 ไบต์ที่ถูกเก็บไว้ ซึ่งเบราว์เซอร์จะผลิตออกมาเมื่อผู้ใช้ยืนยันตัวตนแล้วเท่านั้น
wallet ใช้ sha256("orion-passkey-unlock-v1" || prf) เป็นคีย์ AES-256, ผนึก
wallet ที่ถูก serialise ด้วย AES-256-GCM, ปรับคีย์ให้เป็นศูนย์ และเก็บ blob ที่ผนึกแล้ว
ใน IndexedDB ข้าง credential ID และ salt

ถูกเก็บไม่ถูกเก็บ
Credential ID, PRF salt, IV, ciphertext ของ walletเอาต์พุต PRF, คีย์ที่ถูกสร้าง, PIN, วัสดุคีย์ plaintext ใด ๆ

ผลที่ตามมาซึ่งควรกล่าวไว้อย่างตรงไปตรงมา:

  • PRF เป็นสิ่งที่จำเป็น ไม่มีการลดระดับเด็ดขาด. หาก authenticator ไม่รองรับมัน
    การลงทะเบียนจะ throw และไม่เก็บอะไรเลย ทางเลือกอื่น — การเก็บคีย์ที่อ่านได้
    ไว้ข้าง ciphertext — จะทำให้เรคคอร์ดถอดรหัสตัวเองได้ ซึ่งแย่กว่าการไม่เสนอฟีเจอร์นี้
  • เรคคอร์ดเฉย ๆ ไม่มีประโยชน์. หากปราศจากท่าทางยืนยันตัวตนที่สำเร็จบน
    authenticator นั้น ก็ไม่มีทางสร้างคีย์จากสิ่งที่อยู่บนดิสก์ได้
  • มันผนึก wallet ไม่ใช่ PIN. PIN ยังคงเป็นสิ่งเดียวที่ส่งออกคีย์, เปิดเผยวลี,
    เปลี่ยน PIN หรือสร้างบัญชี ดังนั้นการปลดล็อกด้วย passkey จึงไม่สามารถยกระดับไปถึงสิ่งเหล่านั้นได้
    และเรคคอร์ดที่ถูกเก็บก็รั่วไหลน้อยกว่า PIN ที่ถูกเก็บไว้อย่างเคร่งครัด
  • โมเดลเซสชันเดียวกันกับการปลดล็อกด้วย PIN. การปลดล็อกด้วย passkey ให้เซสชันการปลดล็อก
    เดียวกันกับเพดานแบบไม่มีการใช้งานและแบบสัมบูรณ์เดียวกัน; มันไม่ได้ขยายอย่างใดอย่างหนึ่ง
  • จำกัดอยู่ที่อุปกรณ์และเบราว์เซอร์. ผูกกับ rpId ของ origin และถูกเก็บในเครื่อง มัน
    ไม่ใช่ส่วนหนึ่งของการส่งออก wallet และไม่ได้สร้างจากวลีกู้คืน
  • credential ที่เก่าค้างจะล้มแบบปิด (fail closed). หากการถอดรหัสล้มเหลว — credential ที่ถูกหมุน
    หรือลงทะเบียนใหม่, อุปกรณ์ที่ถูกกู้คืน — เรคคอร์ดจะถูกลบและต้องใช้ PIN
    ท่าทางที่ถูกปิดหรือหมดเวลาโดยเจตนาจะไม่ลบมัน ดังนั้นพร้อมท์ที่ถูกยกเลิก
    จึงไม่สามารถปิดฟีเจอร์อย่างเงียบ ๆ ได้
  • ถูกปฏิเสธสำหรับบัญชี watch-only. ไม่มีวัสดุคีย์ที่จะผนึก

สิ่งที่มันไม่ป้องกันไม่เปลี่ยน: อุปกรณ์ที่ถูกบุกรุก และการรันสคริปต์ในเซสชันที่ยังมีชีวิตอยู่
เหมือนกับเซสชันการปลดล็อกข้างต้นเป๊ะ มันลดการเปิดเผยจริงอย่างหนึ่ง —
การที่ PIN ถูกพิมพ์และถูกจับตามองทุกครั้งที่ปลดล็อก

บัญชี watch-only

บัญชีสามารถถูกเพิ่มด้วยที่อยู่เพียงอย่างเดียว โดยไม่มีคีย์สโตร์ หลักไม่แปรเปลี่ยนคือบัญชี
แบบนั้นไม่สามารถเซ็นได้เด็ดขาด และมันถูกบังคับใช้ตรงที่การเซ็นเกิดขึ้น ไม่ใช่ใน UI:
assertCanSign (src/wallet/watch-only.ts) ถูกเรียกโดยเส้นทาง send, encrypt, stealth,
contract และ dApp-request และ throw โดยระบุทั้งการกระทำและวิธีแก้

มันล้มแบบปิดโดยโครงสร้าง: การตรวจปฏิเสธ wallet ใดก็ตามที่คีย์ลับไม่ใช่
คีย์ Ed25519 เต็ม 64 ไบต์ ดังนั้นคีย์ที่ถูกตัดทอนหรือหายไปจะถูกปฏิเสธแม้แฟล็ก watchOnly
จะหายไปด้วยเหตุใดก็ตาม แฟล็กถูกพาตลอดผ่าน serializeWallet/deserializeWallet
ดังนั้น wallet ที่ถูกกู้คืนจากเซสชันการปลดล็อกจึงยังเป็น watch-only

ความสุ่ม

ค่าที่เกี่ยวข้องกับความปลอดภัยทั้งหมดใช้ crypto.getRandomValues ผ่าน src/crypto/random.ts

makeId ใน src/sdk/protocol.ts มี fallback เป็น Math.random มันถูกใช้เฉพาะสำหรับ
ID การจับคู่ข้อความ ไม่เคยใช้สำหรับค่าด้านความปลอดภัย และถูกทำหมายเหตุไว้เช่นนั้น
อย่านำมันกลับมาใช้สำหรับ challenges, nonces, คีย์ หรือ salts

สามรายการสมควรได้รับคำอธิบาย:

  • 'wasm-unsafe-eval' จำเป็นสำหรับโมดูล PVAC FHE Chromium บล็อก
    WebAssembly.instantiate() หากไม่มีมัน มันอนุญาตการคอมไพล์ WebAssembly เท่านั้น — มันไม่
    เปิดใช้ JavaScript eval() อีกครั้ง
  • 'unsafe-inline' สำหรับสไตล์ จำเป็นสำหรับ CSS วิกฤตก่อนการเพนต์ที่หลีกเลี่ยง
    การกะพริบของเนื้อหาที่ยังไม่แต่งสไตล์ มันใช้กับสไตล์เท่านั้น ไม่เคยใช้กับสคริปต์
  • Loopback ใน connect-src ทำให้โหนดที่รันในเครื่องถูกใช้ได้โดยไม่ขยายนโยบาย
    เป็น plaintext โดยทั่วไป การจราจรไปยัง localhost / 127.0.0.0/8 / [::1] ไม่เคยออกจาก
    เครื่อง ดังนั้นจึงไม่มีอะไรบนสายให้ดักจับ

เอนด์พอยต์ RPC แบบ plaintext (http)

สิ่งอื่นใดผ่าน http:// ธรรมดาจะถูกปฏิเสธโดยค่าเริ่มต้น และ src/wallet/endpoint-policy.ts
คือที่เดียวที่ตัดสินใจ มันเป็นฟังก์ชันล้วนของ URL บวกกับบริบทที่ชัดเจน
ดังนั้น store, UI การตั้งค่า และการทดสอบจะไม่ขัดแย้งกันเรื่องสิ่งที่อนุญาต

ตัวบล็อกอิสระสามตัวมีผล และคำวินิจฉัยจะระบุตัวที่พื้นฐานที่สุดก่อน เพื่อไม่ให้
ผู้ใช้ถูกบอกให้แก้รายการอนุญาตในขณะที่ mixed content เป็นต้นเหตุจริง:

ตัวบล็อกใครบังคับใช้วิธีปลดล็อก
Mixed contentเบราว์เซอร์, อย่างไม่มีเงื่อนไขปลดไม่ได้ ใช้ TLS หรือพร็อกซี
Content-Security-Policymeta-tag CSP ที่มาพร้อมกับตัวสินค้าบิลด์ใหม่ด้วย VITE_ALLOW_HTTP_ENDPOINTS=1
การยินยอมของผู้ใช้allowedInsecureOrigins ในการตั้งค่าTrust origin ใน Settings → Network

หมายเหตุเกี่ยวกับการออกแบบ:

  • CSP เป็น meta tag ดังนั้นมันไม่สามารถขยายตอนรันไทม์ได้ — ไม่มีการตั้งค่าใดให้สิทธิ์นี้ได้
    ซึ่งคือเหตุผลที่มันเป็นบิลด์แฟล็ก VITE_ALLOW_HTTP_ENDPOINTS=1 ต่อท้าย http: เข้ากับ
    connect-src ตอนบิลด์เท่านั้น ไม่มีอะไรอื่น; การยินยอมของผู้ใช้ยังคงจำเป็นเพิ่มเติม
  • การยินยอมเป็นแบบต่อ origin — scheme, host และพอร์ต มันไม่ใช่การจับคู่ชื่อโฮสต์
    และไม่ใช่คำนำหน้า URL ดังนั้นการ trust http://node.lan:8080 จึงไม่ trust พอร์ตอื่น
    บนโฮสต์นั้น และ http://127.0.0.1.evil.com ไม่ถูกถือเป็น loopback
  • URL ของ explorer ได้รับการยกเว้น เพราะมันเป็นเพียงการนำทางแบบ <a href> ไม่ใช่การ fetch
    connect-src และ mixed content ไม่มีผลกับมัน relayerUrl ถูกเก็บแต่ไม่เคยถูก fetch
    มีเพียง rpcUrl เท่านั้นที่อยู่ภายใต้นโยบายนี้
  • เอนด์พอยต์ที่ถูกบล็อกยังคงสร้าง RpcClient ขึ้นมาโดยเจตนา: การปฏิเสธไม่สร้างมัน
    จะทำให้ผู้ใช้ไม่สามารถไปถึง Settings เพื่อแก้ไขได้ เหตุผลกลับถูกแสดงเป็น
    ป้าย ⚠️ Insecure RPC ในเฮดเดอร์ และเป็น RpcClient.unreachableHint ซึ่งถูกต่อท้าย
    กับ TypeError ที่ถูก throw เท่านั้น — ไม่เคยต่อท้ายกับข้อผิดพลาดเซิร์ฟเวอร์จริงหรือ timeout
    ซึ่งจะทำให้เข้าใจผิด
  • rpcProxyUrl ย้ายการตัดสินใจไปที่พร็อกซี: เอนด์พอยต์ถูกตัดสินด้วย scheme ของพร็อกซีเอง
    เพราะนั่นคือสิ่งที่เบราว์เซอร์เชื่อมต่อจริง พร็อกซีเห็นทุกคำขอ ดังนั้น UI จึงบอกให้รันพร็อกซี
    ของคุณเอง มันไม่สามารถเข้าถึงคีย์หรือเซ็นได้

RPC แบบ plaintext คือการเปิดเผยทั้งการรักษาความลับและความถูกต้อง — โหนดบนเส้นทางสามารถอ่าน
ทุกการค้นหาและแก้ไขคำตอบ — แต่ไม่ใช่การเปิดเผยที่ทำให้คีย์ถูกบุกรุก: ลายเซ็นถูกสร้าง
ในเครื่อง และ wallet ไม่ตรวจสอบสิ่งที่มันได้รับให้กลายเป็นวัสดุคีย์

การแยกข้าม origin

COOP/COEP เป็น same-origin / require-corp ทั้งแอป โดยมีค่า override แบบ unsafe-none
บน /connect เพื่อให้ป็อปอัปขออนุมัติสามารถแลกเปลี่ยน MessagePort กับ opener ได้
การจำกัดขอบเขตนี้เป็นไปโดยเจตนาและจำกัดอยู่ที่เส้นทางเดียวเท่านั้น

ความปลอดภัยการเชื่อมต่อ dApp

เมื่อไซต์ขอการเชื่อมต่อ:

  1. ป็อปอัปแสดง origin ที่ร้องขออย่างเด่นชัด
  2. ผู้ใช้ต้องอนุมัติอย่างชัดเจน; ไม่มีการเชื่อมต่อเงียบสำหรับ origin ใหม่
  3. การอนุมัติจำกัดขอบเขตอยู่ที่ origin นั้นและถูกจัดเก็บแบบต่อ origin
  4. การเซ็นทุกครั้งต้องมีการยืนยันเสมอ แม้แต่ไซต์ที่ trust แล้ว

"Trust this site" ระงับพร้อมท์สำหรับคำขอแบบอ่านอย่างเดียว (ยอดคงเหลือ, บัญชี,
เครือข่าย) เท่านั้น มันไม่เคยให้สิทธิ์การเซ็นแบบเงียบ

การเชื่อมต่อสามารถถูกตรวจสอบและเพิกถอนได้ภายใต้ Settings → Connected Sites

สิ่งที่ dApp เรียนรู้เกี่ยวกับเครือข่ายที่กำหนดเอง

เครือข่ายที่ผู้ใช้เพิ่มด้วยมือปรากฏให้ไซต์ที่เชื่อมต่อเห็น (wallet_getNetworkInfo,
wallet_getNetworks และอีเวนต์ networkChanged) เพราะ dApp ไม่สามารถเรนเดอร์ลิงก์ explorer
หรือป้ายเชนที่ถูกต้องได้โดยไม่รู้ว่ามันอยู่บนเครือข่ายไหน เรคคอร์ดที่ข้ามสายไป
เป็นเซ็ตย่อยโดยเจตนา:

ถูกส่งถูกยับยั้ง
id, name, explorerUrl, icon, customrpcUrl, relayerUrl

เอนด์พอยต์ถูกยับยั้งเพราะเครือข่ายที่ผู้ใช้เพิ่มมักเป็นเครือข่ายส่วนตัว — ที่อยู่ LAN,
อุโมงค์, URL ผู้ให้บริการแบบเสียเงินที่มีคีย์ API ใน query string การเชื่อมต่อกับ
ไซต์ไม่ควรเปิดเผยว่าโหนดของผู้ใช้อาศัยอยู่ที่ใดหรือส่งมอบ URL ที่มีข้อมูลประจำตัว
ไม่มีฟังก์ชันใดสูญเสีย: การอ่านถูกพร็อกซีผ่าน wallet และธุรกรรมถูกสร้างและ
กระจายเสียงโดย wallet ดังนั้น dApp จึงไม่ต้องไปถึง RPC ด้วยตัวเอง

ผลที่ตามมาสองอย่างที่น่ารู้:

  • ชื่อของเครือข่ายที่กำหนดเองเป็นสิ่งที่ผู้ใช้เลือกและถูกแสดงให้ dApp เห็น การตั้งชื่อตาม
    ตัวบ่งชี้ส่วนบุคคลจะเปิดเผยตัวบ่งชี้นั้นให้ทุกไซต์ที่คุณเชื่อมต่อ
  • wallet_getNetworks เปิดเผยว่าคุณตั้งค่าเครือข่ายไว้จำนวนเท่าใด นี่คือ
    พื้นผิวการพิมพ์ลายนิ้วมือเล็ก ๆ ซึ่งถูกยอมรับเพื่อให้ dApp เสนอคำแนะนำ "สลับไป X" ได้

ไม่มี dApp ใดเปลี่ยนเครือข่ายได้ ไม่มีเมธอด wallet_switchNetwork; การสลับเกิดขึ้น
ใน UI ของ wallet เองเท่านั้น และ dApp จะรู้ทีหลังผ่าน networkChanged

สถานะ dependency

dependency โปรดักชัน: ช่องโหว่ที่รู้จักเป็นศูนย์ (npm audit --omit=dev)

dependency สำหรับการพัฒนามีคำเตือนใน vitest, vite, esbuild และแพ็กเกจที่เกี่ยวข้อง
การแก้ที่เหลือแต่ละรายการต้องอัปเกรดครั้งใหญ่ (vite 5→8, vitest 2→4) ซึ่งเสี่ยงทำให้
บิลด์พัง แพ็กเกจเหล่านี้เป็นเครื่องมือบิลด์ — มันไม่ถูกส่งถึงผู้ใช้และไม่สามารถส่งผลต่อ
wallet ที่ถูกติดตั้งใช้งาน

นี่คือการแลกเปลี่ยนโดยเจตนา ซึ่งถูกทบทวนทุกครั้งที่เผยแพร่ รัน npm audit --omit=dev เพื่อ
ยืนยันว่าพื้นผิวที่ส่งออกยังสะอาด

คำแนะนำสำหรับผู้ใช้

ควรทำ

  • เก็บวลีกู้คืนของคุณแบบออฟไลน์ บนกระดาษ ในมากกว่าหนึ่งสถานที่
  • ตรวจสอบที่อยู่ผู้รับทีละตัวอักษรก่อนส่ง
  • ตรวจสอบ origin ในพร้อมท์การเชื่อมต่อ dApp ทุกครั้ง
  • ส่งจำนวนเงินทดสอบเล็กน้อยก่อนเมื่อใช้ที่อยู่ใหม่
  • อัปเดตเบราว์เซอร์และระบบปฏิบัติการของคุณอยู่เสมอ

ไม่ควรทำเด็ดขาด

  • ป้อนวลีกู้คืนบนเว็บไซต์ใด ๆ หลังการตั้งค่า
  • เก็บวลีแบบดิจิทัล — ไม่มีการแคปหน้าจอ, โน้ตคลาวด์ หรือข้อความแชท
  • แชร์คีย์ส่วนตัวหรือไฟล์สำรอง .oct ของคุณ
  • ใช้ wallet ที่ถือเงินจริงบนคอมพิวเตอร์ที่ใช้ร่วมกันหรือไม่น่าเชื่อถือ

สำหรับผู้มีส่วนร่วม

หลักไม่แปรเปลี่ยนที่อ่อนไหวด้านความปลอดภัยซึ่งต้องไม่ถูกทำให้อ่อนแอลง:

  • การตรวจสอบ origin บน postMessage ขาเข้าทุกครั้ง
  • CSPRNG สำหรับค่าด้านความปลอดภัยทั้งหมด; makeId ไม่ใช่หนึ่งในนั้น
  • ไม่มีความลับใน localStorage, sessionStorage, ล็อก หรือข้อความผิดพลาด
  • ไม่มี innerHTML หรือ dangerouslySetInnerHTML
  • PIN ไม่ถูกจัดเก็บถาวรเด็ดขาด
  • การปลดล็อกด้วย passkey ต้องใช้ PRF; ไม่ถอยไปเก็บคีย์ที่อ่านได้เด็ดขาด
  • assertCanSign เฝ้าทุกเส้นทางการเซ็น — บัญชี watch-only ต้องไม่เซ็นเด็ดขาด
  • นโยบายเอนด์พอยต์ plaintext ยังคงอยู่ใน endpoint-policy.ts; ไม่มีการตรวจ URL แบบเฉพาะกิจที่อื่น
  • Canonical JSON ยังคงตรงแบบไบต์ต่อไบต์ — ลายเซ็นขึ้นอยู่กับมัน

การเปลี่ยนแปลงใด ๆ ที่แตะการเข้ารหัส, การจัดการคีย์, การจัดเก็บ หรือโฟลว์การเชื่อมต่อ ควรบอก
