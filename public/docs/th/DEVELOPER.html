การติดตั้ง

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps เป็นสิ่งที่จำเป็น: ESLint 9 และ @eslint/js 10 ประกาศช่วง peer dependencies ที่ขัดแย้งกัน
vercel.json ใช้แฟล็กเดียวกัน ดังนั้น CI และการติดตั้งในเครื่องจึงตรงกัน

แนะนำให้ใช้ Node 20+

ระบบบิลด์

ไฟล์คอนฟิก TypeScript คือแหล่งความจริงเพียงแหล่งเดียว:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
อย่าเพิ่มไฟล์ .js คู่กันสำหรับไฟล์เหล่านี้ Vite แก้ vite.config.js ก่อน
vite.config.ts ดังนั้นสำเนาที่ถูกแปลงแล้วซึ่งเก่าค้างจะแอบบดบังคอนฟิกจริง และการแก้ไข
ไฟล์ .ts จะไม่มีผล ไฟล์สามชื่อนั้นอยู่ใน .gitignore
eslint.config.js เป็น flat config จริงและถูกเก็บไว้โดยเจตนา

การละเว้นพวกมันเพียงอย่างเดียวไม่พอ เพราะไม่มีอะไรหยุดยั้งไม่ให้มันถูกสร้างขึ้นมา:
tsconfig.node.json เป็นโปรเจกต์แบบ composite ซึ่งบังคับให้มีการ emit declaration และเมื่อไม่มี
outDir tsc -b ใด ๆ จะเขียน vite.config.js ไว้ข้าง ๆ โค้ดต้นฉบับเลย เกิดแล้วสองครั้ง
ตอนนี้ emit สำหรับโปรเจกต์นั้นไปที่ node_modules/.tmp/tsconfig-node/ ซึ่งไม่สามารถบดบัง
อะไรได้ หากคุณเพิ่มไฟล์คอนฟิกในโปรเจกต์นั้น อย่าแตะ outDir

แฟล็กสภาพแวดล้อม

แฟล็กผลลัพธ์
VITE_ALLOW_HTTP_ENDPOINTS=1ต่อท้าย http: เข้ากับไดเรกทีฟ CSP connect-src ตอนบิลด์ เพื่อให้บิลด์ที่โฮสต์เองสามารถเข้าถึงโหนด RPC แบบ plain-http ได้ การยินยอมของผู้ใช้ต่อ origin ยังคงมีผล — ดู src/wallet/endpoint-policy.ts

ตั้งค่าได้ตอนบิลด์เท่านั้น มันถูกอ่านใน vite.config.ts โดยปลั๊กอิน allowHttpEndpointsCsp
และเขียน index.html ใหม่ มันไม่มีผลตอนรัน เพราะ meta-tag CSP ไม่สามารถขยายได้
เมื่อเอกสารถูกแยกวิเคราะห์แล้ว

COOP/COEP ถูกตั้งเป็น same-origin / require-corp (สงวนไว้สำหรับการทำ threading ของ WASM ในอนาคต)
โดยมีค่า override แบบ unsafe-none บน /connect เพื่อให้การส่ง postMessage + MessagePort
ของป็อปอัปทำงานได้ ส่วนหัวสำหรับ dev อยู่ใน vite.config.ts; ส่วนหัวสำหรับโปรดักชันอยู่ใน vercel.json
จงทำให้ทั้งสองตรงกัน

Content-Security-Policy

นิยามใน index.html script-src ต้องรวม 'wasm-unsafe-eval' — Chromium ปฏิเสธ
WebAssembly.instantiate() หากไม่มีมัน ซึ่งนั่นคือสิ่งที่ทำให้โมดูล PVAC โหลดไม่สำเร็จอย่างเงียบ ๆ
ไดเรกทีฟนี้อนุญาตการคอมไพล์ WebAssembly เท่านั้น มันไม่ได้เปิดใช้
JavaScript eval() อีกครั้ง

connect-src คือ 'self' https: บวกกับ loopback (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*) เพื่อให้โหนดที่รันในเครื่องทำงานได้โดยไม่ต้องเปิด plaintext โดยทั่วไป
สิ่งอื่นใดผ่าน http:// จะถูกคุมโดย src/wallet/endpoint-policy.ts ซึ่งเป็นที่เดียวที่ตัดสินใจ
— เป็นฟังก์ชันล้วนของ URL บวกกับบริบทที่ชัดเจน ดังนั้น store, UI การตั้งค่า
และการทดสอบจะไม่ขัดแย้งกันได้ อย่าเพิ่มการตรวจ URL แบบเฉพาะกิจที่อื่น
ตัวบล็อกอิสระสามตัวมีผล (mixed content → CSP → การยินยอมของผู้ใช้) และคำวินิจฉัยจะรายงาน
ตัวที่พื้นฐานที่สุดก่อน เพื่อไม่ให้ผู้ใช้ถูกบอกให้แก้รายการอนุญาตในขณะที่ตัวเบราว์เซอร์
เป็นฝ่ายปฏิเสธ

ไปป์ไลน์ PVAC WASM

การบิลด์

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

ต้องใช้ patch-pvac-aes.py เพราะ PVAC hard-#error เมื่อไม่มีฮาร์ดแวร์ AES (AES-NI หรือ
ARM crypto extensions) ซึ่ง WebAssembly ไม่มีให้ แพตช์นี้เพิ่มการใช้งานซอฟต์แวร์แบบพกพา
ที่ให้ผลลัพธ์บิตเหมือนเดิมแต่ช้ากว่าประมาณ 5–10 เท่า มันเป็นแบบเพิ่มเติมไม่ทำลาย: เส้นทางฮาร์ดแวร์
ไม่ถูกแตะต้อง และมีการเขียนไฟล์สำรอง .hpp.bak ไว้

การโหลด

src/pvac/wasm-bridge.ts โหลดโมดูลในสามขั้นตอน:

  1. Probe — ส่ง HEAD ไปที่ URL ของ glue เพื่อให้กรณี "ยังไม่บิลด์" (404) แยกออกจาก
    กรณี "ถูกบล็อกโดย CSP" ได้ หากไม่มีขั้นตอนนี้ ทั้งสองกรณีจะปรากฏเป็นความล้มเหลวการนำเข้า
    แบบทึบแสงที่เหมือนกัน
  2. Import — import() แบบไดนามิกของ URL แบบสัมบูรณ์พร้อม /* @vite-ignore */
    มันต้องเป็นแบบสัมบูรณ์: สเปกซ์แบบ bare จะ resolve ไม่ได้ และ ./wasm/pvac.js จะ resolve
    เทียบกับ /assets/ แล้วเจอ 404
  3. Verify — ยืนยันว่า export _pvac_* ที่จำเป็นทั้ง 13 ตัวมีอยู่จริงก่อนสลับ bridge
    เข้ามา บิลด์ก่อนหน้าเคยละเว้นฟังก์ชัน serialization ซึ่งทำให้ encrypt/decrypt พังในแบบ
    ที่โหนดรายงานเพียงว่า "ธุรกรรมไม่ถูกต้อง" (malformed transaction)

ความล้มเหลวถูกจำแนกเป็น PvacFailureReason: not-built, csp-blocked,
missing-exports, init-failed, unknown แต่ละค่าจับคู่กับวิธีแก้ที่เป็นรูปธรรมซึ่งแสดง
ใน Settings singleton promise จะถูกรีเซ็ตเมื่อเกิดความล้มเหลว เพื่อให้ ↻ Reload PVAC
ลองใหม่ได้ แทนที่จะเล่นการปฏิเสธที่แคชไว้ซ้ำ

กฎการจัดการหน่วยความจำ

C API เป็นการจัดการหน่วยความจำด้วยมือ ทุก _malloc ต้องมี _free คู่กัน; ทุก serialize_*
คืนบัฟเฟอร์ที่ต้องปลดปล่อยด้วย _pvac_free_bytes แฮนเดิลจาก keygen/enc_* ต้องใช้
_pvac_free_* ที่ตรงกัน ใช้ try/finally — ดู WasmPvacBridge สำหรับรูปแบบดังกล่าว

การจัดการสถานะ

Zustand ใน src/store/wallet-store.ts มันเป็นเจ้าของ wallet, ไคลเอ็นต์ RPC, การตั้งค่า, สถานะ PVAC,
toasts และแฟล็กการโหลดระดับโลก

แฟล็กการโหลดระดับโลก (isLoading) ขับเคลื่อนโอเวอร์เลย์เบลอเต็มหน้าจอและสงวนไว้สำหรับ
การเปลี่ยนสถานะทั้งแอปเท่านั้น เช่น การปลดล็อก wallet งานระดับแพเนลต้องใช้
usePanelLoading แทน — ดูด้านล่าง

การจัดการข้อผิดพลาด

src/components/ErrorBoundary.tsx ห่อหุ้มทุกแพเนลใน Layout.tsx โดยใช้แท็บที่ใช้งานอยู่เป็นคีย์
เพื่อให้ boundary ที่ถูกชนะรีเซ็ตเมื่อนำทาง พร้อมกับ boundary อีกหนึ่งตัวที่ root ใน main.tsx

เรื่องนี้สำคัญมากกว่าที่เห็น index.html มี:

#root:empty::before { content: 'Loading Orion Wallet…'; }

หากไม่มี boundary การ throw ใด ๆ ตอนเรนเดอร์จะทำให้ React 18 ถอนการติดตั้งทั้งทรี #root
กลายเป็นว่างเปล่า และ fallback นั้นก็ถูกเรนเดอร์ — ทำให้เกิดหน้าเปล่าสีขาวที่ดูเหมือนค้าง
โหลดตลอดไป boundary จะทำให้โครงร่างยังมีชีวิตอยู่และแสดงการ์ดข้อผิดพลาดที่ลองใหม่ได้

ผลที่ตามมา: ฟังก์ชันที่ถูกเรียกระหว่างเรนเดอร์ต้องไม่ throw เมื่อรับอินพุตที่ผิดรูปแบบ
formatAmount ใน src/tx/builder.ts รับ unknown และลดระดับเป็นตัววางตำแหน่ง
เพราะทั้งการตอบสนองของ RPC และแคชธุรกรรมในเครื่องต่างก็ไม่ได้ตรวจสอบ schema
จงทำข้อมูลแถวที่ไม่น่าเชื่อถือให้เป็นปกติก่อนเรนเดอร์ — HistoryView แสดงรูปแบบนี้

สถานะการโหลด

ใช้ usePanelLoading (src/hooks/usePanelLoading.ts) สำหรับงานที่จำกัดขอบเขตแค่แพเนล:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

จากนั้นเรนเดอร์ <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />

คุณสมบัติสองอย่างที่สำคัญ: โมดัลเป็นแบบปิดได้ (งานยังดำเนินต่อในเบื้องหลัง
ดังนั้นเครือข่ายช้าจึงไม่ทำให้ผู้ใช้ติดกับ) และการเขียนสถานะถูกคุมด้วย isMounted()
เพื่อให้การนำทางออกกลางคันไม่ทำให้โมดัลค้างอยู่บนหน้าจอ

การจัดเก็บข้อมูลและการย้ายฐานข้อมูล

IndexedDB ผ่าน idb, ฐานข้อมูล orion-wallet, เวอร์ชัน 6 store ถูกประกาศครั้งเดียวใน
อาร์เรย์ OBJECT_STORES ใน src/wallet/storage.ts; เพิ่ม store ใหม่ที่นั่นเพื่อให้การสร้างและ
การย้ายฐานข้อมูลสอดคล้องกัน — อาร์เรย์นั้นยังขับเคลื่อน wipeEverything() ด้วย ดังนั้น store
ที่เพิ่มที่อื่นจะรอดจากการล้างทั้งหมด

การย้ายฐานข้อมูลเป็นแบบเพิ่มเติมเท่านั้น: เพิ่ม DB_VERSION, ต่อท้ายอาร์เรย์ และจด
เวอร์ชันไว้ในคอมเมนต์ข้างรายการใหม่ store ที่มีอยู่จะไม่ถูกเปลี่ยนชื่อหรือทิ้ง
เวอร์ชันจนถึงตอนนี้: v2 SDK stores, v3 โทเคน OCS01, v4 บุ๊กมาร์ก oct://, v5
unlock-session-keys, v6 contacts + passkey-unlock

การย้ายฐานข้อมูลหลังรีแบรนด์

การเปลี่ยนชื่อฐานข้อมูลจาก webcli-react จะทำให้ wallet ที่มีอยู่ทุกตัวกลายเป็นลูกกำพร้า
เพราะ IndexedDB กำหนดขอบเขตข้อมูลด้วยชื่อฐานข้อมูล migrateLegacyDatabase จะคัดลอก
ทุก store ไปข้างหน้าเมื่อเปิดครั้งแรก มันมีคุณสมบัติ:

  • idempotent — จะถูกข้ามเมื่อฐานข้อมูลเป้าหมายมี wallet ใด ๆ แล้ว
  • non-destructive — ฐานข้อมูลเดิมถูกปล่อยไว้ครบถ้วนเพื่อการย้อนกลับ
  • non-fatal — ความล้มเหลวถูกบันทึกล็อกเท่านั้น ไม่ถูก throw; บั๊กในการย้ายฐานข้อมูลต้องไม่บล็อกการเริ่มระบบ

จำไว้ว่า clearIndexedDB ในตัวช่วย E2E ต้องลบทั้งสองฐานข้อมูล ไม่เช่นนั้น
การย้ายฐานข้อมูลจะคัดลอกข้อมูลเดิมกลับมาตรง ๆ และ "สถานะสะอาด" ก็จะไม่สะอาด

ทั้งสองแบบถูกรับและทำงานเหมือนกัน ชื่อ orion_wallet_* มีไว้สำหรับ dApp ที่

วงจรชีวิตการเชื่อมต่อ

Handshake (ครั้งเดียวต่อเซสชัน):

  1. dApp เรียก provider.connect() → PopupTransport เปิด /connect?v=1&rid=…&origin=…
  2. Wallet เรนเดอร์ ConnectApp, ผู้ใช้ปลดล็อกหากจำเป็น
  3. Wallet ส่ง hello + MessagePort ผ่าน window.postMessage, ตรวจสอบ origin แล้ว
  4. dApp สะท้อน challenge กลับผ่านพอร์ต (กันการเล่นซ้ำ)
  5. ConnectHandler ตรวจสอบ ack, ให้บริการ RPC CONNECT → คืนที่อยู่, บัญชี, เครือข่าย

หลังเชื่อมต่อ:

  • ป็อปอัปอาจปิดได้ แต่ MessagePort ยังเปิดอยู่ — มันเป็นอิสระจากหน้าต่าง
  • เซสชันคงอยู่ใน IndexedDB (sdk-sessions) พร้อม TTL แบบ idle + แบบสัมบูรณ์
  • เมธอดอ่าน (getBalance, getAccounts) ทำงานเงียบต่อเซสชัน
  • เมธอดเซ็นจะเปิดพร้อมท์ขออนุมัติใหม่ทุกครั้ง

วิธีแก้กรณี "เชื่อมต่อได้ แต่สิ่งอื่นไม่ทำงาน":

เดิม PopupTransport.isConnected() ตรวจสอบ popup.closed ดังนั้นทุกการเรียกหลัง
หน้าต่างขออนุมัติปิดจึงล้มเหลวด้วย "Transport is not connected" ตอนนี้มันตรวจสอบแค่
พอร์ต ซึ่งอยู่ยืนยาวกว่าป็อปอัป wallet ปิดป็อปอัปหลังการอนุมัติ แต่การเชื่อมต่อยังมีชีวิตอยู่

โมเดลสิทธิ์

ตอนเชื่อมต่อ: มีเพียงสโคปอ่านอย่างเดียว (viewAccounts, viewBalance, viewNetwork)

สโคปการเซ็น (signMessage, signContract, ฯลฯ) จะถูกให้แบบขี้เกียจ ในการอนุมัติ
ที่สำเร็จครั้งแรก ก่อนการแก้ไข พวกมันไม่อยู่ใน DEFAULT_PERMISSIONS และ
dispatcher จะปฏิเสธทุกการเรียกเซ็นด้วย UNAUTHORIZED ก่อนที่พร้อมท์จะแสดงขึ้นมา —
ซึ่งเป็นต้นเหตุรากที่สองของอาการนี้

ตอนนี้:

  • การตรวจสิทธิ์อนุญาตให้สโคปการเซ็นที่ยังไม่ได้รับหลุดไปถึงพร้อมท์ขออนุมัติได้
  • เมื่ออนุมัติ grantPermission จะบันทึกสโคปไว้ในเซสชัน
  • การเรียกครั้งต่อ ๆ ไปข้ามการตรวจสิทธิ์แต่ยังต้องมีการอนุมัติ — การให้สโคปเพียงแต่บันทึกว่าผู้ใช้ยอมให้ dApp สอบถามได้เท่านั้น

การเพิกถอนเป็นแบบชัดเจน: revokePermission เอาสโคปออกจาก permissions และบันทึก
มันใน deniedPermissions ซึ่ง dispatcher ปฏิเสธทันที

หลักไม่แปรเปลี่ยนด้านความปลอดภัย

อย่าทำให้สิ่งเหล่านี้อ่อนแอลง:

  • การตรวจสอบ origin บน postMessage ขาเข้าทุกครั้ง (PopupTransport.ts, rpc-handler.ts)
  • กันการเล่นซ้ำ: challenge จาก CSPRNG + nonce ของ dApp + nonce แบบ monotonic ต่อเซสชัน makeId มีไว้สำหรับการจับคู่ข้อความเท่านั้นและต้องไม่ถูกใช้เป็นค่าด้านความปลอดภัยเด็ดขาด
  • สิทธิ์ เป็นแบบต่อ origin, ถูกบันทึกใน sdk-sessions, และให้/เพิกถอนอย่างชัดเจน
  • ความเป็นอิสระของ MessagePort: พอร์ตอยู่ยืนยาวกว่าป็อปอัป เมื่อโอนแล้ว wallet สามารถปิดหน้าต่างขออนุมัติได้โดยไม่ทำลายการเชื่อมต่อ
  • เมธอดที่ถูกห้าม ถูกปฏิเสธทั้งฝั่งไคลเอ็นต์ (WalletProvider) และฝั่ง wallet
    (rpc-handler) ดังนั้นการทำงานของธุรกรรมจึงไม่มีทางหลุดไปถึง SDK ได้แม้จะผ่าน
    ช่องทางหนี request() ระดับต่ำก็ตาม
  • localStorage เก็บเพียงคำใบ้กู้คืนเซสชัน (ที่อยู่, เครือข่าย) — ไม่เก็บความลับเด็ดขาด

การผสานรวม dApp

เริ่มต้นอย่างรวดเร็ว

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

การจัดการเซสชัน

เซสชัน Orion หมดอายุหลังจากไม่มีการใช้งาน 30 นาที หรือ8 ชั่วโมงแบบสัมบูรณ์ SDK มี
การตรวจสุขภาพเซสชันในตัวและการเชื่อมต่อใหม่อัตโนมัติ:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

เครือข่าย รวมถึงเครือข่ายของผู้ใช้เอง

ผู้ใช้สามารถเพิ่มเครือข่ายของตัวเองได้ใน Settings → Network (โหนดของตัวเอง, devnet fork,
RPC แบบเสียเงิน) เครือข่ายเหล่านั้นเป็นพลเมืองชั้นหนึ่ง: มันปรากฏในตัวเลือกของป็อปอัปเชื่อมต่อ
เคียงข้างค่าที่ตั้งไว้ และ dApp ที่เชื่อมต่ออยู่สามารถเห็นมันได้

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

จงตรวจสอบความสามารถ customNetworks แบบ feature-detect ก่อนพึ่งพามัน — บิลด์
wallet ที่เก่ากว่าจะตอบเพียง wallet_getNetwork เปล่า ๆ ซึ่งคืนสตริง id

NetworkInfo จงใจไม่นำ rpcUrl และ relayerUrl ติดไปด้วย เครือข่ายที่ผู้ใช้เพิ่ม
มักเป็นเอนด์พอยต์ส่วนตัว — ที่อยู่ LAN, อุโมงค์, URL ของผู้ให้บริการที่มีคีย์ API อยู่ใน
query string — และการส่งต่อให้ทุกไซต์ที่ผู้ใช้เชื่อมต่อจะทำให้โครงสร้างพื้นฐานของเขารั่วไหล
dApp ไม่จำเป็นต้องใช้มัน: ทุกการอ่านผ่าน wallet
(wallet_getBalance และพวกพ้อง) และการทำงานไม่เคยออกจาก UI ของ wallet สิ่งที่ข้าม
สายไปคือสิ่งที่ dApp ต้องการโดยชอบด้วยกฎหมาย — ว่ามันกำลังคุยกับเครือข่ายไหน, เจ้าของ
เพิ่มมันด้วยมือหรือไม่ (custom), และจะลิงก์ธุรกรรมไปที่ใด (explorerUrl)

ไม่มี wallet_switchNetwork การสลับยังคงอยู่ใน UI ของ wallet เอง — ตัวเลือก
ของป็อปอัปหรือ network pill ของหน้าต่างหลัก — สอดคล้องกับกฎที่ว่าการเปลี่ยนสถานะ
ไม่เคยเกิดขึ้นจากฝั่ง dApp dApp ที่ต้องการเครือข่ายอื่นจะขอให้ผู้ใช้สลับ แล้ว
รอ networkChanged

networkChanged ถูกส่งออกจากทั้งสองจุดที่การสลับเกิดขึ้นได้: ป็อปอัปเชื่อมต่อและ
หน้าต่างหลัก เซสชันถูกส่งต่อให้หน้าต่างหลักเมื่อป็อปอัปปิด ดังนั้นเมื่อผู้ใช้ส่วนใหญ่
แตะ network pill ป็อปอัปก็หายไปนานแล้ว — Layout.tsx ส่งอีเวนต์ไปยัง
แฮนเดิลที่รับช่วง เพื่อไม่ให้ dApp ที่เชื่อมต่ออยู่แสดงเครือข่ายที่เก่าค้าง

คลาสอิสระสองคลาส implement WalletHost — src/connect/host.ts (หน้าต่างหลัก) และ
host แบบอินไลน์ใน src/connect/ConnectApp.tsx (ป็อปอัป) สิ่งใดก็ตามที่เพิ่มเข้าไปในอินเทอร์เฟซ
ต้องถูก implement ในทั้งสองแห่ง รวมถึง fixture ใน tests/unit/connect-handler.test.ts

เมธอดที่ถูกห้าม

SDK บล็อกเมธอดเหล่านี้ในเครื่องก่อนที่มันจะถึง transport wallet ยัง
ตรวจซ้ำฝั่งเซิร์ฟเวอร์ ดังนั้นการทำงานของธุรกรรมจึงไม่มีทางหลุดรอดไปได้:

  • wallet_sendTransaction / sendTransaction
  • wallet_broadcastTransaction / broadcastTransaction
  • wallet_transfer / transfer
  • wallet_swap / swap
  • wallet_bridge / bridge

การจัดการเซสชัน

เซสชัน Orion Wallet ถูกจัดการโดยอัตโนมัติโดย SDK เซสชันหมดอายุหลังจาก:

  • หมดอายุเมื่อไม่มีการใช้งาน: ไม่มีการใช้งาน 30 นาที
  • หมดอายุแบบสัมบูรณ์: 8 ชั่วโมงนับจากการเชื่อมต่อ

dApp สามารถตรวจสุขภาพเซสชันได้ทุกเมื่อ:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

เมื่อเซสชันหมดอายุ wallet จะส่งอีเวนต์ sessionExpired dApp ควร
ฟังอีเวนต์นี้และแจ้งให้ผู้ใช้เชื่อมต่อใหม่:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

การกู้คืนเซสชันถูกจัดการโดยอัตโนมัติ — wallet เก็บคำใบ้เซสชันไว้ใน
IndexedDB ดังนั้นการเชื่อมต่อใหม่หลังหมดอายุจึงไม่ต้องให้ผู้ใช้ import wallet ซ้ำ

  1. npm run autofix — ต้องเป็นสีเขียวทั้งหมด
  2. npm run test:e2e กับ npm run build ที่ใหม่สด
  3. npm audit --omit=dev — โปรดักชันต้องรายงานช่องโหว่เป็นศูนย์
  4. ตรวจว่า PVAC โหลดใน preview โปรดักชัน (npm run preview) ไม่ใช่แค่ใน dev
  5. ทดสอบเส้นทางการย้ายฐานข้อมูลจากบิลด์ก่อนรีแบรนด์ที่มีข้อมูล wallet เดิม
  6. ยืนยันว่าเซิร์ฟเวอร์เฮดเดอร์ของ vite.config.ts ยังตรงกับ vercel.json
