Configuration

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps est obligatoire : ESLint 9 et @eslint/js 10 déclarent des plages de pairs
conflictuelles. vercel.json utilise le même drapeau, donc la CI et les installations locales correspondent.

Node 20 ou plus est recommandé.

Architecture

100 % côté client ; il n'y a pas de backend. Les données circulent dans un seul sens :

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

Contraintes de conception

Le JSON canonique doit être exact au niveau de l'octet. src/tx/canonical-json.ts reproduit
exactement l'ordre des clés et le formatage de nlohmann::json. Les signatures sont calculées sur ces
octets, donc tout écart produit une signature que le réseau rejette. Ne « nettoyez » pas ce sérialiseur.

Nommage : produit contre protocole. « Orion Wallet » est le produit. Les méthodes RPC octra_*,
le préfixe d'adresse oct, le symbole OCT et « Octra Network » sont des identifiants de protocole
et ne doivent jamais être renommés.

Système de compilation

Les fichiers de configuration TypeScript sont la source unique de vérité :

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
N'ajoutez pas de jumeaux .js pour ceux-ci. Vite résout vite.config.js avant
vite.config.ts, si bien qu'une copie transpilée obsolète masque silencieusement la vraie configuration et que les
modifications du fichier .ts ne font rien. Ces trois noms de fichiers sont dans .gitignore.
eslint.config.js est une véritable configuration plate (flat config) et est conservé intentionnellement.

Les ignorer ne suffisait pas en soi, car rien n'empêchait qu'ils soient créés :
tsconfig.node.json est un projet composite, ce qui force l'émission de déclarations, et sans
outDir, tout tsc -b écrivait vite.config.js juste à côté de la source. Cela s'est produit deux fois.
L'émission pour ce projet va désormais dans node_modules/.tmp/tsconfig-node/, où elle ne peut rien masquer.
Si vous ajoutez un fichier de configuration à ce projet, ne touchez pas au outDir.

En-têtes

COOP/COEP sont définis à same-origin / require-corp (réservés pour le futur multithreading WASM),
avec des dérogations unsafe-none sur /connect pour que le transfert postMessage + MessagePort
de la fenêtre fonctionne. Les en-têtes de développement vivent dans vite.config.ts ; les en-têtes de production
dans vercel.json. Gardez les deux synchronisés.

Content-Security-Policy

Définie dans index.html. script-src doit inclure 'wasm-unsafe-eval' — Chromium refuse
WebAssembly.instantiate() sans lui, ce qui est précisément ce qui faisait échouer silencieusement le chargement du module PVAC.
Cette directive n'autorise que la compilation WebAssembly ; elle ne réactive pas eval() JavaScript.

connect-src est 'self' https: plus la boucle locale (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*) pour qu'un nœud exécuté localement fonctionne sans ouvrir le texte en clair en général. Tout le reste
en http:// est contrôlé par src/wallet/endpoint-policy.ts, qui est le seul endroit qui décide — une fonction
pure de l'URL plus un contexte explicite, si bien que le store, l'interface des paramètres et les tests ne peuvent pas être
en désaccord. N'ajoutez pas de vérifications d'URL ad hoc ailleurs. Trois bloqueurs indépendants s'appliquent (contenu mixte
→ CSP → consentement de l'utilisateur) et le verdict signale le plus fondamental d'abord, afin que l'utilisateur ne soit
jamais invité à corriger la liste blanche alors que c'est le navigateur qui refuse.

Le pipeline WASM PVAC

Compilation

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py est requis car PVAC fait un #error en dur sans AES matériel (AES-NI ou
extensions crypto ARM), ce que WebAssembly n'offre pas. Le correctif ajoute une implémentation logicielle portable,
identique au niveau de l'octet mais environ 5 à 10 fois plus lente. Il est additif : les chemins matériels sont
intacts, et un fichier de sauvegarde .hpp.bak est écrit.

Chargement

src/pvac/wasm-bridge.ts charge le module en trois étapes :

  1. Probe — HEAD sur l'URL du glue, pour distinguer « non compilé » (404) de
    « bloqué par la CSP ». Sans cela, les deux se présentent comme un échec d'importation opaque identique.
  2. Import — import() dynamique d'une URL absolue avec /* @vite-ignore */. Elle doit être
    absolue : un spécificateur nu ne se résout pas, et ./wasm/pvac.js se résout par rapport à
    /assets/ et renvoie une 404.
  3. Verify — vérifie que les 13 exports _pvac_* requis existent avant de remplacer le pont.
    Les versions antérieures omettaient les fonctions de sérialisation, ce qui cassait le chiffrement/déchiffrement d'une manière
    que le nœud ne signalait que comme « malformed transaction ».

Les échecs sont classés comme PvacFailureReason : not-built, csp-blocked,
missing-exports, init-failed, unknown. Chacun correspond à un remède concret affiché dans
les paramètres. La promesse singleton est réinitialisée en cas d'échec pour que ↻ Reload PVAC puisse
réessayer plutôt que de rejouer un rejet mis en cache.

Règles de mémoire

L'API C est à mémoire manuelle. Chaque _malloc a besoin d'un _free ; chaque serialize_* renvoie un
tampon qui doit être libéré avec _pvac_free_bytes. Les poignées de keygen/enc_* nécessitent leur
_pvac_free_* correspondant. Utilisez try/finally — voir WasmPvacBridge pour le modèle.

Gestion d'état

Zustand, dans src/store/wallet-store.ts. Il possède le portefeuille, le client RPC, les paramètres, l'état
PVAC, les toasts et le drapeau de chargement global.

Le drapeau de chargement global (isLoading) pilote un voile de flou plein écran et est réservé
uniquement aux transitions de toute l'application, comme le déverrouillage du portefeuille. Le travail par panneau
doit utiliser usePanelLoading à la place — voir plus bas.

Gestion des erreurs

src/components/ErrorBoundary.tsx enveloppe chaque panneau dans Layout.tsx, indexé par l'onglet actif
pour qu'une borne déclenchée se réinitialise à la navigation, plus une borne à la racine dans main.tsx.

C'est plus important qu'il n'y paraît. index.html contient :

#root:empty::before { content: 'Loading Orion Wallet…'; }

Sans borne, toute erreur d'émission fait démonter tout l'arbre par React 18, #root
devient vide et ce repli s'affiche — produisant une page blanche qui semble bloquée au chargement pour toujours.
La borne maintient le shell en vie et affiche une carte d'erreur réessayable.

Conséquence : les fonctions appelées pendant l'émission ne doivent pas lever d'exception sur une entrée malformée.
formatAmount dans src/tx/builder.ts accepte unknown et dégrade vers un espace réservé,
car ni les réponses RPC ni le cache de transactions local ne sont validés par schéma. Normalisez les lignes non fiables
avant de les afficher — HistoryView montre le modèle.

États de chargement

Utilisez usePanelLoading (src/hooks/usePanelLoading.ts) pour le travail limité à un panneau :

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

Affichez ensuite <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />.

Deux propriétés comptent : la fenêtre est fermable (le travail continue en arrière-plan, si bien
qu'un réseau lent ne piège jamais l'utilisateur), et les écritures d'état sont conditionnées par isMounted() pour
qu'une navigation en plein vol ne puisse pas laisser une fenêtre bloquée à l'écran.

Stockage et migrations

IndexedDB via idb, base de données orion-wallet, version 6. Les magasins sont déclarés une seule fois dans le
tableau OBJECT_STORES dans src/wallet/storage.ts ; ajoutez-y les nouveaux pour que la création et la migration
restent cohérentes — ce tableau pilote aussi wipeEverything(), donc un magasin ajouté ailleurs survivrait à un effacement.

Les migrations sont uniquement additives : incrémentez DB_VERSION, ajoutez au tableau et notez
la version dans un commentaire à côté des nouvelles entrées. Les magasins existants ne sont jamais renommés ni supprimés.
Les versions jusqu'ici : v2 magasins SDK, v3 jetons OCS01, v4 favoris oct://, v5
unlock-session-keys, v6 contacts + passkey-unlock.

La migration de changement de marque (rebrand)

Renommer la base de données de webcli-react aurait orpheliné tous les portefeuilles existants, car
IndexedDB limite les données par nom de base de données. migrateLegacyDatabase copie tous les magasins au
premier lancement. Il est :

  • idempotent — ignoré une fois que la cible contient un portefeuille
  • non destructif — la base de données héritée est laissée intacte pour un retour en arrière
  • non fatal — les échecs sont journalisés, jamais levés ; un bug de migration ne doit pas bloquer le démarrage

Rappelez-vous que clearIndexedDB dans les utilitaires E2E doit supprimer les deux bases de données,
sinon la migration recopie directement les données héritées et « l'état propre » n'est pas propre.

SDK du portefeuille

src/sdk/ est le fournisseur orienté dApps ; src/connect/ est la fenêtre d'approbation servie sur
/connect.

Cycle de vie de la connexion

Poignée de main (une fois par session) :

  1. La dApp appelle provider.connect() → PopupTransport ouvre /connect?v=1&rid=…&origin=…
  2. Le portefeuille affiche ConnectApp, l'utilisateur déverrouille si nécessaire
  3. Le portefeuille envoie hello + MessagePort via window.postMessage, origine validée
  4. La dApp renvoie challenge sur le port (anti-rejeu)
  5. ConnectHandler vérifie l'accusé de réception, sert le RPC CONNECT → renvoie l'adresse, les comptes, le réseau

Après la connexion :

  • La fenêtre peut se fermer, mais le MessagePort reste ouvert — il est indépendant de la fenêtre
  • La session persiste dans IndexedDB (sdk-sessions) avec une TTL d'inactivité et absolue
  • Les méthodes de lecture (getBalance, getAccounts) sont silencieuses pour la session
  • Les méthodes de signature ouvrent toujours une nouvelle invite d'approbation

Le correctif pour « la connexion fonctionne, rien d'autre » :

À l'origine, PopupTransport.isConnected() vérifiait popup.closed, donc chaque appel après la
fermeture de la fenêtre d'approbation échouait avec « Transport is not connected ». Désormais, il ne vérifie que le port,
qui survit à la fenêtre. Le portefeuille ferme la fenêtre après l'approbation, mais la connexion reste vivante.

Modèle d'autorisations

Au moment de la connexion : uniquement des portées en lecture seule (viewAccounts, viewBalance,
viewNetwork).

Les portées de signature (signMessage, signContract, etc.) sont accordées paresseusement
à la première approbation réussie. Avant le correctif, elles étaient absentes de DEFAULT_PERMISSIONS et le
répartiteur rejetait chaque appel de signature avec UNAUTHORIZED avant que l'invite puisse apparaître —
la seconde cause racine du symptôme.

Désormais :

  • La vérification d'autorisation laisse les portées de signature non accordées aller jusqu'à l'invite d'approbation
  • À l'approbation, grantPermission persiste la portée dans la session
  • Les appels suivants sautent la vérification d'autorisation mais exigent toujours une approbation — accorder une
    portée ne fait qu'enregistrer que l'utilisateur accepte que la dApp puisse demander

La révocation est explicite : revokePermission retire la portée de permissions et l'enregistre dans
deniedPermissions, que le répartiteur refuse d'emblée.

Invariants de sécurité

Ne les affaiblissez pas :

  • Validation de l'origine sur chaque postMessage entrant (PopupTransport.ts, rpc-handler.ts)
  • Anti-rejeu : défi CSPRNG + nonce de dApp + nonce monotone par session. makeId sert
    uniquement à la corrélation de messages et ne doit jamais être utilisé comme valeur de sécurité
  • Autorisations par origine, persistées dans sdk-sessions, accordées/révoquées explicitement
  • Indépendance du MessagePort : le port survit à la fenêtre. Une fois transféré, le portefeuille peut
    fermer la fenêtre d'approbation sans casser la connexion
  • Méthodes interdites rejetées à la fois côté client (WalletProvider) et côté portefeuille
    (rpc-handler), afin que l'exécution de transactions ne puisse jamais s'échapper vers le SDK, même via la
    trappe de sortie de bas niveau request()
  • localStorage ne contient qu'un indice de restauration de session (adresse, réseau) — jamais de secrets

Intégration dApp

Démarrage rapide

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

Gestion de session

Les sessions Orion expirent après 30 minutes d'inactivité ou 8 heures au maximum. Le SDK fournit
des contrôles d'état de session intégrés et une reconnexion automatique :

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

Réseaux, y compris les vôtres

Vous pouvez ajouter votre propre réseau dans Settings → Network (votre propre nœud, un fork de devnet, un
RPC payant). Ces réseaux sont de première classe : ils apparaissent dans le sélecteur de la fenêtre de connexion à côté des
préréglages, et une dApp connectée peut les voir.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

Détectez la capacité customNetworks avant de vous y fier — les anciennes versions du portefeuille ne
répondent qu'au simple wallet_getNetwork, qui renvoie une chaîne d'identifiant.

NetworkInfo ne comporte volontairement ni rpcUrl ni relayerUrl. Un réseau ajouté par
l'utilisateur est souvent un point d'accès privé — une adresse LAN, un tunnel, une URL de fournisseur avec la clé API dans la
chaîne de requête — et le transmettre à chaque site auquel vous vous connectez divulguerait votre infrastructure. Une dApp n'en a
pas besoin : chaque lecture passe par le portefeuille (wallet_getBalance et autres) et l'exécution ne quitte jamais
l'interface du portefeuille. Ce qui traverse la liaison est ce dont une dApp a légitimement besoin — à quel réseau elle parle, si
le propriétaire l'a ajouté à la main (custom), et où lier une transaction (explorerUrl).

Il n'existe pas de wallet_switchNetwork. Le changement reste dans l'interface du portefeuille lui-même —
le sélecteur de la fenêtre contextuelle ou la pastille de réseau de la fenêtre principale — conformément à la règle selon laquelle
les changements d'état ne proviennent jamais d'une dApp. Une dApp qui a besoin d'un autre réseau demande à l'utilisateur de
changer, puis attend networkChanged.

networkChanged est émis depuis les deux endroits où un changement peut se produire : la fenêtre de connexion
et la fenêtre principale. Les sessions sont transférées à la fenêtre principale lorsque la fenêtre contextuelle se ferme, si bien
qu'au moment où la plupart des utilisateurs touchent la pastille de réseau, la fenêtre contextuelle a disparu depuis longtemps —
Layout.tsx émet vers les gestionnaires adoptés afin qu'une dApp connectée ne reste pas avec un réseau obsolète.

Deux classes indépendantes implémentent WalletHost — src/connect/host.ts (fenêtre principale) et un hôte
en ligne dans src/connect/ConnectApp.tsx (fenêtre contextuelle). Tout ce qui est ajouté à l'interface doit être implémenté
dans les deux, plus la maquette dans tests/unit/connect-handler.test.ts.

Méthodes interdites

Le SDK bloque ces méthodes localement avant qu'elles n'atteignent le transport. Le portefeuille revérifie aussi
côté serveur, si bien que l'exécution de transactions ne peut jamais s'échapper :

  • wallet_sendTransaction / sendTransaction
  • wallet_broadcastTransaction / broadcastTransaction
  • wallet_transfer / transfer
  • wallet_swap / swap
  • wallet_bridge / bridge

Gestion de session

Les sessions d'Orion Wallet sont gérées automatiquement par le SDK. Les sessions expirent après :

  • Délai d'inactivité : 30 minutes sans activité
  • Délai absolu : 8 heures à partir de la connexion

La dApp peut vérifier l'état de la session à tout moment :

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

Lorsqu'une session expire, le portefeuille émet un événement sessionExpired. La dApp doit écouter cet événement
et inviter l'utilisateur à se reconnecter :

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

La restauration de session est automatique — le portefeuille conserve l'indice de session dans IndexedDB, si bien que se
reconnecter après expiration ne demande pas à l'utilisateur de réimporter son portefeuille.

Les tests unitaires s'exécutent sous jsdom avec fake-indexeddb. Les tests de composants utilisent
renderToStaticMarkup plutôt qu'une bibliothèque de test DOM — voir
tests/unit/processing-modal.test.tsx.

WebAuthn n'a pas d'implémentation jsdom, aussi tests/unit/passkey.test.ts installe un
FakeAuthenticator qui modélise l'extension PRF (y compris un authentificateur qui ne l'a pas, une invite
rejetée et une clé tournée). Il vérifie ce que l'enregistrement stocké ne doit pas contenir, ce qui est la propriété
qui compte réellement.

Note E2E : avant de croire un mur d'échecs Playwright, vérifiez la machine, pas la différence. Deux limites de
l'environnement produisent des échecs qui ressemblent exactement à de vraies régressions :

  • Espace temporaire. Chromium place chaque profil de navigateur sous TMPDIR (/tmp par
    défaut). Si ce système de fichiers est plein — facile quand /tmp est un petit tmpfs partagé avec d'autres
    processus — les contextes meurent au lancement et des tests sans rapport échouent en quelques millisecondes, ou se
    bloquent jusqu'au délai de 30 s. df -h /tmp d'abord ; relancez avec TMPDIR=$HOME/.cache/e2e-tmp
    sur un système de fichiers spacieux et les mêmes specs passent du dépassement de délai au succès en ~4 s.
  • Mémoire. Environ 2 Go de mémoire libre par worker. Quand elle s'épuise, Chromium est tué en plein test et
    Playwright signale Target crashed ; relancez avec --workers=1.

playwright.config.ts définit reuseExistingServer: !isCI, si bien qu'un npm run preview
resté actif sur le port 4173 est silencieusement réutilisé — y compris un lancé depuis un checkout différent.
Lorsque vous comparez deux arbres, tuez l'écouteur entre les exécutions (ss -lptn | grep 4173) sinon la deuxième
exécution teste la compilation de la première.

Quand vous corrigez un bug, ajoutez un test qui documente le mode de défaillance, pas seulement le correctif.
tests/unit/history-view.test.ts et error-boundary.test.tsx suivent ce principe : chacun nomme le
symptôme qu'il empêche de réapparaître.

Liste de contrôle de publication

  1. npm run autofix — doit être entièrement vert
  2. npm run test:e2e contre une npm run build fraîche
  3. npm audit --omit=dev — la production doit signaler zéro vulnérabilité
  4. Vérifiez que PVAC se charge dans un aperçu de production (npm run preview), pas seulement en dev
  5. Testez le chemin de migration depuis une compilation d'avant le changement de marque, avec des données de portefeuille existantes
  6. Confirmez que les en-têtes de serveur de vite.config.ts correspondent toujours à vercel.json

Problèmes connus

Avis sur les dépendances de développement. npm audit signale des vulnérabilités dans vitest, vite,
esbuild et les paquets associés. Chaque correctif restant exige une mise à niveau majeure (vite 5→8, vitest 2→4).
Ces paquets ne sont que de l'outillage de compilation, non livré aux utilisateurs ; les audits de production sont propres.
Voir SECURITY.html.

Avertissement de découpage de storage.ts. La compilation avertit que storage.ts est importé
à la fois statiquement et dynamiquement, si bien qu'il ne peut pas être découpé dans son propre morceau. Sans danger, mais
cela signifie que les imports dynamiques dans HistoryView et WalletExportImport n'apportent aucun bénéfice
de fractionnement de code.

Performances de l'AES logiciel. Le repli AES WASM est 5 à 10 fois plus lent que le natif. Les opérations PVAC
lourdes bloquent le thread principal ; les déplacer dans un Web Worker est la prochaine étape logique.
