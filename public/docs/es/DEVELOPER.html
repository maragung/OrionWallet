Configuración

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps es obligatorio: ESLint 9 y @eslint/js 10 declaran rangos de pares
en conflicto. vercel.json usa la misma opción, de modo que las instalaciones de CI y locales coinciden.

Se recomienda Node 20+.

Arquitectura

Totalmente del lado del cliente; no hay backend. Los datos fluyen en una sola dirección:

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

Restricciones de diseño

El JSON canónico debe ser exacto a nivel de bytes. src/tx/canonical-json.ts reproduce
exactamente el orden de claves y el formato de nlohmann::json. Las firmas se calculan sobre estos
bytes, de modo que cualquier desviación produce una firma que la red rechaza. No "ordene ni limpie" este
serializador.

Nomenclatura: producto frente a protocolo. "Orion Wallet" es el producto. Los métodos RPC octra_*,
el prefijo de dirección oct, el símbolo OCT y "Octra Network" son identificadores del protocolo
y nunca deben renombrarse.

Sistema de compilación

Los archivos de configuración de TypeScript son la única fuente de verdad:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
No añada equivalentes .js para estos. Vite resuelve vite.config.js antes que
vite.config.ts, de modo que una copia transpilada obsoleta oculta silenciosamente la configuración real y las ediciones
al archivo .ts no surten efecto. Esos tres nombres de archivo están en .gitignore.
eslint.config.js es configuración plana genuina y se conserva intencionadamente.

Ignorarlos no bastaba por sí solo, porque nada impedía que fueran creados:
tsconfig.node.json es un proyecto composite, lo que fuerza la emisión de declaraciones, y sin
ningún outDir cualquier tsc -b escribía vite.config.js justo al lado del código fuente. Ocurrió dos veces.
La emisión de ese proyecto ahora va a node_modules/.tmp/tsconfig-node/, donde no puede ocultar
nada. Si añade un archivo de configuración a ese proyecto, no toque el outDir.

Indicadores de entorno

IndicadorEfecto
VITE_ALLOW_HTTP_ENDPOINTS=1Añade http: a la directiva CSP connect-src en el momento de compilación, de modo que una compilación autoalojada pueda alcanzar un nodo RPC de http simple. El consentimiento del usuario por origen sigue aplicándose; consulte src/wallet/endpoint-policy.ts

Se establece solo en el momento de compilación. Lo lee el complemento allowHttpEndpointsCsp en vite.config.ts
y reescribe index.html; no tiene efecto en tiempo de ejecución, porque una CSP de metaetiqueta no se puede ampliar
una vez analizado el documento.

Cabeceras

COOP/COEP se establecen en same-origin / require-corp (reservado para el futuro uso de hilos en WASM),
con anulaciones unsafe-none en /connect para que funcionen el postMessage de la ventana emergente y la
transferencia de MessagePort. Las cabeceras de desarrollo están en vite.config.ts; las de producción en vercel.json.
Mantenga ambas sincronizadas.

Content-Security-Policy

Definida en index.html. script-src debe incluir 'wasm-unsafe-eval'; Chromium rechaza
WebAssembly.instantiate() sin él, que es exactamente lo que hacía que el módulo PVAC fallara al
cargarse de forma silenciosa. Esa directiva solo permite la compilación de WebAssembly; no vuelve a habilitar
el eval() de JavaScript.

connect-src es 'self' https: más bucle local (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*) para que un nodo ejecutado localmente funcione sin abrir texto plano en general. Cualquier
otra cosa por http:// está controlada por src/wallet/endpoint-policy.ts, que es el único lugar que
decide: una función pura de la URL más un contexto explícito, de modo que el store, la interfaz de Settings
y las pruebas no puedan discrepar. No añada comprobaciones de URL ad hoc en otros lugares. Se aplican tres
bloqueadores independientes (contenido mixto → CSP → consentimiento del usuario) y el veredicto informa del más
fundamental primero, de modo que nunca se le dice al usuario que corrija la lista de permitidos cuando es el navegador
el que rechaza.

El proceso WASM de PVAC

Compilación

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py es necesario porque PVAC lanza un #error rígido sin AES por hardware (AES-NI o
las extensiones criptográficas de ARM), que WebAssembly no ofrece. El parche añade una implementación
por software portátil que es idéntica bit a bit pero aproximadamente 5–10× más lenta. Es aditivo: las
rutas por hardware quedan intactas y se escribe una copia de seguridad .hpp.bak.

Carga

src/pvac/wasm-bridge.ts carga el módulo en tres pasos:

  1. Sondeo — HEAD sobre la URL de pegamento, de modo que "sin compilar" (404) se distinga de "bloqueado por la CSP". Sin esto, ambos se manifiestan como un fallo de importación opaco idéntico.
  2. Importación — import() dinámico de una URL absoluta con /* @vite-ignore */. Debe ser absoluta: un especificador simple no se resuelve, y ./wasm/pvac.js se resuelve contra /assets/ y da 404.
  3. Verificación — comprueba que existen las 13 exportaciones _pvac_* requeridas antes de intercambiar el puente. Las compilaciones anteriores omitían las funciones de serialización, lo que rompía el cifrado/descifrado de una forma que el nodo solo reportaba como "malformed transaction".

Los fallos se clasifican como PvacFailureReason: not-built, csp-blocked,
missing-exports, init-failed, unknown. Cada uno se corresponde con una solución concreta mostrada en
Settings. La promesa singleton se reinicia en caso de fallo para que ↻ Reload PVAC pueda reintentar en lugar
de repetir un rechazo en caché.

Reglas de memoria

La API de C es de memoria manual. Cada _malloc necesita un _free; cada serialize_* devuelve un
búfer que debe liberarse con _pvac_free_bytes. Los identificadores de keygen/enc_* necesitan
su _pvac_free_* correspondiente. Use try/finally; consulte WasmPvacBridge para el patrón.

Gestión del estado

Zustand, en src/store/wallet-store.ts. Es propietario de la cartera, el cliente RPC, los ajustes, el estado
de PVAC, los avisos (toasts) y el indicador global de carga.

El indicador global de carga (isLoading) controla una superposición de desenfoque a pantalla completa y está reservado para
solo las transiciones de toda la aplicación, como el desbloqueo de la cartera. El trabajo por panel debe usar
usePanelLoading en su lugar; vea más abajo.

Gestión de errores

src/components/ErrorBoundary.tsx envuelve cada panel en Layout.tsx, con clave según la pestaña
activa para que un límite que se dispara se reinicie al navegar, más un límite en la raíz en main.tsx.

Esto importa más de lo que parece. index.html contiene:

#root:empty::before { content: 'Loading Orion Wallet…'; }

Sin un límite, cualquier excepción en tiempo de renderizado hace que React 18 desmonte todo el árbol, #root
queda vacío y se renderiza ese contenido de reserva, produciendo una página en blanco que parece atascada
cargando para siempre. El límite mantiene vivo el armazón y muestra una tarjeta de error reintentable.

Consecuencia: las funciones llamadas durante el renderizado no deben lanzar excepciones ante entradas mal formadas.
formatAmount en src/tx/builder.ts acepta unknown y degrada a un marcador de posición,
porque ni las respuestas de RPC ni la caché de transacciones local se validan por esquema. Normalice
las filas no confiables antes de renderizarlas; HistoryView muestra el patrón.

Estados de carga

Use usePanelLoading (src/hooks/usePanelLoading.ts) para el trabajo con alcance de panel:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

Después renderice <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />.

Importan dos propiedades: el modal es descartable (el trabajo continúa en segundo plano, de modo que una
red lenta nunca atrapa al usuario), y las escrituras de estado están condicionadas a isMounted() para que
navegar a otro lugar a mitad de camino no pueda dejar un modal atascado en pantalla.

Almacenamiento y migraciones

IndexedDB mediante idb, base de datos orion-wallet, versión 6. Los almacenes se declaran una sola vez en el
array OBJECT_STORES de src/wallet/storage.ts; añada los nuevos ahí para que la creación y la
migración se mantengan coherentes; ese array también impulsa wipeEverything(), de modo que un almacén añadido
en cualquier otro lugar sobreviviría a un borrado.

Las migraciones son solo aditivas: incremente DB_VERSION, añada al array y anote la
versión en un comentario junto a las nuevas entradas. Los almacenes existentes nunca se renombran ni se eliminan.
Las versiones hasta ahora: v2 almacenes del SDK, v3 tokens OCS01, v4 marcadores oct://, v5
unlock-session-keys, v6 contacts + passkey-unlock.

La migración del cambio de marca

Renombrar la base de datos desde webcli-react habría dejado huérfana cada cartera existente, ya que
IndexedDB delimita los datos por nombre de base de datos. migrateLegacyDatabase copia todos los almacenes hacia adelante en el
primer inicio. Es:

  • idempotente — se omite una vez que el destino tiene alguna cartera
  • no destructiva — la base de datos heredada se deja intacta para poder revertir
  • no fatal — los fallos se registran, nunca se lanzan; un error de migración no debe bloquear el arranque

Recuerde que clearIndexedDB en los ayudantes de E2E debe eliminar ambas bases de datos, o la
migración vuelve a copiar los datos heredados y el "estado limpio" no está limpio.

SDK de la cartera

src/sdk/ es el proveedor orientado a las dApps; src/connect/ es la ventana emergente de aprobación servida en
/connect.

Espacios de nombres de métodos

La cartera responde a dos espacios de nombres equivalentes:

quieren dirigirse explícitamente a Orion Wallet; los nombres genéricos wallet_* siguen siendo compatibles para
que las integraciones existentes sigan funcionando.

canonicalizeMethod en src/sdk/protocol.ts reduce cada nombre de método a su forma canónica
wallet_* antes del despacho, de modo que los dos espacios de nombres nunca puedan desincronizarse.

Ciclo de vida de la conexión

Handshake (una vez por sesión):

  1. La dApp llama a provider.connect() → PopupTransport abre /connect?v=1&rid=…&origin=…
  2. La cartera renderiza ConnectApp, el usuario desbloquea si es necesario
  3. La cartera envía hello + MessagePort mediante window.postMessage, con el origen validado
  4. La dApp devuelve el challenge por el puerto (anti-repetición)
  5. ConnectHandler verifica el acuse, sirve la RPC CONNECT → devuelve dirección, cuentas, red

Tras conectar:

  • La ventana emergente puede cerrarse, pero el MessagePort permanece abierto; es independiente de la ventana
  • La sesión persiste en IndexedDB (sdk-sessions) con TTL por inactividad + absoluto
  • Los métodos de lectura (getBalance, getAccounts) son silenciosos dentro de la sesión
  • Los métodos de firma siempre abren un nuevo aviso de aprobación

La solución para "conectar funciona, nada más funciona":

Originalmente PopupTransport.isConnected() comprobaba popup.closed, de modo que cada llamada después de que la
ventana de aprobación se cerrara fallaba con "Transport is not connected". Ahora solo comprueba el
puerto, que sobrevive a la ventana emergente. La cartera cierra la ventana emergente tras la aprobación, pero la
conexión sigue activa.

Modelo de permisos

En el momento de la conexión: solo ámbitos de solo lectura (viewAccounts, viewBalance, viewNetwork).

Los ámbitos de firma (signMessage, signContract, etc.) se conceden de forma diferida en la primera
aprobación correcta. Antes de la corrección, estaban ausentes de DEFAULT_PERMISSIONS y el
despachador rechazaba cada llamada de firma con UNAUTHORIZED antes de que el aviso pudiera aparecer:
la segunda causa raíz del síntoma.

Ahora:

  • La comprobación de permisos permite que los ámbitos de firma no concedidos avancen hasta el aviso de aprobación
  • Al aprobar, grantPermission persiste el ámbito en la sesión
  • Las llamadas posteriores omiten la comprobación de permisos pero siguen requiriendo aprobación: conceder un ámbito solo registra que el usuario acepta que la dApp pueda preguntar

La revocación es explícita: revokePermission elimina el ámbito de permissions y lo registra
en deniedPermissions, que el despachador rechaza de plano.

Invariantes de seguridad

No debilite estas:

  • Validación de origen en cada postMessage entrante (PopupTransport.ts, rpc-handler.ts)
  • Anti-repetición: desafío CSPRNG + nonce de la dApp + nonce monótono por sesión. makeId sirve únicamente para la correlación de mensajes y nunca debe usarse como valor de seguridad
  • Los permisos son por origen, se persisten en sdk-sessions y se conceden/revocan explícitamente
  • Independencia del MessagePort: el puerto sobrevive a la ventana emergente. Una vez transferido, la cartera puede cerrar la ventana de aprobación sin romper la conexión
  • Los métodos prohibidos se rechazan tanto en el lado del cliente (WalletProvider) como en el lado de la cartera (rpc-handler), de modo que la ejecución de transacciones nunca puede escapar al SDK ni siquiera a través del mecanismo de escape de bajo nivel request()
  • localStorage contiene solo una pista para restaurar la sesión (dirección, red); nunca secretos

Integración de dApps

Inicio rápido

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

Gestión de sesiones

Las sesiones de Orion caducan tras 30 minutos de inactividad u 8 horas absolutas. El SDK proporciona
comprobaciones integradas del estado de la sesión y reconexión automática:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

Redes, incluidas las propias del usuario

Un usuario puede añadir su propia red en Settings → Network (su propio nodo, una bifurcación de devnet, un
RPC de pago). Esas redes son de primera clase: aparecen en el selector de la ventana emergente de conexión
junto a las predefinidas, y una dApp conectada puede verlas.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

Detecte la característica mediante la capacidad customNetworks antes de depender de nada de esto: las
compilaciones de cartera más antiguas solo responden al escueto wallet_getNetwork, que devuelve una cadena de id.

NetworkInfo deliberadamente no lleva ni rpcUrl ni relayerUrl. Una red añadida por el
usuario suele ser un endpoint privado —una dirección de LAN, un túnel, una URL de proveedor con la
clave de API en la cadena de consulta— y entregar eso a cada sitio al que el usuario se conecta
filtraría su infraestructura. Una dApp no lo necesita: cada lectura pasa por la cartera
(wallet_getBalance y similares) y la ejecución nunca sale de la interfaz de la cartera. Lo que cruza
el cable es lo que una dApp necesita legítimamente: a qué red está hablando, si el
propietario la añadió a mano (custom) y dónde enlazar una transacción (explorerUrl).

No existe ningún wallet_switchNetwork. El cambio permanece en la propia interfaz de la cartera —el
selector de la ventana emergente o la píldora de red de la ventana principal—, coherente con la regla de que los cambios de estado
nunca se originan en una dApp. Una dApp que necesita otra red pide al usuario que cambie y luego
espera networkChanged.

networkChanged se emite desde ambos lugares donde puede ocurrir un cambio: la ventana emergente de conexión y
la ventana principal. Las sesiones se traspasan a la ventana principal cuando la ventana emergente se cierra, de modo que para
cuando la mayoría de los usuarios tocan la píldora de red la ventana emergente hace tiempo que desapareció: Layout.tsx emite a los
manejadores adoptados para que a una dApp conectada no se le quede mostrando una red obsoleta.

Dos clases independientes implementan WalletHost: src/connect/host.ts (ventana principal) y un
host en línea en src/connect/ConnectApp.tsx (ventana emergente). Cualquier cosa que se añada a la interfaz debe
implementarse en ambas, más el fixture en tests/unit/connect-handler.test.ts.

Métodos prohibidos

El SDK bloquea estos métodos localmente antes de que lleguen al transporte. La cartera también
vuelve a comprobarlos en el lado del servidor, de modo que la ejecución de transacciones nunca puede escapar:

  • wallet_sendTransaction / sendTransaction
  • wallet_broadcastTransaction / broadcastTransaction
  • wallet_transfer / transfer
  • wallet_swap / swap
  • wallet_bridge / bridge

Gestión de sesiones

Las sesiones de Orion Wallet se gestionan automáticamente mediante el SDK. Las sesiones caducan tras:

  • Tiempo de espera por inactividad: 30 minutos de inactividad
  • Tiempo de espera absoluto: 8 horas desde la conexión

La dApp puede comprobar el estado de la sesión en cualquier momento:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

Cuando una sesión caduca, la cartera emite un evento sessionExpired. La dApp debería
escuchar este evento y pedir al usuario que se reconecte:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

La restauración de la sesión se gestiona automáticamente: la cartera conserva la pista de la sesión en
IndexedDB, de modo que reconectarse tras la caducidad no exige que el usuario vuelva a importar su cartera.

Pruebas

npm test                 # 676 unit tests, 56 files
npm run test:coverage    # V8 coverage, 60% threshold
npm run test:e2e         # 7 Playwright specs (needs npm run build first)
npm run autofix          # typecheck → format → lint --fix → test → build
npm run check            # same, read-only (CI)

Las pruebas unitarias se ejecutan bajo jsdom con fake-indexeddb. Las pruebas de componentes usan
renderToStaticMarkup en lugar de una biblioteca de pruebas del DOM; consulte
tests/unit/processing-modal.test.tsx.

WebAuthn no tiene implementación en jsdom, así que tests/unit/passkey.test.ts instala un
FakeAuthenticator que modela la extensión PRF (incluido un autenticador que carece de ella,
un aviso descartado y un secreto rotado). Afirma lo que el registro almacenado no debe
contener, que es la propiedad que realmente importa.

Nota sobre E2E: antes de creerse un muro de fallos de Playwright, revise la máquina, no el diff.
Dos límites del entorno producen fallos que se parecen exactamente a regresiones reales:

  • Espacio temporal. Chromium coloca cada perfil de navegador bajo TMPDIR (/tmp por defecto). Si ese sistema de archivos está lleno —fácil cuando /tmp es un tmpfs pequeño compartido con otros procesos— los contextos mueren al arrancar y pruebas no relacionadas fallan en milisegundos, o se cuelgan hasta el tiempo de espera de 30 s. Ejecute df -h /tmp primero; vuelva a ejecutar con TMPDIR=$HOME/.cache/e2e-tmp en un sistema de archivos holgado y las mismas specs pasan de agotar el tiempo a superarse en ~4 s.
  • Memoria. Aproximadamente 2 GB de memoria libre por worker. Cuando se agota, Chromium se mata a mitad de prueba y Playwright informa de Target crashed; vuelva a ejecutar con --workers=1.

playwright.config.ts establece reuseExistingServer: !isCI, de modo que un npm run preview residual en
el puerto 4173 se reutiliza silenciosamente: incluido uno iniciado desde un checkout diferente. Al
comparar dos árboles, mate el listener entre ejecuciones (ss -lptn | grep 4173) o la segunda
ejecución probará la compilación de la primera.

Al corregir un error, añada una prueba que documente el modo de fallo, no solo la corrección.

Lista de verificación de publicación

  1. npm run autofix: debe estar totalmente en verde
  2. npm run test:e2e contra un npm run build recién hecho
  3. npm audit --omit=dev: producción debe informar de cero vulnerabilidades
  4. Verifique que PVAC se carga en una vista previa de producción (npm run preview), no solo en desarrollo
  5. Pruebe la ruta de migración desde una compilación anterior al cambio de marca con datos de cartera existentes
  6. Confirme que las cabeceras de servidor de vite.config.ts siguen coincidiendo con vercel.json

Problemas conocidos

Avisos de dependencias de desarrollo. npm audit informa de vulnerabilidades en vitest, vite, esbuild
y paquetes relacionados. Cada corrección restante requiere una actualización mayor (vite 5→8, vitest 2→4).
Son solo herramientas de compilación y no se envían a los usuarios; las auditorías de producción salen limpias. Consulte
SECURITY.html.

Advertencia de fragmentación de storage.ts. La compilación advierte de que storage.ts se importa tanto de forma estática como
dinámica, por lo que no puede dividirse en su propio fragmento. Es inofensivo, pero significa
que las importaciones dinámicas en HistoryView y WalletExportImport no aportan ningún beneficio de división de código.

Rendimiento del AES por software. El AES de WASM de respaldo es 5–10× más lento que el nativo. Las operaciones
pesadas de PVAC bloquean el hilo principal; moverlas a un Web Worker es el siguiente paso lógico.
