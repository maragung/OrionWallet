الإعداد

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps إلزامي: يصرّح كل من ESLint 9 و@eslint/js 10 بنطاقات peer متعارضة.
يستخدم vercel.json العلم نفسه، لذا يتطابق CI مع التثبيتات المحلية.

يُنصح باستخدام Node 20 أو أحدث.

تطبيق طرف-عميل خالص؛ لا توجد خلفية (backend). تتدفق البيانات في اتجاه واحد:

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

قواعد تصميم ملزمة

يجب أن يكون JSON المتعارف عليه مطابقًا بايتًا-ببايت. يعيد src/tx/canonical-json.ts
إنتاج ترتيب المفاتيح وتنسيق nlohmann::json بدقة. تُحسب التواقيع على هذه البايتات،
لذا فإن أي انحراف يُنتج توقيعًا ترفضه الشبكة. لا "ترتّب" هذا المنسّق.

التسمية: المنتج مقابل البروتوكول. "Orion Wallet" هي المنتج. طرق RPC التابعة
لـoctra_*، وبادئة العنوان oct، ورمز OCT، و"Octra Network" هي معرّفات بروتوكول
ويجب ألا يُعاد تسميتها أبدًا.

نظام البناء

ملفات إعداد TypeScript هي المصدر الوحيد للحقيقة:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
لا تُضف ملفات .js مجاورة لهذه. يحل Vite ملف vite.config.js قبل
vite.config.ts، لذا فإن نسخة مُصرَّفة قديمة تظلّل الإعداد الحقيقي بصمت، وتعديلات
ملف .ts لا تأتي بنتيجة. أسماء الملفات الثلاثة هذه موجودة في .gitignore.
أما eslint.config.js فهو إعداد مسطّح حقيقي ويُبقى عمدًا.

لم يكن تجاهلها كافيًا وحده، لأن لا شيء منعها من أن تُنشأ: فـtsconfig.node.json مشروع
composite، وهو يفرض إصدار إعلانات الأنواع، وبدون outDir كتب أي tsc -b
ملف vite.config.js بجوار المصدر مباشرة. وقد حدث ذلك مرتين. يذهب إصدار (emit) ذلك المشروع الآن
إلى node_modules/.tmp/tsconfig-node/، حيث لا يمكنه تظليل أي شيء. إذا أضفت ملف إعداد لذلك المشروع،
فاترك outDir كما هو.

أعلام البيئة

العلمالتأثير
VITE_ALLOW_HTTP_ENDPOINTS=1يضيف http: إلى توجيه CSP connect-src وقت البناء، ليتمكن بناء مستضاف ذاتيًا من الوصول إلى عقدة RPC بنص صريح. وما تزال موافقة المستخدم لكل أصل مطلوبة — انظر src/wallet/endpoint-policy.ts

يُضبط وقت البناء فقط. يُقرأ في vite.config.ts بواسطة إضافة allowHttpEndpointsCsp
ويعيد كتابة index.html؛ وليس له أي تأثير وقت التشغيل، لأن CSP بوسم meta لا يمكن توسيعه
بعد تحليل المستند.

الترويسات

تُضبط COOP/COEP على same-origin / require-corp (محجوزة لخيوط WASM المستقبلية)،
مع تجاوزات unsafe-none على /connect حتى يعمل نقل postMessage + MessagePort
في النافذة المنبثقة. توجد ترويسات التطوير في vite.config.ts؛ وترويسات الإنتاج في vercel.json.
أبقِ الاثنين متزامنين.

سياسة أمان المحتوى

مُعرَّفة في index.html. يجب أن يتضمن script-src قيمة 'wasm-unsafe-eval' — فبدونها يرفض Chromium
استدعاء WebAssembly.instantiate()، وهذا هو بالضبط ما جعل وحدة PVAC تفشل في التحميل بصمت.
يسمح هذا التوجيه بتجميع WebAssembly فقط؛ ولا يعيد تفعيل eval() في JavaScript.

connect-src هو 'self' https: بالإضافة إلى الحلقة المحلية (http://localhost:*، http://127.0.0.1:*،
http://[::1]:*) لكي تعمل عقدة محلية دون فتح النص الصريح عمومًا. أي شيء آخر عبر http://
يُقيَّد بـsrc/wallet/endpoint-policy.ts، وهو المكان الوحيد الذي يقرر — دالة خالصة من عنوان URL
وسياق صريح، فلا يمكن للمخزن أو واجهة الإعدادات أو الاختبارات أن تختلف. لا تُضف فحوصات عناوين مخصصة
في مكان آخر. تنطبق ثلاثة عوائق مستقلة (mixed content ← CSP ← موافقة المستخدم)، ويُبلَّغ التقرير
بالعائق الأكثر أساسية أولًا، فلا يُطلب من المستخدم أبدًا إصلاح القائمة المسموحة بينما المتصفح هو الرافض.

خط أنابيب PVAC WASM

البناء

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py مطلوب لأن PVAC يُصدر #error صارمًا بدون AES عتادي (AES-NI أو
إضافات التشفير في ARM)، وهو ما لا يوفره WebAssembly. يضيف التصحيح تطبيقًا برمجيًا محمولًا
مطابقًا بايتًا-ببايت لكنه أبطأ بنحو 5–10 أضعاف. وهو إضافي: مسارات العتاد غير ممسوسة،
ويُكتب نسخ احتياطي بامتداد .hpp.bak.

التحميل

يحمل src/pvac/wasm-bridge.ts الوحدة في ثلاث خطوات:

  1. الاستكشاف (Probe) — طلب HEAD على عنوان اللاصق (glue)، ليكون "غير مبني" (404) قابلًا للتمييز عن
    "محجوب بواسطة CSP". بدون هذا يظهر كلاهما كفشل استيراد معتمٍ مماثل.
  2. الاستيراد (Import) — import() ديناميكي لعنوان مطلق مع /* @vite-ignore */. يجب أن يكون
    مطلقًا: فالمُعرِّف المجرد يفشل في التحليل، و./wasm/pvac.js يُحل بالنسبة إلى
    /assets/ فيُعيد 404.
  3. التحقق (Verify) — التأكد من وجود كل الصادرات الـ13 المطلوبة _pvac_* قبل تبديل الجسر.
    أغفلت البناءات الأقدم دوال التسلسل، ما كسر التشفير/فك التشفير بطريقة لم يُبلِّغ عنها
    العقدة إلا كـ"malformed transaction".

تُصنَّف حالات الفشل كـPvacFailureReason: not-built، csp-blocked،
missing-exports، init-failed، unknown. وكل واحد يقابل علاجًا ملموسًا يُعرض في
Settings. تُصفَّر وعد singleton عند الفشل ليتمكن ↻ Reload PVAC من إعادة المحاولة بدلًا من
إعادة تشغيل رفض مخزَّن.

قواعد الذاكرة

واجهة C هي ذاكرة يدوية. كل _malloc يحتاج إلى _free؛ وكل serialize_* يُرجع
مخزنًا مؤقتًا يجب تحريره بـ_pvac_free_bytes. والمقابض الصادرة من keygen/enc_* تحتاج
إلى _pvac_free_* المطابق لها. استخدم try/finally — انظر WasmPvacBridge للنمط.

Zustand، في src/store/wallet-store.ts. يملك المحفظة، وعميل RPC، والإعدادات، وحالة PVAC،
والإشعارات (toasts)، وعلم التحميل العام.

حالات التحميل

استخدم usePanelLoading (src/hooks/usePanelLoading.ts) للعمل بنطاق لوحة:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

ثم اعرض <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />.

خاصيتان مهمتان: النافذة قابلة للإغلاق (dismissible) — يستمر العمل في الخلفية، فلا تحاصر
الشبكة البطيئة المستخدم أبدًا — وكتابات الحالة موقوفة على isMounted() بحيث
لا يمكن لمغادرة في منتصف العملية أن تترك نافذة عالقة على الشاشة.

التخزين والترحيلات

IndexedDB عبر idb، وقاعدة البيانات orion-wallet، إصدار 6. تُصرَّح المخازن مرة واحدة في
مصفوفة OBJECT_STORES في src/wallet/storage.ts؛ أضف الجديدة هناك ليبقى الإنشاء
والترحيل متسقين — وهذه المصفوفة تقود أيضًا wipeEverything()، لذا فإن أي مخزن
أُضيف في مكان آخر سينجو من المسح.

الترحيلات إضافية فقط: ارفع DB_VERSION، وألحق بالمصفوفة، وسجّل
الإصدار في تعليق بجانب الإدخالات الجديدة. لا يُعاد تسمية المخازن القائمة ولا تُحذف أبدًا.
الإصدارات حتى الآن: v2 مخازن SDK، وv3 رموز OCS01، وv4 إشارات oct://، وv5
unlock-session-keys، وv6 contacts + passkey-unlock.

ترحيل إعادة التسمية

كانت إعادة تسمية قاعدة البيانات من webcli-react ستُيتم كل محفظة قائمة، لأن
IndexedDB تنطّق البيانات باسم قاعدة البيانات. ينسخ migrateLegacyDatabase كل المخازن إلى الأمام
عند أول تشغيل. وهو:

  • عديم الأثر عند التكرار (idempotent) — يُتخطى بمجرد أن يحوي الهدف أي محفظة
  • غير مُتلف — تُترك قاعدة البيانات القديمة سليمة للتراجع
  • غير قاتل — تُسجَّل حالات الفشل ولا تُرمى أبدًا؛ يجب ألا يحجب خطأ الترحيل بدء التشغيل

تذكّر أن clearIndexedDB في أدوات E2E يجب أن تحذف قاعدتي البيانات كلتيهما، وإلا
ينسخ الترحيل البيانات القديمة مباشرة ولا تكون "الحالة النظيفة" نظيفة.

دورة حياة الاتصال

المصافحة (مرة واحدة لكل جلسة):

  1. يستدعي dApp الدالة provider.connect() → يفتح PopupTransport نافذة /connect?v=1&rid=…&origin=…
  2. تعرض المحفظة ConnectApp، ويفتح المستخدم القفل إذا لزم
  3. ترسل المحفظة hello + MessagePort عبر window.postMessage، بعد التحقق من الأصل
  4. يرد dApp بـchallenge عبر المنفذ (مضاد لإعادة التشغيل)
  5. يتحقق ConnectHandler من الإقرار، ويقدّم RPC CONNECT → يُرجع العنوان والحسابات والشبكة

بعد الاتصال:

  • قد تُغلق النافذة المنبثقة، لكن MessagePort يبقى مفتوحًا — فهو مستقل عن النافذة
  • تستمر الجلسة في IndexedDB (sdk-sessions) مع حدّي TTL للخمول والمطلق
  • طرق القراءة (getBalance، getAccounts) صامتة داخل الجلسة
  • طرق التوقيع تفتح دائمًا مطالبة موافقة جديدة

الإصلاح لمشكلة "الاتصال يعمل لكن لا شيء غيره":

في الأصل كان PopupTransport.isConnected() يفحص popup.closed، لذا فشل كل استدعاء بعد
إغلاق نافذة الموافقة برسالة "Transport is not connected". الآن يفحص المنفذ فقط،
الذي يعيش أطول من النافذة المنبثقة. تغلق المحفظة النافذة المنبثقة بعد الموافقة، لكن الاتصال يبقى حيًّا.

نموذج الأذونات

وقت الاتصال: نطاقات القراءة فقط (viewAccounts، viewBalance، viewNetwork) فقط.

نطاقات التوقيع (signMessage، signContract، إلخ) تُمنح كسولًا (lazily) عند أول
موافقة ناجحة. قبل الإصلاح، كانت غائبة من DEFAULT_PERMISSIONS وكان الموزّع يرفض كل استدعاء توقيع
برسالة UNAUTHORIZED قبل أن تظهر المطالبة — السبب الجذري الثاني للعَرَض.

الآن:

  • يسمح فحص الإذن لنطاقات التوقيع غير الممنوحة بالمتابعة إلى مطالبة الموافقة
  • عند الموافقة، يثبّت grantPermission النطاق في الجلسة
  • تتخطى الاستدعاءات اللاحقة فحص الإذن لكنها ما تزال تتطلب الموافقة — منح النطاق يسجّل فقط أن المستخدم يوافق على أن dApp قد يطلب

الإلغاء صريح: يزيل revokePermission النطاق من permissions ويسجّله
في deniedPermissions، الذي يرفضه الموزّع رفضًا باتًّا.

ثوابت الأمان

لا تُضعف هذه:

  • التحقق من الأصل في كل postMessage وارد (PopupTransport.ts، rpc-handler.ts)
  • مضاد إعادة التشغيل: تحدٍّ من CSPRNG + nonce من dApp + nonce رتيب لكل جلسة. makeId مخصص لربط الرسائل فقط ويجب ألا يُستخدم أبدًا كقيمة أمنية
  • الأذونات لكل أصل، وتُخزَّن في sdk-sessions، وتُمنح وتُلغى صراحةً
  • استقلالية MessagePort: يعيش المنفذ أطول من النافذة المنبثقة. وبمجرد نقله، يمكن للمحفظة إغلاق نافذة الموافقة دون كسر الاتصال
  • الطرق المحظورة تُرفض طرف-العميل (WalletProvider) وطرف-المحفظة معًا
    (rpc-handler)، فلا يمكن لتنفيذ المعاملات أن يهرب إلى SDK حتى عبر منفذ الهروب منخفض المستوى request()
  • localStorage يحمل فقط تلميح استعادة الجلسة (العنوان، الشبكة) — لا أسرار أبدًا

تكامل dApp

بداية سريعة

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

إدارة الجلسة

تنتهي جلسات Orion بعد 30 دقيقة خمول أو 8 ساعات مطلقة. يوفر SDK
فحوصات صحة جلسة مدمجة وإعادة اتصال تلقائية:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

الشبكات، بما فيها شبكات المستخدم الخاصة

يمكن للمستخدم إضافة شبكته الخاصة في Settings → Network (عقدته الخاصة، أو فرع devnet، أو
RPC مدفوع). تلك الشبكات من الدرجة الأولى: تظهر في مُحدِّد النافذة المنبثقة للاتصال
إلى جانب الإعدادات المسبقة، ويمكن لتطبيق dApp متصل رؤيتها.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

اكشف عن الميزة بالتحقق من إمكانية customNetworks قبل الاعتماد على أي منها — فبناءات
المحفظة الأقدم لا تجيب إلا على wallet_getNetwork المجرّد، الذي يُرجع سلسلة معرّف.

NetworkInfo لا يحمل rpcUrl ولا relayerUrl عمدًا. الشبكة التي أضافها المستخدم غالبًا
نقطة نهاية خاصة — عنوان LAN، أو نفق، أو عنوان موفَّر مع مفتاح API في سلسلة الاستعلام —
وإعطاء ذلك لكل موقع يتصل به المستخدم يسرّب بنيته التحتية. لا يحتاجه تطبيق dApp:
كل قراءة تتم عبر المحفظة (wallet_getBalance وما يشبهه) ولا يغادر التنفيذ واجهة المحفظة أبدًا.
ما يعبر السلك هو ما يحتاجه dApp شرعيًا — أي شبكة يخاطب، وما إذا كان مالكها أضافها يدويًا
(custom)، وأين يربط معاملة (explorerUrl).

لا يوجد wallet_switchNetwork. يبقى التبديل في واجهة المحفظة نفسها — مُحدِّد النافذة المنبثقة
أو حبة الشبكة في النافذة الرئيسية — اتساقًا مع قاعدة أن تغييرات الحالة لا تنشأ أبدًا من تطبيق dApp.
وdApp الذي يحتاج شبكة أخرى يطلب من المستخدم التبديل، ثم ينتظر حدث networkChanged.

يُصدَر networkChanged من كلا الموضعين اللذين يمكن أن يحدث فيهما التبديل: النافذة المنبثقة للاتصال
والنافذة الرئيسية. تُسلَّم الجلسات إلى النافذة الرئيسية عند إغلاق النافذة المنبثقة، لذا بحلول وقت
لمس معظم المستخدمين حبة الشبكة تكون النافذة المنبثقة قد ولّت منذ زمن — يبث Layout.tsx
إلى المعالجات المعتمدة حتى لا يُترك dApp متصل يعرض شبكة قديمة.

يُنفّذ WalletHost صنفان مستقلان — src/connect/host.ts (النافذة الرئيسية) ومضيف
مضمّن في src/connect/ConnectApp.tsx (النافذة المنبثقة). أي شيء يُضاف إلى الواجهة يجب
أن يُنفَّذ في كليهما، بالإضافة إلى النموذج (fixture) في tests/unit/connect-handler.test.ts.

إدارة الجلسة

تُدار جلسات Orion Wallet تلقائيًا بواسطة SDK. تنتهي الجلسات بعد:

  • مهلة الخمول: 30 دقيقة من عدم النشاط
  • المهلة المطلقة: 8 ساعات من لحظة الاتصال

يمكن لتطبيق dApp فحص صحة الجلسة في أي وقت:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

عند انتهاء الجلسة، تصدر المحفظة حدث sessionExpired. ينبغي على dApp
الاستماع لهذا الحدث ومطالبة المستخدم بإعادة الاتصال:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

تُعالَج استعادة الجلسة تلقائيًا — تحفظ المحفظة تلميح الجلسة في
IndexedDB، لذا فإن إعادة الاتصال بعد الانتهاء لا تتطلب من المستخدم إعادة استيراد محفظته.

ملاحظة E2E: قبل تصديق جدارٍ من إخفاقات Playwright، افحص الجهاز لا الفرق (diff).
ثمة حدّان بيئيان يُنتجان إخفاقات تشبه الانحدارات الحقيقية تمامًا:

  • المساحة المؤقتة. يضع Chromium كل ملف تعريف للمتصفح تحت TMPDIR (/tmp افتراضيًا). إذا كان نظام الملفات ممتلئًا — وهو أمر سهل عندما يكون /tmp نظام tmpfs صغيرًا مشتركًا مع عمليات أخرى — تموت السياقات عند الإقلاع وتفشل اختبارات غير ذات صلة خلال ميلي ثانية، أو تعلق حتى مهلة الثلاثين ثانية. تحقق أولًا عبر df -h /tmp؛ ثم أعد التشغيل مع TMPDIR=$HOME/.cache/e2e-tmp على نظام ملفات متّسع، وستنتقل المواصفات نفسها من التعلّق إلى النجاح في نحو 4 ثوانٍ.
  • الذاكرة. يلزم نحو 2 غيغابايت من الذاكرة الحرة لكل عامل. عندما تنفد، يُقتل Chromium في منتصف الاختبار ويُبلغ Playwright عن Target crashed؛ أعد التشغيل مع --workers=1.

يضبط playwright.config.ts الخيار reuseExistingServer: !isCI، لذا يُعاد استخدام أي
npm run preview متبقٍّ على المنفذ 4173 بصمت — بما فيها نسخة بدأت من نسخة عمل
مختلفة. عند مقارنة شجرتين، اقتل المستمع بين عمليتي التشغيل (ss -lptn | grep 4173)
وإلا اختبرت عملية التشغيل الثانية بناء الأولى.

عند إصلاح خطأ، أضف اختبارًا يوثّق نمط الفشل، لا الإصلاح فقط.
tests/unit/history-view.test.ts وerror-boundary.test.tsx تتبعان هذا النهج:

قائمة فحص الإصدار

  1. npm run autofix — يجب أن يكون أخضر بالكامل
  2. npm run test:e2e مقابل بناء جديد من npm run build
  3. npm audit --omit=dev — يجب أن يُظهر الإنتاج صفر ثغرات
  4. تحقق من تحميل PVAC في معاينة إنتاجية (npm run preview)، وليس في وضع التطوير فقط
  5. اختبر مسار الترحيل من بناء سابق لإعادة التسمية مع بيانات محفظة موجودة
  6. أكِّد أن ترويسات خادم vite.config.ts ما تزال تطابق vercel.json
