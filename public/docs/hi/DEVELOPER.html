सेटअप

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps अनिवार्य है: ESLint 9 और @eslint/js 10 परस्पर विरोधी पीयर
रेंज घोषित करते हैं। vercel.json वही फ़्लैग उपयोग करता है, इसलिए CI और स्थानीय इंस्टॉल एक-दूसरे से मेल खाते हैं।

Node 20+ अनुशंसित है।

आर्किटेक्चर

पूरी तरह क्लाइंट-साइड; कोई बैकएंड नहीं है। डेटा एक ही दिशा में बहता है:

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

डिज़ाइन बाध्यताएँ

कैनोनिकल JSON बाइट-सटीक होना चाहिए। src/tx/canonical-json.ts nlohmann::json की
की-ऑर्डरिंग और फ़ॉर्मेटिंग को ठीक-ठीक पुनरुत्पादित करता है। हस्ताक्षर इन्हीं बाइट्स पर परिकलित होते हैं,
इसलिए कोई भी विचलन ऐसा हस्ताक्षर बनाता है जिसे नेटवर्क अस्वीकार कर देता है। इस सीरियलाइज़र को "साफ़-सुथरा" न करें।

नामकरण: प्रोडक्ट बनाम प्रोटोकॉल। "Orion Wallet" प्रोडक्ट है। octra_* RPC मेथड,
oct एड्रेस प्रीफ़िक्स, OCT टिकर, और "Octra Network" प्रोटोकॉल आइडेंटिफ़ायर हैं
और इनका नाम कभी नहीं बदला जाना चाहिए।

बिल्ड सिस्टम

TypeScript कॉन्फ़िग फ़ाइलें सत्य का एकमात्र स्रोत हैं:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
इनके लिए .js सहोदर फ़ाइलें न जोड़ें। Vite vite.config.js को
vite.config.ts से पहले रिज़ॉल्व करता है, इसलिए कोई बासी ट्रांसपाइल की गई प्रति चुपचाप असली कॉन्फ़िग को
ढँक देती है और .ts फ़ाइल में किए गए संपादन कुछ नहीं करते। वे तीनों फ़ाइलनाम .gitignore में हैं।
eslint.config.js असली फ़्लैट कॉन्फ़िग है और इसे जान-बूझकर रखा गया है।

उन्हें केवल अनदेखा करना अपने-आप में पर्याप्त नहीं था, क्योंकि कुछ भी उन्हें बनने से नहीं रोकता था:
tsconfig.node.json एक composite प्रोजेक्ट है, जो डिक्लेरेशन एमिट को बाध्य करता है, और बिना किसी
outDir के कोई भी tsc -b vite.config.js को सीधे सोर्स के बगल में लिख देता था। ऐसा दो बार हुआ।
अब उस प्रोजेक्ट का एमिट node_modules/.tmp/tsconfig-node/ में जाता है, जहाँ यह कुछ भी नहीं ढँक सकता।
यदि आप उस प्रोजेक्ट में कोई कॉन्फ़िग फ़ाइल जोड़ते हैं, तो outDir को वैसा ही रहने दें।

एनवायरनमेंट फ़्लैग

फ़्लैगप्रभाव
VITE_ALLOW_HTTP_ENDPOINTS=1बिल्ड के समय connect-src CSP डायरेक्टिव में http: जोड़ता है, ताकि कोई सेल्फ़-होस्टेड बिल्ड किसी plain-http RPC नोड तक पहुँच सके। हर ऑरिजिन के लिए उपयोगकर्ता की सहमति फिर भी लागू रहती है — देखें src/wallet/endpoint-policy.ts

केवल बिल्ड के समय सेट होता है। इसे vite.config.ts में allowHttpEndpointsCsp प्लगइन द्वारा पढ़ा जाता है
और यह index.html को फिर से लिखता है; इसका कोई रनटाइम प्रभाव नहीं है, क्योंकि दस्तावेज़ पार्स हो जाने के
बाद किसी मेटा-टैग CSP को चौड़ा नहीं किया जा सकता।

हेडर

COOP/COEP को same-origin / require-corp पर सेट किया गया है (भविष्य की WASM थ्रेडिंग के लिए आरक्षित),
/connect पर unsafe-none ओवरराइड के साथ ताकि पॉपअप का postMessage + MessagePort
ट्रांसफ़र काम करे। डेव हेडर vite.config.ts में रहते हैं; प्रोडक्शन हेडर vercel.json में।
दोनों को समक्रमिक रखें।

Content-Security-Policy

index.html में परिभाषित। script-src में 'wasm-unsafe-eval' शामिल होना ही चाहिए — इसके बिना
Chromium WebAssembly.instantiate() को अस्वीकार कर देता है, और ठीक यही वह वजह थी जिससे PVAC मॉड्यूल
चुपचाप लोड होने में विफल हो जाता था। वह डायरेक्टिव केवल WebAssembly कम्पाइलेशन की अनुमति देता है; यह
JavaScript eval() को दोबारा सक्षम नहीं करता।

connect-src है 'self' https: तथा लूपबैक (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*) ताकि स्थानीय रूप से चलने वाला नोड सामान्यतः प्लेनटेक्स्ट खोले बिना काम करे।
http:// पर बाकी कुछ भी src/wallet/endpoint-policy.ts द्वारा नियंत्रित होता है, जो निर्णय लेने वाली
एकमात्र जगह है — URL और एक स्पष्ट संदर्भ का एक शुद्ध फ़ंक्शन, ताकि स्टोर, Settings UI
और टेस्ट आपस में असहमत न हो सकें। कहीं और तदर्थ URL जाँचें न जोड़ें। तीन स्वतंत्र
ब्लॉकर लागू होते हैं (मिक्स्ड कंटेंट → CSP → उपयोगकर्ता सहमति) और फ़ैसला सबसे
बुनियादी वाले को पहले बताता है, ताकि उपयोगकर्ता को कभी यह न कहा जाए कि allowlist ठीक करें जबकि मना तो
ब्राउज़र कर रहा है।

PVAC WASM पाइपलाइन

बिल्डिंग

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py आवश्यक है क्योंकि हार्डवेयर AES (AES-NI या ARM क्रिप्टो एक्सटेंशन) के बिना PVAC
कठोरता से #error देता है, जो WebAssembly प्रदान नहीं करता। यह पैच एक पोर्टेबल सॉफ़्टवेयर
कार्यान्वयन जोड़ता है जो बिट-समान है पर लगभग 5–10× धीमा है। यह योगात्मक है:
हार्डवेयर पथ अछूते रहते हैं, और एक बैकअप .hpp.bak लिखा जाता है।

लोडिंग

src/pvac/wasm-bridge.ts मॉड्यूल को तीन चरणों में लोड करता है:

  1. Probe — ग्लू URL पर HEAD, ताकि "not built" (404) को "blocked by CSP" से
    अलग पहचाना जा सके। इसके बिना दोनों एक जैसी अपारदर्शी इंपोर्ट विफलता के रूप में सामने आते हैं।
  2. Import — /* @vite-ignore */ के साथ किसी absolute URL का डायनैमिक import()। यह absolute
    होना ही चाहिए: कोई बेयर स्पेसिफ़ायर रिज़ॉल्व नहीं हो पाता, और ./wasm/pvac.js /assets/ के सापेक्ष
    रिज़ॉल्व होकर 404 देता है।
  3. Verify — ब्रिज को स्वैप करने से पहले पुष्टि करें कि सभी 13 आवश्यक _pvac_* एक्सपोर्ट मौजूद हैं।
    पहले के बिल्ड सीरियलाइज़ेशन फ़ंक्शन छोड़ देते थे, जिससे एन्क्रिप्ट/डिक्रिप्ट इस तरह टूटता था कि
    नोड इसे केवल "malformed transaction" के रूप में रिपोर्ट करता था।

विफलताओं को PvacFailureReason के रूप में वर्गीकृत किया जाता है: not-built, csp-blocked,
missing-exports, init-failed, unknown। प्रत्येक Settings में दिखाए गए एक ठोस उपाय से मैप होता है।
विफलता पर सिंगलटन प्रॉमिस रीसेट हो जाता है ताकि ↻ Reload PVAC किसी कैश की गई अस्वीकृति को
दोहराने के बजाय पुनः प्रयास कर सके।

मेमोरी नियम

C API मैनुअल-मेमोरी वाला है। हर _malloc को एक _free चाहिए; हर serialize_* एक
बफ़र लौटाता है जिसे _pvac_free_bytes से रिलीज़ करना ज़रूरी है। keygen/enc_* से मिले हैंडल को
उनके संगत _pvac_free_* की ज़रूरत होती है। try/finally का उपयोग करें — पैटर्न के लिए WasmPvacBridge देखें।

स्टेट प्रबंधन

Zustand, src/store/wallet-store.ts में। यह वॉलेट, RPC क्लाइंट, सेटिंग्स, PVAC
स्थिति, टोस्ट, और ग्लोबल लोडिंग फ़्लैग का स्वामी है।

ग्लोबल लोडिंग फ़्लैग (isLoading) एक फ़ुल-स्क्रीन ब्लर ओवरले चलाता है और केवल पूरे-ऐप के
ट्रांज़िशन के लिए आरक्षित है, जैसे वॉलेट अनलॉक। प्रति-पैनल काम के लिए इसके बजाय
usePanelLoading का उपयोग होना चाहिए — नीचे देखें।

एरर हैंडलिंग

src/components/ErrorBoundary.tsx Layout.tsx में हर पैनल को रैप करती है, जो सक्रिय टैब के
अनुसार की-गई होती है ताकि नेविगेशन पर कोई ट्रिप हुई बाउंड्री रीसेट हो जाए, साथ ही main.tsx में रूट पर एक बाउंड्री।

यह दिखने से ज़्यादा मायने रखता है। index.html में यह है:

#root:empty::before { content: 'Loading Orion Wallet…'; }

किसी बाउंड्री के बिना, रेंडर-समय पर कोई भी थ्रो React 18 से पूरे ट्री को अनमाउंट करा देता है, #root
खाली हो जाता है, और वह फ़ॉलबैक रेंडर होता है — जिससे एक खाली सफ़ेद पेज बनता है जो हमेशा के लिए लोड होने पर
अटका हुआ दिखता है। बाउंड्री शेल को जीवित रखती है और एक पुनः-प्रयास योग्य एरर कार्ड दिखाती है।

परिणाम: रेंडर के दौरान बुलाए जाने वाले फ़ंक्शन विकृत इनपुट पर थ्रो नहीं करने चाहिए।
src/tx/builder.ts में formatAmount unknown स्वीकार करता है और एक प्लेसहोल्डर पर उतर आता है,
क्योंकि न तो RPC प्रतिक्रियाएँ और न ही स्थानीय tx कैश स्कीमा-सत्यापित होते हैं। अविश्वसनीय पंक्तियों को
रेंडर करने से पहले सामान्यीकृत करें — HistoryView इस पैटर्न को दिखाता है।

लोडिंग स्थितियाँ

पैनल-स्कोप वाले काम के लिए usePanelLoading (src/hooks/usePanelLoading.ts) का उपयोग करें:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

फिर <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} /> रेंडर करें।

दो गुण मायने रखते हैं: मोडल बंद किया जा सकने वाला है (काम पृष्ठभूमि में जारी रहता है, इसलिए कोई
धीमा नेटवर्क उपयोगकर्ता को कभी नहीं फँसाता), और स्टेट राइट isMounted() पर नियंत्रित होते हैं ताकि
बीच-प्रवाह में कहीं और जाने पर कोई मोडल स्क्रीन पर अटका न रह जाए।

स्टोरेज और माइग्रेशन

idb के ज़रिए IndexedDB, डेटाबेस orion-wallet, संस्करण 6। स्टोर src/wallet/storage.ts में
OBJECT_STORES ऐरे में एक बार घोषित किए जाते हैं; नए स्टोर वहीं जोड़ें ताकि निर्माण और
माइग्रेशन सुसंगत रहें — वह ऐरे wipeEverything() को भी चलाता है, इसलिए कहीं और जोड़ा गया कोई स्टोर
वाइप से बच जाएगा।

माइग्रेशन केवल योगात्मक होते हैं: DB_VERSION बढ़ाएँ, ऐरे में जोड़ें, और नई प्रविष्टियों के
बगल में एक टिप्पणी में संस्करण नोट करें। मौजूदा स्टोर कभी भी न तो नाम बदले जाते हैं और न हटाए जाते हैं।
अब तक के संस्करण: v2 SDK स्टोर, v3 OCS01 टोकन, v4 oct:// बुकमार्क, v5
unlock-session-keys, v6 contacts + passkey-unlock।

रीब्रांड माइग्रेशन

डेटाबेस का नाम webcli-react से बदलने पर हर मौजूदा वॉलेट अनाथ हो जाता, क्योंकि
IndexedDB डेटा को डेटाबेस नाम के अनुसार स्कोप करता है। migrateLegacyDatabase पहली बार लॉन्च पर सभी
स्टोर को आगे कॉपी कर देता है। यह है:

  • idempotent — लक्ष्य में कोई भी वॉलेट होते ही छोड़ दिया जाता है
  • non-destructive — रोलबैक के लिए लेगेसी डेटाबेस को अक्षुण्ण छोड़ा जाता है
  • non-fatal — विफलताएँ लॉग होती हैं, कभी थ्रो नहीं होतीं; कोई माइग्रेशन बग स्टार्टअप को नहीं रोकना चाहिए

याद रखें कि E2E हेल्पर्स में clearIndexedDB को दोनों डेटाबेस हटाने ही चाहिए, वरना
माइग्रेशन लेगेसी डेटा को सीधे वापस कॉपी कर देता है और "clean state" साफ़ नहीं रहता।

कनेक्शन जीवनचक्र

हैंडशेक (प्रति सेशन एक बार):

  1. dApp provider.connect() कॉल करता है → PopupTransport /connect?v=1&rid=…&origin=… खोलता है
  2. वॉलेट ConnectApp रेंडर करता है, ज़रूरत पड़ने पर उपयोगकर्ता अनलॉक करता है
  3. वॉलेट window.postMessage पर hello + MessagePort भेजता है, ऑरिजिन-सत्यापित
  4. dApp पोर्ट पर challenge को प्रतिध्वनित करता है (anti-replay)
  5. ConnectHandler ack सत्यापित करता है, CONNECT RPC परोसता है → एड्रेस, अकाउंट, नेटवर्क लौटाता है

कनेक्ट के बाद:

  • पॉपअप बंद हो सकता है, पर MessagePort खुला रहता है — यह विंडो से स्वतंत्र है
  • सेशन IndexedDB (sdk-sessions) में idle + absolute TTL के साथ बना रहता है
  • रीड मेथड (getBalance, getAccounts) सेशन-मौन होते हैं
  • साइनिंग मेथड हमेशा एक नया अनुमोदन प्रॉम्प्ट खोलते हैं

"connect काम करता है, बाकी कुछ नहीं" का समाधान:

मूल रूप से PopupTransport.isConnected() popup.closed जाँचता था, इसलिए अनुमोदन विंडो बंद
होने के बाद हर कॉल "Transport is not connected" के साथ विफल हो जाती थी। अब यह केवल पोर्ट जाँचता है,
जो पॉपअप से अधिक समय तक जीवित रहता है। वॉलेट अनुमोदन के बाद पॉपअप बंद कर देता है, पर
कनेक्शन जीवित रहता है।

अनुमति मॉडल

कनेक्ट-समय: केवल रीड-ओनली स्कोप (viewAccounts, viewBalance, viewNetwork)।

साइनिंग स्कोप (signMessage, signContract, आदि) पहली सफल अनुमोदन पर आलस्यपूर्वक
प्रदान किए जाते हैं। समाधान से पहले, वे DEFAULT_PERMISSIONS से अनुपस्थित थे और
डिस्पैचर प्रॉम्प्ट प्रकट होने से पहले ही हर साइनिंग कॉल को UNAUTHORIZED के साथ अस्वीकार कर देता था —
लक्षण का दूसरा मूल कारण।

अब:

  • अनुमति जाँच बिना-प्रदत्त साइनिंग स्कोप को अनुमोदन प्रॉम्प्ट तक बढ़ने देती है
  • अनुमोदन पर, grantPermission स्कोप को सेशन में स्थायी कर देता है
  • बाद की कॉल अनुमति जाँच को छोड़ देती हैं पर फिर भी अनुमोदन आवश्यक है — कोई स्कोप प्रदान करना केवल यह दर्ज करता है कि उपयोगकर्ता सहमत है कि dApp पूछ सकता है

निरसन स्पष्ट है: revokePermission स्कोप को permissions से हटाता है और उसे
deniedPermissions में दर्ज करता है, जिसे डिस्पैचर सीधे अस्वीकार कर देता है।

सुरक्षा अपरिवर्तनीय नियम

इन्हें कमज़ोर न करें:

  • ऑरिजिन सत्यापन हर इनबाउंड postMessage पर (PopupTransport.ts, rpc-handler.ts)
  • Anti-replay: CSPRNG challenge + dApp nonce + प्रति-सेशन मोनोटोनिक nonce। makeId केवल
    संदेश सहसंबंध के लिए है और इसे कभी भी सुरक्षा मान के रूप में उपयोग नहीं करना चाहिए
  • अनुमतियाँ प्रति-ऑरिजिन होती हैं, sdk-sessions में स्थायी रहती हैं, और स्पष्ट रूप से प्रदान/निरस्त की जाती हैं
  • MessagePort स्वतंत्रता: पोर्ट पॉपअप से अधिक समय तक जीवित रहता है। एक बार ट्रांसफ़र हो जाने पर,
    वॉलेट कनेक्शन तोड़े बिना अनुमोदन विंडो बंद कर सकता है
  • निषिद्ध मेथड क्लाइंट-साइड (WalletProvider) और वॉलेट-साइड (rpc-handler) दोनों पर अस्वीकार
    किए जाते हैं, इसलिए लेनदेन निष्पादन कभी भी SDK तक नहीं भाग सकता, यहाँ तक कि निम्न-स्तरीय request() एस्केप हैच के ज़रिए भी नहीं
  • localStorage केवल एक सेशन-रीस्टोर संकेत रखता है (एड्रेस, नेटवर्क) — कभी रहस्य नहीं

सेशन प्रबंधन

Orion सेशन 30 मिनट निष्क्रिय या 8 घंटे निरपेक्ष के बाद समाप्त हो जाते हैं। SDK
अंतर्निहित सेशन-स्वास्थ्य जाँच और ऑटो-रीकनेक्ट प्रदान करता है:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

नेटवर्क, उपयोगकर्ता के अपने सहित

उपयोगकर्ता Settings → Network में अपना खुद का नेटवर्क जोड़ सकता है (उनका अपना नोड, एक devnet फ़ोर्क, एक
भुगतान वाला RPC)। वे नेटवर्क प्रथम-श्रेणी के होते हैं: वे प्रीसेट के साथ-साथ कनेक्ट पॉपअप के सिलेक्टर में
दिखते हैं, और एक कनेक्टेड dApp उन्हें देख सकता है।

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

इस पर निर्भर होने से पहले customNetworks क्षमता पर फ़ीचर-डिटेक्ट करें — पुराने
वॉलेट बिल्ड केवल सादे wallet_getNetwork का उत्तर देते हैं, जो एक id स्ट्रिंग लौटाता है।

NetworkInfo जान-बूझकर न कोई rpcUrl रखता है और न कोई relayerUrl। उपयोगकर्ता-जोड़ा
नेटवर्क अक्सर एक निजी एंडपॉइंट होता है — एक LAN एड्रेस, एक टनल, क्वेरी स्ट्रिंग में API की के साथ एक
प्रोवाइडर URL — और उसे उपयोगकर्ता द्वारा कनेक्ट की गई हर साइट को सौंपना उनके इन्फ़्रास्ट्रक्चर को
लीक कर देता। किसी dApp को इसकी ज़रूरत नहीं: हर रीड वॉलेट से होकर जाता है
(wallet_getBalance और उसके साथी) और निष्पादन कभी वॉलेट UI से बाहर नहीं जाता। तार पर जो
पार होता है वही है जिसकी किसी dApp को वैध रूप से ज़रूरत है — वह किस नेटवर्क से बात कर रहा है, क्या
मालिक ने उसे हाथ से जोड़ा (custom), और लेनदेन को कहाँ लिंक करना है (explorerUrl)।

कोई wallet_switchNetwork नहीं है। स्विचिंग वॉलेट के अपने UI में ही रहती है — पॉपअप का
सिलेक्टर या मुख्य विंडो की नेटवर्क पिल — इस नियम के अनुरूप कि स्टेट परिवर्तन कभी किसी dApp से
उत्पन्न नहीं होते। किसी अन्य नेटवर्क की ज़रूरत वाला dApp उपयोगकर्ता से स्विच करने को कहता है, फिर
networkChanged की प्रतीक्षा करता है।

networkChanged उन दोनों जगहों से एमिट होता है जहाँ स्विच हो सकता है: कनेक्ट पॉपअप और
मुख्य विंडो। पॉपअप बंद होने पर सेशन मुख्य विंडो को सौंप दिए जाते हैं, इसलिए जब तक
अधिकांश उपयोगकर्ता नेटवर्क पिल को छूते हैं तब तक पॉपअप कब का जा चुका होता है — Layout.tsx अपनाए गए
हैंडलर को एमिट करता है ताकि किसी कनेक्टेड dApp को एक बासी नेटवर्क दिखाता न छोड़ा जाए।

दो स्वतंत्र क्लास WalletHost को कार्यान्वित करती हैं — src/connect/host.ts (मुख्य विंडो) और
src/connect/ConnectApp.tsx में एक इनलाइन होस्ट (पॉपअप)। इंटरफ़ेस में जोड़ी गई कोई भी चीज़
दोनों में कार्यान्वित होनी चाहिए, साथ ही tests/unit/connect-handler.test.ts में फ़िक्स्चर में भी।

सेशन प्रबंधन

Orion Wallet सेशन SDK द्वारा स्वचालित रूप से प्रबंधित होते हैं। सेशन इसके बाद समाप्त होते हैं:

  • निष्क्रिय टाइमआउट: 30 मिनट की निष्क्रियता
  • निरपेक्ष टाइमआउट: कनेक्शन से 8 घंटे

dApp किसी भी समय सेशन स्वास्थ्य जाँच सकता है:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

जब कोई सेशन समाप्त होता है, वॉलेट एक sessionExpired इवेंट एमिट करता है। dApp को
इस इवेंट को सुनना चाहिए और उपयोगकर्ता को पुनः कनेक्ट करने का संकेत देना चाहिए:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

सेशन रीस्टोर स्वचालित रूप से संभाला जाता है — वॉलेट सेशन संकेत को IndexedDB में
सुरक्षित रखता है, इसलिए समाप्ति के बाद पुनः कनेक्ट करने के लिए उपयोगकर्ता को अपना वॉलेट फिर से इंपोर्ट करने की ज़रूरत नहीं होती।

    वह फ़ाइलसिस्टम भरा हो — जो तब आसानी से होता है जब /tmp दूसरी प्रक्रियाओं के साथ साझा एक छोटा tmpfs हो —
    तो कॉन्टेक्स्ट लॉन्च पर मर जाते हैं और असंबंधित टेस्ट मिलीसेकंडों में विफल हो जाते हैं, या 30 सेकंड के टाइमआउट तक
    लटके रहते हैं। पहले df -h /tmp; किसी विशाल फ़ाइलसिस्टम पर TMPDIR=$HOME/.cache/e2e-tmp के साथ फिर से
    चलाएँ और वही स्पेक टाइमआउट होने से ~4 सेकंड में पास होने तक पहुँच जाते हैं।
  • Memory. प्रति वर्कर लगभग 2 GB खाली मेमोरी। जब यह समाप्त हो जाती है तो Chromium टेस्ट के बीच
    मार दिया जाता है और Playwright Target crashed रिपोर्ट करता है; --workers=1 के साथ फिर से चलाएँ।

रिलीज़ चेकलिस्ट

  1. npm run autofix — पूरी तरह हरा होना चाहिए
  2. किसी ताज़ा npm run build के विरुद्ध npm run test:e2e
  3. npm audit --omit=dev — प्रोडक्शन को शून्य कमज़ोरियाँ रिपोर्ट करनी चाहिए
  4. पुष्टि करें कि PVAC किसी प्रोडक्शन प्रीव्यू (npm run preview) में लोड होता है, केवल dev में नहीं
  5. मौजूदा वॉलेट डेटा के साथ किसी pre-rebrand बिल्ड से माइग्रेशन पथ का परीक्षण करें
  6. पुष्टि करें कि vite.config.ts सर्वर हेडर अब भी vercel.json से मेल खाते हैं
