nlohmann::json-এর কী অর্ডারিং ও ফরম্যাটিং হুবহু পুনরুৎপাদন করে। স্বাক্ষর এই
বাইটগুলোর উপর গণনা করা হয়, তাই যেকোনো বিচ্যুতি এমন একটি স্বাক্ষর তৈরি করে যা নেটওয়ার্ক প্রত্যাখ্যান করে। এই
সিরিয়ালাইজারটি "পরিপাটি" করার চেষ্টা করবেন না।

নামকরণ: পণ্য বনাম প্রোটোকল। "Orion Wallet" হলো পণ্য। octra_* RPC মেথড,
oct অ্যাড্রেস প্রিফিক্স, OCT টিকার, এবং "Octra Network" হলো প্রোটোকল শনাক্তকারী
এবং কখনও এগুলোর নাম পরিবর্তন করা যাবে না।

বিল্ড সিস্টেম

TypeScript কনফিগ ফাইলগুলো সত্যের একক উৎস:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
এগুলোর জন্য .js সহোদর ফাইল যোগ করবেন না। Vite vite.config.ts-এর আগে
vite.config.js রিজলভ করে, তাই একটি পুরনো ট্রান্সপাইল করা কপি নিঃশব্দে আসল কনফিগকে ছায়া দেয় এবং .ts
ফাইলে করা সম্পাদনা কিছুই করে না। ওই তিনটি ফাইলনেম .gitignore-এ আছে।
eslint.config.js হলো প্রকৃত ফ্ল্যাট কনফিগ এবং ইচ্ছাকৃতভাবে রাখা হয়েছে।

কেবল এগুলো ইগনোর করাই যথেষ্ট ছিল না, কারণ কোনো কিছুই এগুলো তৈরি হওয়া থেকে থামায়নি:
tsconfig.node.json একটি composite প্রোজেক্ট, যা ডিক্লারেশন এমিট বাধ্যতামূলক করে, এবং কোনো
outDir না থাকায় যেকোনো tsc -b সরাসরি সোর্সের পাশে vite.config.js লিখত। এটি দুবার ঘটেছে।
ওই প্রোজেক্টের এমিট এখন node_modules/.tmp/tsconfig-node/-এ যায়, যেখানে এটি কিছুই ছায়া দিতে পারে না।
আপনি ওই প্রোজেক্টে কোনো কনফিগ ফাইল যোগ করলে, outDir-কে অপরিবর্তিত রাখুন।

এনভায়রনমেন্ট ফ্ল্যাগ

ফ্ল্যাগপ্রভাব
VITE_ALLOW_HTTP_ENDPOINTS=1বিল্ড টাইমে connect-src CSP নির্দেশিকায় http: যুক্ত করে, যাতে একটি সেল্ফ-হোস্টেড বিল্ড একটি plain-http RPC নোডে পৌঁছাতে পারে। প্রতি-অরিজিন ব্যবহারকারীর সম্মতি তখনও প্রযোজ্য — src/wallet/endpoint-policy.ts দেখুন

কেবল বিল্ড টাইমে সেট করা হয়। এটি vite.config.ts-এ allowHttpEndpointsCsp প্লাগইন দ্বারা পড়া হয়
এবং index.html পুনর্লিখন করে; এর কোনো রানটাইম প্রভাব নেই, কারণ ডকুমেন্ট পার্স হয়ে গেলে একটি
মেটা-ট্যাগ CSP আর প্রসারিত করা যায় না।

হেডার

COOP/COEP same-origin / require-corp-এ সেট করা আছে (ভবিষ্যতের WASM থ্রেডিংয়ের জন্য সংরক্ষিত),
/connect-এ unsafe-none ওভাররাইডসহ, যাতে পপআপের postMessage + MessagePort
ট্রান্সফার কাজ করে। ডেভ হেডার vite.config.ts-এ থাকে; প্রোডাকশন হেডার vercel.json-এ।
দুটোকে সিঙ্কে রাখুন।

Content-Security-Policy

index.html-এ সংজ্ঞায়িত। script-src-এ অবশ্যই 'wasm-unsafe-eval' থাকতে হবে — Chromium এটি ছাড়া
WebAssembly.instantiate() প্রত্যাখ্যান করে, যা ঠিক সেই কারণ যা PVAC মডিউলকে নিঃশব্দে লোড হতে ব্যর্থ করেছিল। ওই নির্দেশিকা কেবল WebAssembly কম্পাইলেশন অনুমোদন করে; এটি
JavaScript eval() পুনরায় সক্রিয় করে না।

connect-src হলো 'self' https: প্লাস লুপব্যাক (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*) যাতে একটি স্থানীয়ভাবে চালানো নোড সাধারণভাবে প্লেইনটেক্সট না খুলেই কাজ করে। http://-এর মাধ্যমে অন্য
যেকোনো কিছু src/wallet/endpoint-policy.ts দ্বারা নিয়ন্ত্রিত, যা একমাত্র জায়গা যেটি
সিদ্ধান্ত নেয় — URL প্লাস একটি সুস্পষ্ট কনটেক্সটের একটি বিশুদ্ধ ফাংশন, তাই স্টোর, Settings UI
এবং টেস্টগুলো দ্বিমত করতে পারে না। অন্য কোথাও অ্যাড-হক URL চেক যোগ করবেন না। তিনটি স্বাধীন
ব্লকার প্রযোজ্য (মিক্সড কন্টেন্ট → CSP → ব্যবহারকারীর সম্মতি) এবং রায়টি সবচেয়ে
মৌলিকটি প্রথমে জানায়, তাই ব্রাউজার যখন প্রত্যাখ্যান করছে তখন ব্যবহারকারীকে কখনও অ্যালোলিস্ট ঠিক করতে বলা হয় না।

PVAC WASM পাইপলাইন

বিল্ড করা

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py আবশ্যক, কারণ হার্ডওয়্যার AES (AES-NI বা ARM ক্রিপ্টো এক্সটেনশন) ছাড়া PVAC
কঠোরভাবে #error করে, আর WebAssembly তা অফার করে না। প্যাচটি একটি পোর্টেবল
সফটওয়্যার ইমপ্লিমেন্টেশন যোগ করে যা বিট-অভিন্ন কিন্তু প্রায় ৫–১০× ধীর। এটি অ্যাডিটিভ:
হার্ডওয়্যার পাথগুলো অপরিবর্তিত থাকে, এবং একটি ব্যাকআপ .hpp.bak লেখা হয়।

লোড করা

src/pvac/wasm-bridge.ts মডিউলটি তিনটি ধাপে লোড করে:

  1. Probe — গ্লু URL-এ HEAD পাঠানো হয়, যাতে "not built" (404) কে "blocked by CSP" থেকে আলাদা করা যায়। এটি ছাড়া দুটোই একই অস্বচ্ছ ইমপোর্ট ব্যর্থতা হিসেবে ধরা পড়ে।
  2. Import — /* @vite-ignore */সহ একটি পরম URL-এর ডায়নামিক import()। এটি অবশ্যই পরম হতে হবে: একটি নগ্ন স্পেসিফায়ার রিজলভ করতে ব্যর্থ হয়, আর ./wasm/pvac.js /assets/-এর সাপেক্ষে রিজলভ হয়ে 404 দেয়।
  3. Verify — ব্রিজটি স্যুইচ করার আগে নিশ্চিত করুন যে প্রয়োজনীয় 13টি _pvac_* এক্সপোর্ট সবই বিদ্যমান।

আগের বিল্ডগুলো সিরিয়ালাইজেশন ফাংশনগুলো বাদ দিয়েছিল, যা এনক্রিপ্ট/ডিক্রিপ্ট এমনভাবে ভেঙেছিল
যে নোডটি এটি শুধু "malformed transaction" হিসেবে রিপোর্ট করেছিল।

ব্যর্থতাগুলো PvacFailureReason হিসেবে শ্রেণীবদ্ধ করা হয়: not-built, csp-blocked,
missing-exports, init-failed, unknown। প্রতিটি Settings-এ দেখানো একটি কংক্রিট প্রতিকারের সাথে ম্যাপ করা হয়।
সিঙ্গেলটন প্রমিসটি ব্যর্থতায় রিসেট করা হয়, যাতে ↻ Reload PVAC একটি ক্যাশ করা প্রত্যাখ্যান
পুনরায় চালানোর পরিবর্তে আবার চেষ্টা করতে পারে।

মেমোরি নিয়ম

C API হলো ম্যানুয়াল-মেমোরি। প্রতিটি _malloc-এর একটি _free প্রয়োজন; প্রতিটি serialize_* একটি
বাফার ফেরত দেয় যা _pvac_free_bytes দিয়ে মুক্ত করতে হয়। keygen/enc_* থেকে পাওয়া হ্যান্ডেলগুলোর
নিজ নিজ _pvac_free_* প্রয়োজন। try/finally ব্যবহার করুন — প্যাটার্নটির জন্য WasmPvacBridge দেখুন।

স্টেট ম্যানেজমেন্ট

Zustand, src/store/wallet-store.ts-এ। এটি ওয়ালেট, RPC ক্লায়েন্ট, সেটিংস, PVAC
স্ট্যাটাস, টোস্ট এবং গ্লোবাল লোডিং ফ্ল্যাগের মালিক।

গ্লোবাল লোডিং ফ্ল্যাগটি (isLoading) একটি ফুল-স্ক্রিন ব্লার ওভারলে চালায় এবং এটি
শুধুমাত্র পুরো-অ্যাপ ট্রানজিশনের জন্য সংরক্ষিত, যেমন ওয়ালেট আনলক। প্যানেল-নির্দিষ্ট কাজের জন্য
পরিবর্তে usePanelLoading ব্যবহার করতে হবে — নিচে দেখুন।

ফাঁকা হয়ে যায়, এবং সেই ফলব্যাকটি রেন্ডার হয় — ফলে একটি সাদা ফাঁকা পেজ তৈরি হয় যা চিরকাল লোডিং-এ
আটকে থাকা বলে মনে হয়। বাউন্ডারিটি শেলকে জীবিত রাখে এবং একটি পুনরায়-চেষ্টাযোগ্য এরর কার্ড দেখায়।

পরিণতি: রেন্ডারের সময় ডাকা ফাংশনগুলো অবশ্যই ত্রুটিপূর্ণ ইনপুটে থ্রো করবে না।
src/tx/builder.ts-এর formatAmount unknown গ্রহণ করে এবং একটি প্লেসহোল্ডারে অবনমিত হয়,
কারণ RPC রেসপন্স বা লোকাল tx ক্যাশ — কোনোটিই স্কিমা-যাচাই করা হয় না। রেন্ডার করার আগে
অবিশ্বস্ত সারিগুলোকে নরমালাইজ করুন — HistoryView প্যাটার্নটি দেখায়।

লোডিং স্টেট

প্যানেল-স্কোপড কাজের জন্য usePanelLoading (src/hooks/usePanelLoading.ts) ব্যবহার করুন:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

তারপর <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} /> রেন্ডার করুন।

দুটি বৈশিষ্ট্য গুরুত্বপূর্ণ: মোডালটি খারিজযোগ্য (কাজটি ব্যাকগ্রাউন্ডে চলতে থাকে, তাই একটি
ধীর নেটওয়ার্ক কখনও ব্যবহারকারীকে আটকে রাখে না), এবং স্টেট লেখা isMounted()-এ গেট করা থাকে, যাতে
কাজ চলাকালীন অন্যত্র নেভিগেট করলে স্ক্রিনে একটি মোডাল আটকে থাকতে না পারে।

স্টোরেজ ও মাইগ্রেশন

idb-এর মাধ্যমে IndexedDB, ডেটাবেস orion-wallet, ভার্সন 6। স্টোরগুলো src/wallet/storage.ts-এর
OBJECT_STORES অ্যারেতে একবার ডিক্লেয়ার করা হয়; সেখানে নতুন স্টোর যোগ করুন, যাতে তৈরি ও
মাইগ্রেশন সামঞ্জস্যপূর্ণ থাকে — সেই অ্যারেটিই wipeEverything()-কেও চালায়, তাই অন্য কোথাও
যোগ করা একটি স্টোর ওয়াইপের পরেও টিকে থাকবে।

মাইগ্রেশনগুলো কেবল অ্যাডিটিভ: DB_VERSION বাড়ান, অ্যারেতে যোগ করুন, এবং নতুন এন্ট্রিগুলোর পাশে
কমেন্টে ভার্সনটি লিখে রাখুন। বিদ্যমান স্টোর কখনও পুনঃনামকরণ বা বাদ দেওয়া হয় না।
এ পর্যন্ত ভার্সনগুলো: v2 SDK স্টোর, v3 OCS01 টোকেন, v4 oct:// বুকমার্ক, v5
unlock-session-keys, v6 contacts + passkey-unlock।

রিব্র্যান্ড মাইগ্রেশন

ডেটাবেসটির নাম webcli-react থেকে বদলালে প্রতিটি বিদ্যমান ওয়ালেট এতিম হয়ে যেত, যেহেতু
IndexedDB ডেটাকে ডেটাবেসের নাম দিয়ে সুযোগ দেয়। migrateLegacyDatabase প্রথম চালুতে
সব স্টোর সামনের দিকে কপি করে। এটি:

  • আইডেমপোটেন্ট — টার্গেটে যেকোনো ওয়ালেট থাকলে এটি এড়িয়ে যায়
  • অ-ধ্বংসাত্মক — লিগ্যাসি ডেটাবেস রোলব্যাকের জন্য অক্ষত রাখা হয়
  • অ-মারাত্মক — ব্যর্থতা লগ করা হয়, কখনও থ্রো করা হয় না; একটি মাইগ্রেশন বাগ যেন স্টার্টআপ আটকে না দেয়

মনে রাখবেন, E2E হেল্পারদের clearIndexedDB-কে দুটি ডেটাবেসই মুছতে হবে, নইলে
মাইগ্রেশন লিগ্যাসি ডেটা সোজাসুজি ফিরিয়ে আনে এবং "পরিষ্কার অবস্থা" আসলে পরিষ্কার থাকে না।

সংযোগের লাইফসাইকেল

হ্যান্ডশেক (প্রতি সেশনে একবার):

  1. dApp provider.connect() কল করে → PopupTransport /connect?v=1&rid=…&origin=… খোলে
  2. ওয়ালেট ConnectApp রেন্ডার করে, প্রয়োজন হলে ব্যবহারকারী আনলক করে
  3. ওয়ালেট window.postMessage-এর মাধ্যমে hello + MessagePort পাঠায়, অরিজিন-যাচাই করা হয়
  4. dApp পোর্টের উপর challenge প্রতিধ্বনিত করে (অ্যান্টি-রিপ্লে)
  5. ConnectHandler ack যাচাই করে, CONNECT RPC পরিবেশন করে → অ্যাড্রেস, অ্যাকাউন্ট ও নেটওয়ার্ক ফেরত দেয়

সংযোগের পরে:

  • পপআপ বন্ধ হতে পারে, কিন্তু MessagePort খোলা থাকে — এটি উইন্ডো থেকে স্বাধীন
  • সেশনটি IndexedDB-তে (sdk-sessions) আইডল + অ্যাবসোলিউট TTL-সহ স্থায়ী হয়
  • রিড মেথডগুলো (getBalance, getAccounts) সেশন-নীরব
  • সই করার মেথডগুলো সর্বদা একটি নতুন অনুমোদন প্রম্পট খোলে

"সংযোগ কাজ করে, কিন্তু আর কিছুই কাজ করে না"-এর সমাধান:

মূলত PopupTransport.isConnected() popup.closed পরীক্ষা করত, তাই অনুমোদন উইন্ডো বন্ধ হওয়ার পর
প্রতিটি কল "Transport is not connected" দিয়ে ব্যর্থ হতো। এখন এটি কেবল পোর্টটি পরীক্ষা করে,
যা পপআপের চেয়ে দীর্ঘজীবী। অনুমোদনের পর ওয়ালেট পপআপটি বন্ধ করে দেয়, কিন্তু সংযোগটি সচল থাকে।

অনুমতি মডেল

সংযোগ-সময়: কেবল রিড-অনলি স্কোপ (viewAccounts, viewBalance, viewNetwork)।

সই করার স্কোপ (signMessage, signContract, ইত্যাদি) প্রথম সফল অনুমোদনে
অলসভাবে মঞ্জুর করা হয়। ফিক্সের আগে, এগুলো DEFAULT_PERMISSIONS-এ অনুপস্থিত ছিল এবং
প্রম্পটটি দেখা দেওয়ার আগেই ডিসপ্যাচার UNAUTHORIZED দিয়ে প্রতিটি সই কল প্রত্যাখ্যান করত —
উপসর্গটির দ্বিতীয় মূল কারণ।

এখন:

  • অনুমতি পরীক্ষা মঞ্জুর-না-করা সই স্কোপগুলোকে অনুমোদন প্রম্পটে যেতে দেয়
  • অনুমোদনে, grantPermission স্কোপটি সেশনে স্থায়ী করে
  • পরবর্তী কলগুলো অনুমতি পরীক্ষা এড়িয়ে যায় কিন্তু তখনও অনুমোদন প্রয়োজন — একটি স্কোপ
    মঞ্জুর করা শুধু রেকর্ড করে যে ব্যবহারকারী সম্মত যে dApp জিজ্ঞাসা করতে পারে

প্রত্যাহার সুস্পষ্ট: revokePermission স্কোপটি permissions থেকে সরিয়ে deniedPermissions-এ
রেকর্ড করে, যেটি ডিসপ্যাচার সরাসরি প্রত্যাখ্যান করে।

নিরাপত্তা ইনভ্যারিয়েন্ট

এগুলো দুর্বল করবেন না:

  • প্রতিটি ইনবাউন্ড postMessage-এ অরিজিন যাচাই (PopupTransport.ts, rpc-handler.ts)
  • অ্যান্টি-রিপ্লে: CSPRNG চ্যালেঞ্জ + dApp ননস + প্রতি-সেশন মনোটোনিক ননস। makeId কেবল
    বার্তা কোরিলেশনের জন্য এবং এটিকে কখনও একটি নিরাপত্তা মান হিসেবে ব্যবহার করা যাবে না
  • অনুমতিগুলো প্রতি-অরিজিন, sdk-sessions-এ স্থায়ী, এবং স্পষ্টভাবে মঞ্জুর/প্রত্যাহার করা হয়
  • MessagePort স্বাধীনতা: পোর্টটি পপআপের চেয়ে দীর্ঘজীবী। একবার ট্রান্সফার করা হলে, ওয়ালেট
    সংযোগ না ভেঙেই অনুমোদন উইন্ডোটি বন্ধ করতে পারে
  • নিষিদ্ধ মেথডগুলো ক্লায়েন্ট-সাইডে (WalletProvider) এবং ওয়ালেট-সাইডে
    (rpc-handler) উভয় জায়গাতেই প্রত্যাখ্যান করা হয়, তাই নিম্ন-স্তরের request()
    এস্কেপ হ্যাচ দিয়েও লেনদেন নির্বাহ কখনও SDK-তে পালাতে পারে না
  • localStorage-এ কেবল একটি সেশন-পুনরুদ্ধার ইঙ্গিত থাকে (অ্যাড্রেস, নেটওয়ার্ক) — কখনও সিক্রেট নয়

সেশন ম্যানেজমেন্ট

Orion সেশন 30 মিনিট নিষ্ক্রিয়তায় বা 8 ঘণ্টা অ্যাবসোলিউটে মেয়াদ শেষ হয়। SDK অন্তর্নির্মিত
সেশন স্বাস্থ্য পরীক্ষা এবং অটো-রিকানেক্ট সরবরাহ করে:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

নেটওয়ার্ক, ব্যবহারকারীর নিজেরসহ

একজন ব্যবহারকারী Settings → Network-এ নিজের নেটওয়ার্ক যোগ করতে পারেন (নিজের নোড, একটি devnet ফর্ক, একটি
পেইড RPC)। সেই নেটওয়ার্কগুলো প্রথম-শ্রেণির: প্রিসেটগুলোর পাশাপাশি কানেক্ট পপআপের সিলেক্টরে এগুলো দেখা যায়,
এবং একটি সংযুক্ত dApp সেগুলো দেখতে পায়।

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

কোনো কিছুর উপর নির্ভর করার আগে customNetworks ক্যাপাবিলিটিতে ফিচার-ডিটেক্ট করুন — পুরনো
ওয়ালেট বিল্ডগুলো কেবল নগ্ন wallet_getNetwork-এর উত্তর দেয়, যা একটি আইডি স্ট্রিং ফেরত দেয়।

NetworkInfo ইচ্ছাকৃতভাবে কোনো rpcUrl বা relayerUrl বহন করে না। ব্যবহারকারী-যোগ করা
নেটওয়ার্ক প্রায়ই একটি প্রাইভেট এন্ডপয়েন্ট — একটি LAN অ্যাড্রেস, একটি টানেল, একটি প্রোভাইডার URL যাতে
কোয়েরি স্ট্রিংয়ে API কী থাকে — এবং এটি ব্যবহারকারী যে প্রতিটি সাইটে সংযোগ করে তাকে দিলে
তাদের ইনফ্রাস্ট্রাকচার লিক হয়ে যাবে। একটি dApp-এর এটি দরকার নেই: প্রতিটি রিড ওয়ালেটের মাধ্যমেই যায়
(wallet_getBalance ও অন্যান্য) এবং নির্বাহ কখনও ওয়ালেট UI ছেড়ে যায় না। তারের উপর দিয়ে
যা যায় তা-ই একটি dApp-এর বৈধভাবে প্রয়োজন — এটি কোন নেটওয়ার্কের সাথে কথা বলছে, মালিক এটি হাতে
যোগ করেছে কি না (custom), এবং একটি লেনদেন কোথায় লিঙ্ক করতে হবে (explorerUrl)।

কোনো wallet_switchNetwork নেই। স্যুইচিং ওয়ালেটের নিজস্ব UI-তেই থাকে — পপআপের
সিলেক্টর বা মূল উইন্ডোর network pill — এই নিয়মের সাথে সামঞ্জস্যপূর্ণ যে স্টেট পরিবর্তন কখনও
dApp থেকে উদ্ভূত হয় না। যে dApp-এর অন্য নেটওয়ার্ক প্রয়োজন সে ব্যবহারকারীকে স্যুইচ করতে বলে, তারপর
networkChanged-এর জন্য অপেক্ষা করে।

networkChanged দুটি জায়গা থেকেই নির্গত হয় যেখানে স্যুইচ ঘটতে পারে: কানেক্ট পপআপ এবং
মূল উইন্ডো। পপআপ বন্ধ হলে সেশনগুলো মূল উইন্ডোতে হ্যান্ড অফ করা হয়, তাই বেশিরভাগ ব্যবহারকারী
network pill স্পর্শ করার সময় পপআপ অনেক আগেই চলে যায় — Layout.tsx গৃহীত হ্যান্ডলারদের কাছে নির্গত করে
যাতে একটি সংযুক্ত dApp একটি পুরনো নেটওয়ার্ক দেখিয়ে আটকে না থাকে।

দুটি স্বাধীন ক্লাস WalletHost বাস্তবায়ন করে — src/connect/host.ts (মূল উইন্ডো) এবং
src/connect/ConnectApp.tsx-এ একটি ইনলাইন হোস্ট (পপআপ)। ইন্টারফেসে যোগ করা যেকোনো কিছু
দুটোতেই বাস্তবায়ন করতে হবে, পাশাপাশি tests/unit/connect-handler.test.ts-এর ফিক্সচারেও।

সেশন ম্যানেজমেন্ট

Orion Wallet সেশনগুলো SDK দ্বারা স্বয়ংক্রিয়ভাবে পরিচালিত হয়। সেশনগুলো মেয়াদ শেষ হয়:

  • নিষ্ক্রিয় টাইমআউট: 30 মিনিটের নিষ্ক্রিয়তা
  • পরম টাইমআউট: সংযোগ থেকে 8 ঘণ্টা

dApp যেকোনো সময় সেশন স্বাস্থ্য পরীক্ষা করতে পারে:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

যখন একটি সেশনের মেয়াদ শেষ হয়, ওয়ালেট একটি sessionExpired ইভেন্ট নির্গত করে। dApp-এর
এই ইভেন্টটি শোনা উচিত এবং ব্যবহারকারীকে পুনরায় সংযোগ করতে বলা উচিত:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

সেশন পুনরুদ্ধার স্বয়ংক্রিয়ভাবে পরিচালিত হয় — ওয়ালেট সেশন ইঙ্গিতটি
IndexedDB-তে সংরক্ষণ করে, তাই মেয়াদ শেষ হওয়ার পর পুনরায় সংযোগ করলে ব্যবহারকারীকে তাদের ওয়ালেট
পুনরায় ইমপোর্ট করতে হয় না।

E2E নোট: Playwright ব্যর্থতার একটি দেয়ালে বিশ্বাস করার আগে, ডিফ নয়, মেশিনটি পরীক্ষা করুন।
দুটি পরিবেশগত সীমাবদ্ধতা এমন ব্যর্থতা তৈরি করে যা দেখতে হুবহু আসল রিগ্রেশনের মতো:

  • টেম্প স্পেস। Chromium প্রতিটি ব্রাউজার প্রোফাইল TMPDIR-এর অধীনে রাখে (ডিফল্টে /tmp)। যদি
    সেই ফাইলসিস্টেমটি পূর্ণ থাকে — সহজেই ঘটে যখন /tmp একটি ছোট tmpfs হয় যা অন্যান্য প্রসেসের সাথে ভাগ করা —
    কনটেক্সটগুলো চালু হওয়ার সময়ই মারা যায় এবং সম্পর্কহীন টেস্টগুলো মিলিসেকেন্ডে ব্যর্থ হয়, বা 30 সেকেন্ডের
    টাইমআউটে ঝুলে যায়। আগে df -h /tmp চালান; একটি প্রশস্ত ফাইলসিস্টেমে TMPDIR=$HOME/.cache/e2e-tmp দিয়ে
    পুনরায় চালান এবং একই স্পেকগুলো টাইমআউট হওয়া থেকে ~4 সেকেন্ডে পাস করার দিকে চলে যায়।
  • মেমোরি। প্রতি ওয়ার্কারে প্রায় 2 GB ফ্রি মেমোরি। এটি ফুরিয়ে গেলে Chromium টেস্টের মাঝপথে
    নিহত হয় এবং Playwright Target crashed রিপোর্ট করে; --workers=1 দিয়ে পুনরায় চালান।

playwright.config.ts reuseExistingServer: !isCI সেট করে, তাই পোর্ট 4173-এ একটি অবশিষ্ট npm run preview
নিঃশব্দে পুনরায় ব্যবহৃত হয় — একটি ভিন্ন চেকআউট থেকে শুরু করা থাকলেও। দুইটি ট্রি তুলনা করার সময়,
রানগুলোর মধ্যে লিসনারটি বন্ধ করুন (ss -lptn | grep 4173), নইলে দ্বিতীয় রান প্রথমটির বিল্ড পরীক্ষা করবে।

একটি বাগ ঠিক করার সময়, শুধু ফিক্স নয়, ব্যর্থতার ধরনটি নথিভুক্ত করে এমন একটি টেস্ট যোগ করুন।
tests/unit/history-view.test.ts এবং error-boundary.test.tsx এটি অনুসরণ করে: প্রতিটি সেই উপসর্গের নাম দেয়
যা এটি পুনরাবৃত্তি হতে বাধা দেয়।

রিলিজ চেকলিস্ট

  1. npm run autofix — অবশ্যই সম্পূর্ণ সবুজ হতে হবে
  2. একটি নতুন npm run build-এর বিরুদ্ধে npm run test:e2e
  3. npm audit --omit=dev — প্রোডাকশনে শূন্য দুর্বলতা রিপোর্ট করতে হবে
  4. PVAC একটি প্রোডাকশন প্রিভিউতে (npm run preview) লোড হয় কি না যাচাই করুন, শুধু ডেভে নয়
  5. বিদ্যমান ওয়ালেট ডেটাসহ একটি প্রি-রিব্র্যান্ড বিল্ড থেকে মাইগ্রেশন পথটি পরীক্ষা করুন
  6. নিশ্চিত করুন vite.config.ts সার্ভার হেডার এখনও vercel.json-এর সাথে মিলে যায়
