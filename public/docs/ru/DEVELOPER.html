Настройка

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps обязателен: ESLint 9 и @eslint/js 10 объявляют конфликтующие диапазоны
зависимостей (peer). vercel.json использует тот же флаг, так что CI и локальные установки совпадают.

Рекомендуется Node 20+.

Проектные ограничения

Канонический JSON должен быть побайтово точным. src/tx/canonical-json.ts воспроизводит
порядок ключей и форматирование nlohmann::json в точности. Подписи вычисляются по этим
байтам, поэтому любое отклонение порождает подпись, которую сеть отвергает. Не «наводите порядок» в этом
сериализаторе.

Именование: продукт против протокола. «Orion Wallet» — это продукт. RPC-методы octra_*,
префикс адреса oct, тикер OCT и «Octra Network» — это идентификаторы протокола,
которые никогда не должны переименовываться.

Система сборки

Файлы конфигурации TypeScript — это единственный источник истины:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
Не добавляйте .js-двойники для них. Vite разрешает vite.config.js раньше
vite.config.ts, так что устаревшая транспилированная копия молча затеняет настоящую конфигурацию, и правки
в файле .ts ничего не делают. Эти три имени файлов внесены в .gitignore.
eslint.config.js — это подлинный flat config, и он оставлен намеренно.

Игнорирования их самого по себе было недостаточно, потому что ничто не мешало им создаваться:
tsconfig.node.json — это composite-проект, который принудительно генерирует декларации, и без
outDir любой tsc -b писал vite.config.js прямо рядом с исходником. Это случалось дважды.
Генерация для этого проекта теперь идёт в node_modules/.tmp/tsconfig-node/, где она не может ничего
затенить. Если вы добавляете файл конфигурации в этот проект, не трогайте outDir.

Заголовки

COOP/COEP установлены в same-origin / require-corp (зарезервировано для будущей многопоточности WASM),
с переопределениями unsafe-none на /connect, чтобы работала передача postMessage + MessagePort
из всплывающего окна. Dev-заголовки находятся в vite.config.ts; production-заголовки — в vercel.json.
Держите оба в синхронизации.

Content-Security-Policy

Определяется в index.html. script-src должен включать 'wasm-unsafe-eval' — Chromium отказывает
WebAssembly.instantiate() без него, что как раз и заставляло модуль PVAC незаметно не
загружаться. Эта директива разрешает только компиляцию WebAssembly; она не включает заново
JavaScript eval().

connect-src — это 'self' https: плюс loopback (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*), так что локально запущенный узел работает без открытия открытого текста в целом. Всё
остальное по http:// контролируется src/wallet/endpoint-policy.ts, единственным местом, которое
решает — чистая функция от URL плюс явный контекст, так что хранилище, UI Settings
и тесты не могут расходиться. Не добавляйте разрозненные проверки URL в других местах. Применяются три независимых
блокировщика (смешанное содержимое → CSP → согласие пользователя), и вердикт сообщает о самом
фундаментальном первым, так что пользователю никогда не говорят исправить список разрешений, когда отказывает именно
браузер.

Конвейер PVAC WASM

Сборка

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py необходим, потому что PVAC жёстко выдаёт #error без аппаратного AES (AES-NI или
криптографических расширений ARM), которых WebAssembly не предоставляет. Патч добавляет портативную
программную реализацию, которая побитово идентична, но примерно в 5–10× медленнее. Он аддитивен:
аппаратные пути не затрагиваются, и записывается резервная копия .hpp.bak.

Загрузка

src/pvac/wasm-bridge.ts загружает модуль в три шага:

  1. Probe — HEAD-запрос по URL связующего кода, так что «not built» (404) отличимо от «blocked by CSP». Без этого оба проявляются как одинаковый непрозрачный сбой импорта.
  2. Import — динамический import() абсолютного URL с /* @vite-ignore */. Он должен быть абсолютным: голый спецификатор не разрешается, а ./wasm/pvac.js разрешается относительно /assets/ и даёт 404.
  3. Verify — проверить, что все 13 требуемых экспортов _pvac_* существуют, прежде чем подставлять мост. Более ранние сборки пропускали функции сериализации, что ломало шифрование/расшифровку так, что узел сообщал об этом лишь как о «malformed transaction».

Сбои классифицируются как PvacFailureReason: not-built, csp-blocked,
missing-exports, init-failed, unknown. Каждый сопоставляется с конкретным средством устранения, показанным в
Settings. Singleton-промис сбрасывается при сбое, так что ↻ Reload PVAC может повторить попытку, а не
воспроизводить закэшированный отказ.

Правила работы с памятью

C API управляет памятью вручную. Каждому _malloc нужен _free; каждый serialize_* возвращает
буфер, который должен быть освобождён с помощью _pvac_free_bytes. Дескрипторам из keygen/enc_* нужны
их соответствующие _pvac_free_*. Используйте try/finally — см. WasmPvacBridge для образца.

Управление состоянием

Zustand, в src/store/wallet-store.ts. Он владеет кошельком, RPC-клиентом, настройками, статусом
PVAC, тостами и глобальным флагом загрузки.

Глобальный флаг загрузки (isLoading) управляет полноэкранным размытым оверлеем и зарезервирован для
переходов только в масштабе всего приложения, таких как разблокировка кошелька. Работа в рамках панели должна вместо этого использовать
usePanelLoading — см. ниже.

Обработка ошибок

src/components/ErrorBoundary.tsx оборачивает каждую панель в Layout.tsx, с ключом по активной
вкладке, так что сработавшая граница сбрасывается при навигации, плюс одна граница в корне в main.tsx.

Это важнее, чем кажется. index.html содержит:

#root:empty::before { content: 'Loading Orion Wallet…'; }

Без границы любой выброс во время рендеринга заставляет React 18 размонтировать всё дерево, #root
становится пустым, и рендерится этот запасной вариант — создавая пустую белую страницу, которая кажется зависшей
на загрузке навсегда. Граница сохраняет оболочку живой и показывает карточку ошибки с возможностью повтора.

Следствие: функции, вызываемые во время рендеринга, не должны выбрасывать исключения на некорректном вводе.
formatAmount в src/tx/builder.ts принимает unknown и деградирует до заполнителя,
потому что ни ответы RPC, ни локальный кэш транзакций не валидируются по схеме. Нормализуйте
недоверенные строки перед их рендерингом — HistoryView показывает этот шаблон.

Состояния загрузки

Используйте usePanelLoading (src/hooks/usePanelLoading.ts) для работы в пределах панели:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

Затем отрендерите <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />.

Важны два свойства: модальное окно можно закрыть (работа продолжается в фоне, поэтому
медленная сеть никогда не запирает пользователя), а запись состояния защищена условием isMounted(), так что
уход со страницы в процессе не может оставить модальное окно застрявшим на экране.

Хранилище и миграции

IndexedDB через idb, база данных orion-wallet, версия 6. Хранилища объявляются один раз в
массиве OBJECT_STORES в src/wallet/storage.ts; добавляйте новые именно туда, чтобы создание и
миграция оставались согласованными — этот массив также управляет wipeEverything(), поэтому хранилище, добавленное
где-либо ещё, пережило бы полную очистку.

Миграции только аддитивные: увеличьте DB_VERSION, добавьте запись в массив и укажите
версию в комментарии рядом с новыми записями. Существующие хранилища никогда не переименовываются и не удаляются.
Версии на данный момент: v2 хранилища SDK, v3 токены OCS01, v4 закладки oct://, v5
unlock-session-keys, v6 contacts + passkey-unlock.

Миграция при ребрендинге

Переименование базы данных с webcli-react осиротило бы каждый существующий кошелёк, поскольку
IndexedDB разграничивает данные по имени базы. migrateLegacyDatabase при первом запуске копирует
все хранилища вперёд. Она:

  • идемпотентна — пропускается, как только в целевой базе появляется хоть один кошелёк
  • неразрушающа — устаревшая база остаётся нетронутой для отката
  • нефатальна — сбои логируются, но никогда не выбрасываются; ошибка миграции не должна блокировать запуск

Помните, что clearIndexedDB в помощниках E2E должен удалять обе базы данных, иначе
миграция скопирует устаревшие данные обратно и «чистое состояние» окажется нечистым.

Жизненный цикл подключения

Рукопожатие (один раз за сессию):

  1. dApp вызывает provider.connect() → PopupTransport открывает /connect?v=1&rid=…&origin=…
  2. Кошелёк рендерит ConnectApp, пользователь при необходимости разблокирует его
  3. Кошелёк отправляет hello + MessagePort через window.postMessage, с проверкой источника
  4. dApp отражает challenge обратно через порт (защита от повторов)
  5. ConnectHandler проверяет подтверждение, обслуживает RPC CONNECT → возвращает адрес, аккаунты, сеть

После подключения:

  • всплывающее окно может закрыться, но MessagePort остаётся открытым — он независим от окна
  • Сессия сохраняется в IndexedDB (sdk-sessions) с TTL по простою и абсолютным TTL
  • Методы чтения (getBalance, getAccounts) не требуют взаимодействия в рамках сессии
  • Методы подписи всегда открывают новый запрос одобрения

Исправление проблемы «подключение работает, а больше ничего не работает»:

Изначально PopupTransport.isConnected() проверял popup.closed, поэтому каждый вызов после того, как
окно одобрения закрывалось, завершался ошибкой «Transport is not connected». Теперь он проверяет только
порт, который переживает всплывающее окно. Кошелёк закрывает окно после одобрения, но
соединение остаётся живым.

Модель разрешений

На момент подключения: только области только для чтения (viewAccounts, viewBalance, viewNetwork).

Области подписи (signMessage, signContract и т. д.) предоставляются лениво при первом
успешном одобрении. До исправления они отсутствовали в DEFAULT_PERMISSIONS, и
диспетчер отклонял каждый вызов подписи с UNAUTHORIZED ещё до того, как мог появиться запрос —
вторая первопричина этого симптома.

Теперь:

  • Проверка разрешений позволяет непредоставленным областям подписи дойти до запроса одобрения
  • При одобрении grantPermission сохраняет область в сессии
  • Последующие вызовы пропускают проверку разрешений, но всё равно требуют одобрения — предоставление области лишь фиксирует, что пользователь согласен, чтобы dApp мог спрашивать

Отзыв явный: revokePermission удаляет область из permissions и записывает
её в deniedPermissions, которые диспетчер отклоняет напрямую.

Инварианты безопасности

Не ослабляйте их:

  • Проверка источника при каждом входящем postMessage (PopupTransport.ts, rpc-handler.ts)
  • Защита от повторов: challenge на основе CSPRNG + nonce от dApp + монотонный nonce на сессию. makeId предназначен только для корреляции сообщений и никогда не должен использоваться как значение для безопасности
  • Разрешения задаются для каждого источника, сохраняются в sdk-sessions и предоставляются/отзываются явно
  • Независимость MessagePort: порт переживает всплывающее окно. После передачи кошелёк может закрыть окно одобрения, не разрывая соединение
  • Запрещённые методы отклоняются как на стороне клиента (WalletProvider), так и на стороне кошелька (rpc-handler), поэтому выполнение транзакций никогда не может ускользнуть в SDK даже через низкоуровневую лазейку request()
  • localStorage хранит только подсказку для восстановления сессии (адрес, сеть) — никогда не секреты

Интеграция dApp

Быстрый старт

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

Управление сессиями

Сессии Orion истекают после 30 минут простоя или 8 часов в абсолютном выражении. SDK предоставляет
встроенные проверки состояния сессии и автоматическое переподключение:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

Сети, включая собственные сети пользователя

Пользователь может добавить свою собственную сеть в Settings → Network (собственный узел, форк devnet,
платный RPC). Эти сети полноправны: они появляются в селекторе всплывающего окна подключения
наряду с предустановленными, и подключённый dApp может их видеть.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

Определяйте поддержку возможности customNetworks, прежде чем полагаться на что-либо из этого — старые
сборки кошелька отвечают только на голый wallet_getNetwork, который возвращает строку-идентификатор.

NetworkInfo намеренно не несёт ни rpcUrl, ни relayerUrl. Добавленная
пользователем сеть часто является приватной точкой доступа — адресом в локальной сети, туннелем, URL провайдера с
API-ключом в строке запроса — и передача этого каждому сайту, к которому подключается пользователь,
раскрыла бы его инфраструктуру. dApp это не нужно: каждое чтение проходит через кошелёк
(wallet_getBalance и подобные), а выполнение никогда не покидает интерфейс кошелька. По проводу
передаётся то, что dApp законно необходимо — с какой сетью он общается, добавил ли
владелец её вручную (custom) и куда ссылаться для транзакции (explorerUrl).

Метода wallet_switchNetwork нет. Переключение остаётся в собственном интерфейсе кошелька — в селекторе
всплывающего окна или в «пилюле» сети главного окна — в соответствии с правилом, что изменения состояния
никогда не исходят от dApp. dApp, которому нужна другая сеть, просит пользователя переключиться, а затем
ждёт networkChanged.

networkChanged генерируется из обоих мест, где может произойти переключение: из всплывающего окна подключения и
из главного окна. Сессии передаются главному окну при закрытии всплывающего окна, поэтому к
моменту, когда большинство пользователей касаются «пилюли» сети, всплывающего окна уже давно нет — Layout.tsx генерирует событие для
перенятых обработчиков, чтобы подключённый dApp не остался с устаревшей сетью.

Интерфейс WalletHost реализуют два независимых класса — src/connect/host.ts (главное окно) и
встроенный хост в src/connect/ConnectApp.tsx (всплывающее окно). Всё, что добавляется в интерфейс, должно быть
реализовано в обоих, плюс в фикстуре в tests/unit/connect-handler.test.ts.

Запрещённые методы

SDK блокирует эти методы локально, прежде чем они достигнут транспорта. Кошелёк также
перепроверяет их на стороне сервера, поэтому выполнение транзакций никогда не может ускользнуть:

  • wallet_sendTransaction / sendTransaction
  • wallet_broadcastTransaction / broadcastTransaction
  • wallet_transfer / transfer
  • wallet_swap / swap
  • wallet_bridge / bridge

Управление сессиями

Сессии Orion Wallet управляются автоматически с помощью SDK. Сессии истекают после:

  • Тайм-аут простоя: 30 минут бездействия
  • Абсолютный тайм-аут: 8 часов с момента подключения

dApp может проверить состояние сессии в любой момент:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

Когда сессия истекает, кошелёк генерирует событие sessionExpired. dApp должен
слушать это событие и предлагать пользователю переподключиться:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

Восстановление сессии происходит автоматически — кошелёк сохраняет подсказку сессии в
IndexedDB, поэтому переподключение после истечения не требует от пользователя повторного импорта кошелька.

Тестирование

npm run autofix          # typecheck → format → lint --fix → test → build

Модульные тесты выполняются под jsdom с fake-indexeddb. Тесты компонентов используют
renderToStaticMarkup, а не библиотеку тестирования DOM — см.
tests/unit/processing-modal.test.tsx.

У WebAuthn нет реализации в jsdom, поэтому tests/unit/passkey.test.ts устанавливает
FakeAuthenticator, который моделирует расширение PRF (включая аутентификатор, у которого его нет,
отклонённый запрос и заменённый секрет). Он проверяет, чего именно сохранённая запись не должна содержать — свойство, которое действительно важно.

Замечание об E2E: прежде чем поверить в стену сбоев Playwright, проверьте машину, а не диф.
Два ограничения окружения порождают сбои, которые выглядят в точности как настоящие регрессии:

  • Место во временной папке. Chromium размещает профиль каждого браузера в TMPDIR (/tmp по умолчанию). Если эта файловая система переполнена — что легко, когда /tmp — это небольшой tmpfs, разделяемый с другими процессами, — контексты умирают при запуске, и несвязанные тесты падают за миллисекунды или зависают до 30-секундного тайм-аута. Сначала выполните df -h /tmp; перезапустите с TMPDIR=$HOME/.cache/e2e-tmp на просторной файловой системе, и те же спецификации из зависающих превращаются в проходящие за ~4 с.
  • Память. Примерно 2 ГБ свободной памяти на воркер. Когда она заканчивается, Chromium убивается посреди теста, и Playwright сообщает Target crashed; перезапустите с --workers=1.

playwright.config.ts задаёт reuseExistingServer: !isCI, поэтому оставшийся npm run preview на
порту 4173 молча переиспользуется — в том числе запущенный из другого checkout. При
сравнении двух деревьев убивайте слушатель между запусками (ss -lptn | grep 4173), иначе второй
запуск тестирует сборку первого.

Исправляя баг, добавьте тест, который документирует режим сбоя, а не только исправление.
tests/unit/history-view.test.ts и error-boundary.test.tsx следуют этому: каждый называет
симптом, повторение которого он предотвращает.

Чек-лист релиза

  1. npm run autofix — должен быть полностью зелёным
  2. npm run test:e2e на свежей сборке npm run build
  3. npm audit --omit=dev — в продакшене должно быть ноль уязвимостей
  4. Убедитесь, что PVAC загружается в продакшен-превью (npm run preview), а не только в dev
  5. Проверьте путь миграции со сборки до ребрендинга с существующими данными кошелька
  6. Убедитесь, что серверные заголовки в vite.config.ts всё ещё совпадают с vercel.json

Известные проблемы

Уведомления о dev-зависимостях. npm audit сообщает об уязвимостях в vitest, vite, esbuild
и связанных пакетах. Каждое оставшееся исправление требует мажорного обновления (vite 5→8, vitest 2→4).
Это только инструменты сборки, и они не поставляются пользователям; аудит продакшена чист. См.
SECURITY.html.

Предупреждение о разбиении storage.ts на чанки. Сборка предупреждает, что storage.ts импортируется и статически, и
динамически, поэтому его нельзя выделить в отдельный чанк. Это безвредно, но означает,
что динамические импорты в HistoryView и WalletExportImport не дают выгоды от
разбиения кода.

Производительность программного AES. Запасной вариант AES на WASM в 5–10× медленнее нативного. Тяжёлые операции PVAC
блокируют основной поток; перенос их в Web Worker — логичный следующий шаг.
