கட்டமைப்பு

முழுவதும் கிளையன்ட்-பக்கமே; பின்தளம் இல்லை. தரவு ஒரு திசையில் பாய்கிறது:

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

வடிவமைப்பு கட்டுப்பாடுகள்

Canonical JSON பைட்-எக்ஸாக்டாக இருக்க வேண்டும். src/tx/canonical-json.ts
nlohmann::json சாவி வரிசைமுறை மற்றும் வடிவமைப்பைச் சரியாக மீண்டும் உருவாக்குகிறது. கையொப்பங்கள் இந்த
பைட்டுகளின் மீது கணக்கிடப்படுகின்றன, எனவே எந்த விலகலும் நெட்வொர்க் நிராகரிக்கும் ஒரு கையொப்பத்தை உருவாக்குகிறது. இந்த
சீரியலைசரை "சுத்தப்படுத்த" வேண்டாம்.

பெயரிடல்: தயாரிப்பு எதிராக நெறிமுறை. "Orion Wallet" என்பது தயாரிப்பு. octra_* RPC முறைகள்,
oct முகவரி முன்னொட்டு, OCT டிக்கர் மற்றும் "Octra Network" ஆகியவை நெறிமுறை அடையாளங்காட்டிகள்,
அவை ஒருபோதும் மறுபெயரிடப்படக்கூடாது.

பில்ட் அமைப்பு

TypeScript கட்டமைப்பு கோப்புகளே ஒரே உண்மை மூலமாகும்:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
இவற்றுக்கு .js உடன்பிறப்புகளைச் சேர்க்க வேண்டாம். Vite vite.config.ts-க்கு முன்னால்
vite.config.js-ஐத் தீர்க்கிறது, எனவே ஒரு பழைய மொழிபெயர்க்கப்பட்ட நகல் உண்மையான கட்டமைப்பை அமைதியாக மறைத்து,
.ts கோப்புக்கான திருத்தங்கள் எதையும் செய்யாது. அந்த மூன்று கோப்புப்பெயர்களும் .gitignore-இல் உள்ளன.
eslint.config.js உண்மையான flat config, அது வேண்டுமென்றே வைக்கப்பட்டுள்ளது.

அவற்றைப் புறக்கணிப்பது மட்டும் போதாது, ஏனெனில் அவை உருவாக்கப்படுவதைத் தடுக்க எதுவும் இல்லை:
tsconfig.node.json ஒரு composite திட்டம், இது declaration emit-ஐ கட்டாயப்படுத்துகிறது, மேலும்
outDir இல்லாமல் எந்த tsc -b உம் vite.config.js-ஐ மூலத்தின் அருகிலேயே எழுதியது. அது இருமுறை நடந்தது.
அந்தத் திட்டத்திற்கான emit இப்போது node_modules/.tmp/tsconfig-node/-க்குச் செல்கிறது, அங்கு அது எதையும் மறைக்க முடியாது.
அந்தத் திட்டத்தில் ஒரு கட்டமைப்பு கோப்பைச் சேர்த்தால், outDir-ஐ மாற்றாமல் விடுங்கள்.

சூழல் கொடிகள்

கொடிவிளைவு
VITE_ALLOW_HTTP_ENDPOINTS=1பில்ட் நேரத்தில் CSP directive connect-src-இல் http:-ஐச் சேர்க்கிறது, எனவே சுய-ஹோஸ்ட் செய்யப்பட்ட பில்ட் ஒரு வெற்று-http RPC நோட்களை அடைய முடியும். ஒவ்வொரு-origin பயனர் ஒப்புதல் இன்னும் பொருந்தும் — src/wallet/endpoint-policy.ts-ஐப் பார்க்கவும்

பில்ட் நேரத்தில் மட்டுமே அமைக்கப்படுகிறது. இது vite.config.ts-இல் allowHttpEndpointsCsp plugin-ஆல்
படிக்கப்பட்டு index.html-ஐ மீண்டும் எழுதுகிறது; இதற்கு இயக்க நேர விளைவு இல்லை, ஏனெனில் ஒரு meta-tag CSP-ஐ
ஆவணம் பாகுபடுத்தப்பட்டவுடன் விரிவுபடுத்த முடியாது.

ஹெடர்கள்

COOP/COEP same-origin / require-corp என அமைக்கப்பட்டுள்ளன (எதிர்கால WASM threadingக்காக ஒதுக்கப்பட்டவை),
/connect-இல் unsafe-none மேலடுக்குகளுடன், பாப்அப்பின் postMessage + MessagePort
பரிமாற்றம் வேலை செய்ய. Dev ஹெடர்கள் vite.config.ts-இல் வாழ்கின்றன; production ஹெடர்கள் vercel.json-இல்.
இரண்டையும் ஒத்திசைவில் வைத்திருங்கள்.

Content-Security-Policy

index.html-இல் வரையறுக்கப்பட்டுள்ளது. script-src 'wasm-unsafe-eval'-ஐச் சேர்க்க வேண்டும் — Chromium
அது இல்லாமல் WebAssembly.instantiate()-ஐ மறுக்கிறது, இதுவே PVAC தொகுதி அமைதியாக ஏற்றப்படத் தோல்வியடையச் செய்தது.
அந்த directive WebAssembly தொகுப்பை மட்டுமே அனுமதிக்கிறது; அது JavaScript eval()-ஐ மீண்டும் இயக்காது.

connect-src 'self' https: கூடுதலாக loopback (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*) என உள்ளது, எனவே உள்ளூரில் இயங்கும் நோட் பொதுவாக ப்ளைன்டெக்ஸ்டைத் திறக்காமல் வேலை செய்கிறது. http://-ல்
வேறு எதுவும் src/wallet/endpoint-policy.ts-ஆல் கட்டுப்படுத்தப்படுகிறது, அதுவே முடிவெடுக்கும் ஒரே இடம் — URL-இன்
கூடுதலாக ஒரு வெளிப்படையான சூழலின் தூய செயல்பாடு, எனவே ஸ்டோர், Settings UI
மற்றும் சோதனைகள் மாறுபட முடியாது. வேறு இடங்களில் ad-hoc URL சோதனைகளைச் சேர்க்க வேண்டாம். மூன்று சுயாதீன
தடுப்பான்கள் பொருந்தும் (மிக்ஸ்டு கண்டென்ட் → CSP → பயனர் ஒப்புதல்), மேலும் தீர்ப்பு மிக அடிப்படையானதை
முதலில் அறிக்கை செய்கிறது, எனவே உலாவியே மறுக்கும்போது அனுமதிப் பட்டியலைச் சரிசெய்ய நீங்கள் ஒருபோதும் கூறப்படமாட்டீர்கள்.

PVAC WASM பைப்லைன்

பில்ட் செய்தல்

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py தேவை, ஏனெனில் PVAC வன்பொருள் AES (AES-NI அல்லது
ARM crypto நீட்டிப்புகள்) இல்லாமல் கடினமாக #error-ஐ எழுப்புகிறது, WebAssembly அதை வழங்காது. பேட்ச் ஒரு சிறிய
மென்பொருள் செயலாக்கத்தைச் சேர்க்கிறது, அது பிட்-ஒத்ததாக ஆனால் தோராயமாக 5–10× மெதுவானது. இது கூட்டல்: வன்பொருள்
பாதைகள் தொடப்படாமல் உள்ளன, மேலும் ஒரு காப்பு .hpp.bak எழுதப்படுகிறது.

ஏற்றுதல்

src/pvac/wasm-bridge.ts தொகுதியை மூன்று படிகளில் ஏற்றுகிறது:

  1. Probe — glue URL-இல் HEAD, எனவே "கட்டப்படவில்லை" (404) என்பது "CSP-ஆல் தடுக்கப்பட்டது" என்பதிலிருந்து வேறுபடுத்தக்கூடியது. இது இல்லாமல் இரண்டும் ஒரே மாதிரியான ஒளிபுகா இறக்குமதி தோல்வியாக மேற்பரப்பில் வரும்.
  2. Import — /* @vite-ignore */ உடன் ஒரு முழுமையான URL-இன் டைனமிக் import(). அது முழுமையானதாக
    இருக்க வேண்டும்: ஒரு வெற்று specifier தீர்க்கத் தோல்வியடைகிறது, மேலும் ./wasm/pvac.js /assets/-க்கு எதிராக
    தீர்க்கப்பட்டு 404 ஆகிறது.
  3. Verify — பாலத்தை மாற்றுவதற்கு முன் தேவையான அனைத்து 13 _pvac_* ஏற்றுமதிகளும் இருப்பதை உறுதிப்படுத்தவும். முந்தைய பில்ட்கள்
    சீரியலைசேஷன் செயல்பாடுகளை விடுபடச் செய்தன, இது நோட் "malformed transaction" என்று மட்டுமே அறிவிக்கும் வகையில்
    encrypt/decrypt-ஐ உடைத்தது.

தோல்விகள் PvacFailureReason ஆக வகைப்படுத்தப்படுகின்றன: not-built, csp-blocked,
missing-exports, init-failed, unknown. ஒவ்வொன்றும் Settings-இல் காட்டப்படும் ஒரு உறுதியான
தீர்வுக்கு வரைபடமாகிறது. singleton promise தோல்வியில் மீட்டமைக்கப்படுகிறது, எனவே ↻ Reload PVAC
சேமிக்கப்பட்ட நிராகரிப்பை மீண்டும் இயக்காமல் மீண்டும் முயற்சிக்க முடியும்.

try/finally-ஐப் பயன்படுத்தவும் — முறைக்கு WasmPvacBridge-ஐப் பார்க்கவும்.

நிலை, toasts மற்றும் உலகளாவிய ஏற்றுதல் கொடியை வைத்துள்ளது.

usePanelLoading-ஐப் பயன்படுத்த வேண்டும் — கீழே காண்க.

இது தோன்றுவதை விட முக்கியமானது. index.html கொண்டுள்ளது:

#root:empty::before { content: 'Loading Orion Wallet…'; }

ஒரு எல்லை இல்லாமல், எந்த render-time throw உம் React 18 முழு மரத்தையும் பிரிக்கச் செய்யும், #root
காலியாகிறது, அந்த வீழ்ச்சி வழி காட்டப்படுகிறது — எப்போதும் ஏற்றப்படுவது போல் தோன்றும் ஒரு வெற்று வெள்ளை பக்கத்தை உருவாக்குகிறது.
எல்லை ஷெல்லை உயிருடன் வைத்து ஒரு மீண்டும் முயற்சிக்கக்கூடிய பிழை அட்டையைக் காட்டுகிறது.

விளைவு: render-இன் போது அழைக்கப்படும் செயல்பாடுகள் தவறான உள்ளீட்டில் throw செய்யக்கூடாது.

ஏற்றுதல் நிலைகள்

பேனல்-வரம்பு வேலைக்கு usePanelLoading-ஐ (src/hooks/usePanelLoading.ts) பயன்படுத்தவும்:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

பிறகு <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />-ஐ render செய்யவும்.

இரண்டு பண்புகள் முக்கியம்: மாடல் நிராகரிக்கக்கூடியது (வேலை பின்னணியில் தொடர்கிறது, எனவே ஒரு
மெதுவான நெட்வொர்க் ஒருபோதும் பயனரைச் சிக்க வைக்காது), மேலும் state எழுத்துக்கள் isMounted() மீது கட்டுப்படுத்தப்படுகின்றன, எனவே
நடுவில் வழிசெலுத்துவது ஒரு மாடலைத் திரையில் சிக்க வைக்க முடியாது.

ரீபிராண்ட் இடம்பெயர்வு

database-ஐ webcli-react-லிருந்து மறுபெயரிடுவது ஒவ்வொரு ஏற்கனவே உள்ள வாலட்டையும் அனாதையாக்கியிருக்கும், ஏனெனில்
IndexedDB தரவை database பெயரால் வரம்பிடுகிறது. migrateLegacyDatabase முதல்
துவக்கத்தில் அனைத்து ஸ்டோர்களையும் முன்னோக்கி நகலெடுக்கிறது. அது:

  • idempotent — இலக்கில் ஏதேனும் வாலட் இருந்தவுடன் தவிர்க்கப்படும்
  • அழிவில்லாதது — பழைய database rollbackக்காக அப்படியே விடப்படுகிறது
  • ஆபத்தற்றது — தோல்விகள் பதிவு செய்யப்படுகின்றன, ஒருபோதும் throw செய்யப்படுவதில்லை; ஒரு இடம்பெயர்வு பிழை துவக்கத்தைத் தடுக்கக்கூடாது

E2E உதவியாளர்களில் clearIndexedDB இரண்டு database-களையும் நீக்க வேண்டும் என்பதை நினைவில் கொள்ளுங்கள், இல்லையெனில்
இடம்பெயர்வு பழைய தரவை நேராக மீண்டும் நகலெடுக்கும், "சுத்தமான நிலை" சுத்தமாக இருக்காது.

இணைப்பு வாழ்க்கைச் சுழற்சி

கைகுலுக்கல் (ஒரு செஷனுக்கு ஒருமுறை):

  1. dApp provider.connect()-ஐ அழைக்கிறது → PopupTransport /connect?v=1&rid=…&origin=…-ஐத் திறக்கிறது
  2. வாலட் ConnectApp-ஐ render செய்கிறது, தேவைப்பட்டால் பயனர் திறக்கிறார்
  3. வாலட் hello + MessagePort-ஐ window.postMessage மூலம் அனுப்புகிறது, origin-சரிபார்க்கப்பட்டது
  4. dApp port-இல் challenge-ஐ எதிரொலிக்கிறது (anti-replay)
  5. ConnectHandler ack-ஐ சரிபார்த்து, CONNECT RPC-ஐ வழங்குகிறது → முகவரி, கணக்குகள், நெட்வொர்க்கைத் தருகிறது

இணைப்பிற்குப் பிறகு:

  • பாப்அப் மூடப்படலாம், ஆனால் MessagePort திறந்தே இருக்கும் — அது சாளரத்திலிருந்து சுயாதீனமானது
  • செஷன் IndexedDB-இல் (sdk-sessions) செயலற்ற + முழுமையான TTL உடன் நீடிக்கிறது
  • படிப்பு முறைகள் (getBalance, getAccounts) செஷன்-அமைதியானவை
  • கையொப்ப முறைகள் எப்போதும் ஒரு புதிய ஒப்புதல் அறிவிப்பைத் திறக்கின்றன

"இணைப்பு வேலை செய்கிறது, மற்றதெல்லாம் இல்லை" என்பதற்கான திருத்தம்:

முதலில் PopupTransport.isConnected() popup.closed-ஐச் சரிபார்த்தது, எனவே ஒப்புதல்
சாளரம் மூடப்பட்ட பிறகு ஒவ்வொரு அழைப்பும் "Transport is not connected" என்று தோல்வியடைந்தது. இப்போது அது port-ஐ மட்டுமே சரிபார்க்கிறது,
அது பாப்அப்பை விட நீடிக்கிறது. ஒப்புதலுக்குப் பிறகு வாலட் பாப்அப்பை மூடுகிறது, ஆனால்
இணைப்பு உயிருடன் இருக்கிறது.

அனுமதி மாதிரி

இணைப்பு-நேரம்: படிக்க-மட்டும் நோக்கங்கள் மட்டுமே (viewAccounts, viewBalance, viewNetwork).

கையொப்ப நோக்கங்கள் (signMessage, signContract, போன்றவை) முதல்
வெற்றிகரமான ஒப்புதலில் சோம்பேறித்தனமாக வழங்கப்படுகின்றன. திருத்தத்திற்கு முன், அவை DEFAULT_PERMISSIONS-இல் இல்லை, மேலும்
டிஸ்பாட்சர் ஒவ்வொரு கையொப்ப அழைப்பையும் அறிவிப்பு தோன்றுவதற்கு முன்பே UNAUTHORIZED உடன் நிராகரித்தது —
அறிகுறியின் இரண்டாவது மூல காரணம்.

இப்போது:

  • அனுமதி சரிபார்ப்பு வழங்கப்படாத கையொப்ப நோக்கங்கள் ஒப்புதல் அறிவிப்புக்குச் செல்ல அனுமதிக்கிறது
  • ஒப்புதலில், grantPermission நோக்கத்தை செஷனில் நிரந்தரமாக்குகிறது
  • அடுத்தடுத்த அழைப்புகள் அனுமதி சரிபார்ப்பைத் தவிர்க்கின்றன, ஆனால் இன்னும் ஒப்புதல் தேவை — ஒரு நோக்கத்தை வழங்குவது
    dApp கேட்கலாம் என்பதைப் பயனர் ஒப்புக்கொள்கிறார் என்பதை மட்டுமே பதிவு செய்கிறது

நிராகரித்தல் வெளிப்படையானது: revokePermission நோக்கத்தை permissions-இலிருந்து நீக்கி அதை
deniedPermissions-இல் பதிவு செய்கிறது, அதை டிஸ்பாட்சர் நேரடியாக மறுக்கிறது.

பாதுகாப்பு மாறாத விதிகள்

இவற்றைப் பலவீனப்படுத்த வேண்டாம்:

  • Origin சரிபார்ப்பு ஒவ்வொரு உள்வரும் postMessage-இலும் (PopupTransport.ts, rpc-handler.ts)
  • Anti-replay: CSPRNG சேலஞ்ச் + dApp nonce + ஒவ்வொரு-செஷன் மோனோடோனிக் nonce. makeId செய்தி தொடர்புக்கு மட்டுமே, பாதுகாப்பு மதிப்பாக ஒருபோதும் பயன்படுத்தப்படக்கூடாது
  • அனுமதிகள் ஒவ்வொரு-origin, sdk-sessions-இல் நிரந்தரமானவை, வெளிப்படையாக வழங்கப்பட்டு/நிராகரிக்கப்படுகின்றன
  • MessagePort சுயாட்சி: port பாப்அப்பை விட நீடிக்கிறது. மாற்றப்பட்டவுடன், வாலட்
    இணைப்பை உடைக்காமல் ஒப்புதல் சாளரத்தை மூட முடியும்
  • தடைசெய்யப்பட்ட முறைகள் கிளையன்ட்-பக்க (WalletProvider) மற்றும் வாலட்-பக்க
    (rpc-handler) இரண்டிலும் நிராகரிக்கப்படுகின்றன, எனவே பரிவர்த்தனை செயல்படுத்தல் குறைந்த-நிலை request()
    தப்பிக்கும் வழி வழியாகவும் SDK-க்குத் தப்ப முடியாது
  • localStorage ஒரு செஷன்-மீட்டெடுப்பு குறிப்பை (முகவரி, நெட்வொர்க்) மட்டுமே வைத்திருக்கிறது — ரகசியங்களை ஒருபோதும் இல்லை

dApp ஒருங்கிணைப்பு

விரைவுத் துவக்கம்

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',

    'approveContract',
    'signContract',

const result = await provider.connect();

செஷன் மேலாண்மை

Orion செஷன்கள் 30 நிமிட செயலற்ற தன்மை அல்லது 8 மணி நேர முழுமையான பிறகு காலாவதியாகின்றன. SDK உள்ளமைக்கப்பட்ட
செஷன் சுகாதார சோதனைகள் மற்றும் தானியங்கி-மறு இணைப்பை வழங்குகிறது:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

நெட்வொர்க்குகள், பயனரின் சொந்தம் உட்பட

ஒரு பயனர் Settings → Network-இல் தனது சொந்த நெட்வொர்க்கைச் சேர்க்கலாம் (தனது சொந்த நோட், ஒரு devnet fork, ஒரு
கட்டண RPC). அந்த நெட்வொர்க்குகள் முதல்-வகுப்பு: அவை இணைப்பு பாப்அப்பின் தேர்வியில்
முன்னமைவுகளுடன் தோன்றும், மேலும் இணைக்கப்பட்ட dApp அவற்றைப் பார்க்க முடியும்.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

எதையாவது நம்புவதற்கு முன் customNetworks திறனில் feature-detect செய்யவும் — பழைய
வாலட் பில்ட்கள் வெற்று wallet_getNetwork-க்கு மட்டுமே பதிலளிக்கின்றன, அது ஒரு id சரத்தைத் தருகிறது.

NetworkInfo வேண்டுமென்றே rpcUrl-ஐயும் relayerUrl-ஐயும் எடுத்துச் செல்வதில்லை. பயனர் சேர்த்த
நெட்வொர்க் அடிக்கடி ஒரு தனிப்பட்ட முனையாகும் — ஒரு LAN முகவரி, ஒரு டனல், query string-இல்
API key உள்ள ஒரு வழங்குநர் URL — மேலும் அதைப் பயனர் இணைக்கும் ஒவ்வொரு தளத்திற்கும் கொடுப்பது
அவர்களின் உள்கட்டமைப்பைக் கசியவிடும். ஒரு dApp அதைத் தேவைப்படுத்தாது: ஒவ்வொரு வாசிப்பும் வாலட் வழியாகச் செல்கிறது
(wallet_getBalance மற்றும் நண்பர்கள்) மேலும் செயல்படுத்தல் வாலட் UI-ஐ விட்டு ஒருபோதும் வெளியேறாது. கம்பி வழியாகக்
கடப்பது ஒரு dApp நியாயமாகத் தேவைப்படுவதே — எந்த நெட்வொர்க்குடன் பேசுகிறது, உரிமையாளர் அதைக் கையால் சேர்த்தாரா (custom),
மற்றும் ஒரு பரிவர்த்தனையை இணைக்க எங்கே (explorerUrl).

wallet_switchNetwork இல்லை. மாற்றுவது வாலட்டின் சொந்த UI-இல் தான் இருக்கும் — பாப்அப்பின்
தேர்வி அல்லது பிரதான சாளரத்தின் network pill — நிலை மாற்றங்கள் ஒருபோதும் dApp-இலிருந்து உருவாகாது என்ற விதியுடன் ஒத்துப்போகிறது. வேறு
நெட்வொர்க் தேவைப்படும் ஒரு dApp பயனரை மாற்றச் சொல்லி, பிறகு networkChanged-க்காகக் காத்திருக்கிறது.

networkChanged ஒரு மாற்றம் நடக்கக்கூடிய இரண்டு இடங்களிலிருந்தும் வெளியிடப்படுகிறது: இணைப்பு பாப்அப் மற்றும்
பிரதான சாளரம். பாப்அப் மூடப்படும்போது செஷன்கள் பிரதான சாளரத்திடம் ஒப்படைக்கப்படுகின்றன, எனவே பெரும்பாலான பயனர்கள்
network pill-ஐத் தொடும் நேரத்தில் பாப்அப் நீண்ட காலத்திற்கு முன்பே போய்விட்டது — Layout.tsx
தத்தெடுக்கப்பட்ட ஹேண்ட்லர்களுக்கு வெளியிடுகிறது, எனவே இணைக்கப்பட்ட dApp பழைய நெட்வொர்க்கைக் காட்டாமல் இருக்கிறது.

இரண்டு சுயாதீன வகுப்புகள் WalletHost-ஐச் செயல்படுத்துகின்றன — src/connect/host.ts (பிரதான சாளரம்) மற்றும் ஒரு
inline host src/connect/ConnectApp.tsx-இல் (பாப்அப்). இடைமுகத்தில் சேர்க்கப்படும் எதுவும்
இரண்டிலும் செயல்படுத்தப்பட வேண்டும், கூடுதலாக tests/unit/connect-handler.test.ts-இல் உள்ள fixture.

செஷன் மேலாண்மை

Orion Wallet செஷன்கள் SDK-ஆல் தானாக நிர்வகிக்கப்படுகின்றன. செஷன்கள் பிறகு காலாவதியாகின்றன:

  • செயலற்ற காலாவதி: 30 நிமிட செயலற்ற தன்மை
  • முழுமையான காலாவதி: இணைப்பிலிருந்து 8 மணி நேரம்

dApp எந்த நேரத்திலும் செஷன் சுகாதாரத்தைச் சரிபார்க்கலாம்:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

ஒரு செஷன் காலாவதியாகும்போது, வாலட் ஒரு sessionExpired நிகழ்வை வெளியிடுகிறது. dApp இந்த நிகழ்வைக்
கேட்டு பயனரை மீண்டும் இணைக்கும்படி கேட்க வேண்டும்:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

செஷன் மீட்டெடுப்பு தானாக கையாளப்படுகிறது — வாலட் IndexedDB-இல் செஷன் குறிப்பைப் பாதுகாக்கிறது,
எனவே காலாவதிக்குப் பிறகு மீண்டும் இணைவதற்கு பயனர் தனது வாலட்டை மீண்டும் இறக்குமதி செய்யத் தேவையில்லை.

E2E குறிப்பு: Playwright தோல்விகளின் ஒரு சுவரை நம்புவதற்கு முன், diff-ஐ அல்ல, இயந்திரத்தைச் சரிபார்க்கவும்.
இரண்டு சூழல் வரம்புகள் உண்மையான பின்னடைவுகளைப் போலவே இருக்கும் தோல்விகளை உருவாக்குகின்றன:

  • தற்காலிக இடம். Chromium ஒவ்வொரு உலாவி சுயவிவரத்தையும் TMPDIR-இன் கீழ் வைக்கிறது (/tmp இயல்பாக). அந்த
    கோப்பு முறைமை நிரம்பியிருந்தால் — /tmp மற்ற செயல்முறைகளுடன் பகிரப்பட்ட ஒரு சிறிய tmpfs ஆக இருக்கும்போது எளிதானது —
    சூழல்கள் துவக்கத்தில் இறந்து, தொடர்பில்லாத சோதனைகள் மில்லி விநாடிகளில் தோல்வியடைகின்றன, அல்லது 30 வி
    காலாவதிக்குத் தொங்குகின்றன. df -h /tmp முதலில்; ஒரு விசாலமான கோப்பு முறைமையில் TMPDIR=$HOME/.cache/e2e-tmp உடன் மீண்டும் இயக்கவும்,
    அதே specs ~4 வி-இல் காலாவதியிலிருந்து தேர்ச்சிக்குச் செல்லும்.
  • நினைவகம். ஒரு worker-க்கு தோராயமாக 2 GB கட்டற்ற நினைவகம். அது தீரும்போது Chromium
    சோதனை நடுவில் கொல்லப்படுகிறது, Playwright Target crashed-ஐ அறிக்கை செய்கிறது; --workers=1 உடன் மீண்டும் இயக்கவும்.

playwright.config.ts reuseExistingServer: !isCI-ஐ அமைக்கிறது, எனவே port 4173-இல் ஒரு எஞ்சிய npm run preview
அமைதியாக மீண்டும் பயன்படுத்தப்படுகிறது — வேறு checkout-இலிருந்து தொடங்கப்பட்டது உட்பட. இரண்டு
மரங்களை ஒப்பிடும்போது, இயக்கங்களுக்கு இடையில் கேட்பவரைக் கொல்லுங்கள் (ss -lptn | grep 4173), அல்லது இரண்டாவது
இயக்கம் முதல் இயக்கத்தின் பில்ட்டைச் சோதிக்கும்.

ஒரு பிழையைச் சரிசெய்யும்போது, திருத்தத்தை மட்டுமல்ல, தோல்வி முறையை ஆவணப்படுத்தும் ஒரு சோதனையைச் சேர்க்கவும்.
