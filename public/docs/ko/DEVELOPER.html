설정

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps는 필수입니다. ESLint 9와 @eslint/js 10이 충돌하는 peer
범위를 선언하기 때문입니다. vercel.json도 같은 플래그를 사용하므로 CI와 로컬 설치가 일치합니다.

Node 20+를 권장합니다.

아키텍처

순수 클라이언트 측이며 백엔드가 없습니다. 데이터는 한 방향으로 흐릅니다.

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

설계 제약 조건

표준 JSON은 바이트 단위로 정확해야 합니다. src/tx/canonical-json.ts는
nlohmann::json의 키 순서와 형식을 정확히 재현합니다. 서명은 이 바이트들에 대해 계산되므로,
조금만 어긋나도 네트워크가 거부하는 서명이 만들어집니다. 이 직렬화기를 "정리"하지 마십시오.

명명: 제품 대 프로토콜. "Orion Wallet"은 제품입니다. octra_* RPC 메서드,
oct 주소 접두사, OCT 티커, 그리고 "Octra Network"는 프로토콜 식별자이며
결코 이름을 바꾸어서는 안 됩니다.

빌드 시스템

TypeScript 구성 파일이 유일한 진실 공급원입니다.

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
이것들에 .js 형제 파일을 추가하지 마십시오. Vite는 vite.config.ts보다
vite.config.js를 먼저 해석하므로, 오래된 트랜스파일 사본이 실제 구성을 조용히 가리고
.ts 파일에 대한 편집이 아무 효과도 없게 됩니다. 그 세 파일 이름은 .gitignore에 있습니다.
eslint.config.js는 진짜 플랫 구성이며 의도적으로 유지됩니다.

무시하는 것만으로는 충분하지 않았습니다. 그것들이 생성되는 것을 막을 수 없었기 때문입니다.
tsconfig.node.json은 composite 프로젝트라 선언 내보내기를 강제하고, outDir이 없으면
어떤 tsc -b든 vite.config.js를 소스 바로 옆에 썼습니다. 두 번 그런 일이 있었습니다.
이제 해당 프로젝트의 내보내기는 node_modules/.tmp/tsconfig-node/로 가서 아무것도 가리지 못합니다.
그 프로젝트에 구성 파일을 추가한다면 outDir은 건드리지 마십시오.

환경 플래그

플래그효과
VITE_ALLOW_HTTP_ENDPOINTS=1빌드 시 http:를 connect-src CSP 지시문에 추가하여, 자체 호스팅 빌드가 일반 http RPC 노드에 도달할 수 있게 합니다. 출처별 사용자 동의는 여전히 적용됩니다 — src/wallet/endpoint-policy.ts 참조

빌드 시에만 설정됩니다. vite.config.ts에서 allowHttpEndpointsCsp 플러그인이 읽어
index.html을 다시 씁니다. 런타임 효과는 없습니다. meta-tag CSP는 문서가 파싱되면
더 넓힐 수 없기 때문입니다.

헤더

COOP/COEP는 same-origin / require-corp로 설정되어 있으며(향후 WASM 스레딩을 위해 예약),
/connect에는 unsafe-none 재정의가 있어 팝업의 postMessage + MessagePort
전송이 작동합니다. 개발 헤더는 vite.config.ts에, 운영 헤더는 vercel.json에 있습니다.
둘을 동기화 상태로 유지하십시오.

Content-Security-Policy

index.html에 정의되어 있습니다. script-src에는 'wasm-unsafe-eval'이 포함되어야 합니다.
없으면 Chromium이 WebAssembly.instantiate()를 거부하는데, 그것이 바로 PVAC 모듈을
조용히 로드 실패하게 만든 원인이었습니다. 그 지시문은 WebAssembly 컴파일만 허용하며
JavaScript eval()을 다시 활성화하지 않습니다.

connect-src는 'self' https:에 더해 루프백(http://localhost:*, http://127.0.0.1:*,
http://[::1]:*)을 포함하므로 일반 평문을 열지 않고도 로컬 실행 노드가 작동합니다.
http://를 통한 그 밖의 모든 것은 src/wallet/endpoint-policy.ts가 차단합니다. 이것이
결정하는 유일한 곳입니다 — URL과 명시적 컨텍스트의 순수 함수이므로 스토어, Settings UI,
테스트가 서로 다르게 말할 수 없습니다. 다른 곳에 임시 URL 검사를 추가하지 마십시오. 세 가지
독립적인 차단 요인(혼합 콘텐츠 → CSP → 사용자 동의)이 적용되며 판정은 가장 근본적인 것을
먼저 보고하므로, 거부하는 쪽이 브라우저일 때 사용자가 허용 목록을 고치라고 안내받지 않습니다.

PVAC WASM 파이프라인

빌드

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py가 필요한 이유는 PVAC가 하드웨어 AES(AES-NI 또는
ARM 암호화 확장)가 없으면 하드-#error를 내기 때문이며, WebAssembly는 이를 제공하지 않습니다.
이 패치가 이식 가능한 소프트웨어 구현을 추가하며, 비트 단위로 동일하지만 대략 5–10× 느립니다.
부가적입니다: 하드웨어 경로는 건드리지 않으며 백업 .hpp.bak이 작성됩니다.

로딩

src/pvac/wasm-bridge.ts는 모듈을 세 단계로 로드합니다:

  1. 탐색(Probe) — 글루 URL에 HEAD를 보내 "not built"(404)와 "blocked by CSP"를 구분합니다. 이것이 없으면 둘 다 동일한 불투명한 가져오기 실패로 드러납니다.
  2. 가져오기(Import) — /* @vite-ignore */가 있는 절대 URL의 동적 import(). 반드시 절대 URL이어야 합니다. 베어 지정자는 해석에 실패하며 ./wasm/pvac.js는 /assets/ 기준으로 해석되어 404가 됩니다.
  3. 검증(Verify) — 브리지를 교체하기 전에 필요한 13개 _pvac_* 내보내기가 모두 존재하는지 확인합니다. 초기 빌드는 직렬화 함수를 빠뜨려, 노드가 "malformed transaction"으로만 보고하는 방식으로 암호화/복호화를 깨뜨렸습니다.

실패는 PvacFailureReason으로 분류됩니다: not-built, csp-blocked,
missing-exports, init-failed, unknown. 각각은 Settings에 표시되는
구체적인 해결책에 매핑됩니다. 싱글턴 promise는 실패 시 재설정되므로 ↻ Reload PVAC이
캐시된 거부를 재생하는 대신 재시도할 수 있습니다.

메모리 규칙

C API는 수동 메모리 방식입니다. 모든 _malloc에는 _free가 필요하고, 모든 serialize_*는
_pvac_free_bytes로 해제해야 하는 버퍼를 반환합니다. keygen/enc_*의 핸들에는 그에 맞는
_pvac_free_*가 필요합니다. try/finally를 사용하십시오 — 패턴은 WasmPvacBridge를 참조하십시오.

오류 처리

src/components/ErrorBoundary.tsx는 Layout.tsx의 모든 패널을 활성 탭 키로 감싸서,
트리거된 경계가 내비게이션 시 재설정되게 하며, main.tsx의 루트에도 경계를 하나 둡니다.

이것은 보기보다 중요합니다. index.html은 다음을 포함합니다:

#root:empty::before { content: 'Loading Orion Wallet…'; }

경계가 없으면 렌더 중 발생하는 모든 throw가 React 18로 하여금 트리 전체를 마운트 해제하게 하고,
#root가 비워지며 그 폴백이 렌더링됩니다 — 영원히 로딩 중처럼 보이는 빈 흰 페이지가
만들어집니다. 경계는 셸을 살려 두고 재시도 가능한 오류 카드를 표시합니다.

결과: 렌더 중 호출되는 함수는 잘못된 입력에 대해 throw해서는 안 됩니다.
src/tx/builder.ts의 formatAmount는 unknown을 받아 플레이스홀더로 대체하는데,
RPC 응답이나 로컬 tx 캐시 모두 스키마 검증을 거치지 않기 때문입니다. 신뢰할 수 없는 행은
렌더링 전에 정규화하십시오 — HistoryView가 그 패턴을 보여줍니다.

로딩 상태

패널 범위 작업에는 usePanelLoading(src/hooks/usePanelLoading.ts)을 사용하십시오:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

그런 다음 <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />를 렌더링하십시오.

두 가지 속성이 중요합니다: 모달은 닫을 수 있으며(작업은 백그라운드에서 계속되므로
느린 네트워크가 사용자를 가두지 않습니다), 상태 쓰기는 isMounted()로 게이트되어
작업 중간에 다른 곳으로 이동해도 모달이 화면에 붙어 남지 않습니다.

저장소 및 마이그레이션

idb를 통한 IndexedDB, 데이터베이스 orion-wallet, 버전 6. 스토어는 src/wallet/storage.ts의
OBJECT_STORES 배열에 한 번만 선언됩니다; 새 스토어는 거기에 추가하여 생성과
마이그레이션이 일관되게 유지되게 하십시오 — 그 배열은 wipeEverything()도 구동하므로,
다른 곳에 추가된 스토어는 초기화에서 살아남게 됩니다.

마이그레이션은 추가 전용입니다: DB_VERSION을 올리고 배열에 항목을 덧붙이며,
새 항목 옆 주석에 버전을 기록하십시오. 기존 스토어는 절대 이름을 바꾸거나 제거하지 않습니다.
지금까지의 버전: v2 SDK 스토어, v3 OCS01 토큰, v4 oct:// 북마크, v5
unlock-session-keys, v6 contacts + passkey-unlock.

리브랜드 마이그레이션

데이터베이스 이름을 webcli-react에서 바꾸면 기존 지갑이 모두 고아가 되었을 것입니다.
IndexedDB는 데이터베이스 이름으로 데이터 범위를 정하기 때문입니다. migrateLegacyDatabase는
첫 실행 시 모든 스토어를 앞으로 복사합니다. 그 함수는:

  • 멱등적(idempotent) — 대상에 지갑이 하나라도 있으면 건너뜁니다
  • 비파괴적(non-destructive) — 롤백을 위해 레거시 데이터베이스를 그대로 둡니다
  • 비치명적(non-fatal) — 실패는 기록될 뿐 throw되지 않습니다; 마이그레이션 버그는 시작을 막아서는 안 됩니다

E2E 헬퍼의 clearIndexedDB는 두 데이터베이스를 모두 삭제해야 합니다. 그렇지 않으면
마이그레이션이 레거시 데이터를 곧바로 다시 복사해서 "clean state"가 깨끗하지 않게 됩니다.

연결 수명 주기

핸드셰이크(세션당 한 번):

  1. dApp이 provider.connect()를 호출하면 → PopupTransport가 /connect?v=1&rid=…&origin=…을 엽니다
  2. 지갑이 ConnectApp을 렌더링하고, 필요하면 사용자가 잠금을 해제합니다
  3. 지갑이 window.postMessage를 통해 hello + MessagePort를 보내며, 출처(origin)를 검증합니다
  4. dApp이 포트를 통해 challenge를 되돌려 보냅니다(재생 방지)
  5. ConnectHandler가 ack를 확인하고 CONNECT RPC를 처리합니다 → 주소, 계정, 네트워크를 반환합니다

연결 후:

  • 팝업은 닫힐 수 있지만 MessagePort는 열린 채로 유지됩니다 — 창과 독립적입니다
  • 세션은 유휴 + 절대 TTL과 함께 IndexedDB(sdk-sessions)에 유지됩니다
  • 읽기 메서드(getBalance, getAccounts)는 세션에서 조용히 처리됩니다
  • 서명 메서드는 항상 새 승인 프롬프트를 엽니다

"connect는 되는데 그 외에는 아무것도 안 되는" 문제의 해결책:

원래 PopupTransport.isConnected()는 popup.closed를 검사했기 때문에, 승인 창이 닫힌
후의 모든 호출은 "Transport is not connected"로 실패했습니다. 이제는 팝업보다 오래 사는
포트만 검사합니다. 지갑은 승인 후 팝업을 닫지만 연결은 계속 유지됩니다.

권한 모델

연결 시점: 읽기 전용 범위(viewAccounts, viewBalance, viewNetwork)만 허용됩니다.

서명 범위(signMessage, signContract 등)는 첫 번째
성공적인 승인 시 지연 부여됩니다. 수정 전에는 DEFAULT_PERMISSIONS에 없어서,
디스패처는 프롬프트가 나타나기 전에 모든 서명 호출을 UNAUTHORIZED로 거부했습니다 —
그 증상의 두 번째 근본 원인입니다.

이제:

  • 권한 검사는 부여되지 않은 서명 범위가 승인 프롬프트로 진행되게 허용합니다
  • 승인 시 grantPermission이 그 범위를 세션에 저장합니다
  • 이후 호출은 권한 검사를 건너뛰지만 여전히 승인이 필요합니다 — 범위를 부여하는 것은 사용자가 dApp이 물어볼 수 있다는 데 동의한다는 기록일 뿐입니다

철회는 명시적입니다: revokePermission은 permissions에서 범위를 제거하고
그것을 deniedPermissions에 기록하며, 디스패처는 이를 단호히 거부합니다.

보안 불변식

다음을 약화시키지 마십시오:

  • 출처(Origin) 검증 — 모든 인바운드 postMessage에 대해 수행 (PopupTransport.ts, rpc-handler.ts)
  • 재생 방지: CSPRNG 챌린지 + dApp 논스 + 세션별 단조 논스. makeId는 메시지 상관 관계용일 뿐이며 보안 값으로 절대 사용해서는 안 됩니다
  • 권한은 출처별이며 sdk-sessions에 저장되고 명시적으로 부여/철회됩니다
  • MessagePort 독립성: 포트는 팝업보다 오래 갑니다. 일단 전송되면 지갑은 연결을 끊지 않고 승인 창을 닫을 수 있습니다
  • 금지된 메서드는 클라이언트 측(WalletProvider)과 지갑 측(rpc-handler)에서 모두 거부되므로, 낮은 수준의 request() 탈출구를 통해서도 트랜잭션 실행이 SDK로 새어 나갈 수 없습니다
  • localStorage는 세션 복원 힌트(주소, 네트워크)만 보관합니다 — 절대 비밀 값은 아닙니다

dApp 통합

빠른 시작

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

세션 관리

Orion 세션은 유휴 30분 또는 절대 8시간 후에 만료됩니다. SDK는
내장 세션 상태 확인과 자동 재연결을 제공합니다:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

네트워크 — 사용자 소유 포함

사용자는 Settings → Network에서 자신의 네트워크를 추가할 수 있습니다(자체 노드, devnet
포크, 유료 RPC). 그런 네트워크는 일급 객체입니다: 프리셋과 함께 연결 팝업의 선택기에
나타나며, 연결된 dApp도 그것들을 볼 수 있습니다.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

이 기능에 의존하기 전에 customNetworks 능력을 기능 감지하십시오 — 이전
지갑 빌드는 id 문자열을 반환하는 기본 wallet_getNetwork만 지원합니다.

NetworkInfo는 의도적으로 rpcUrl과 relayerUrl을 담지 않습니다. 사용자가
추가한 네트워크는 흔히 개인 엔드포인트입니다 — LAN 주소, 터널, API 키가 쿼리 문자열에
든 공급자 URL — 이를 사용자가 연결하는 모든 사이트에 넘기면 사용자의 인프라가
새어 나갑니다. dApp에는 그것이 필요 없습니다: 모든 읽기는 지갑을 거치며
(wallet_getBalance 등) 실행은 결코 지갑 UI를 벗어나지 않습니다. 선을 넘어가는 것은
dApp이 정당하게 필요한 것뿐입니다 — 어느 네트워크와 대화 중인지, 소유자가 손으로
추가했는지(custom), 트랜잭션을 어디에 링크할지(explorerUrl).

wallet_switchNetwork는 없습니다. 전환은 지갑 자체 UI에서 이루어집니다 — 팝업의
선택기나 기본 창의 네트워크 알약 — 상태 변경이 절대 dApp에서 시작되지 않는다는 규칙과
일치합니다. 다른 네트워크가 필요한 dApp은 사용자에게 전환을 요청한 다음
networkChanged를 기다립니다.

networkChanged는 전환이 일어날 수 있는 두 곳 모두에서 발생합니다: 연결 팝업과
기본 창. 팝업이 닫히면 세션은 기본 창으로 인계되므로, 대부분의 사용자가 네트워크
알약을 건드릴 때쯤이면 팝업은 이미 사라져 있습니다 — Layout.tsx는 채택된 핸들러로
발생시켜 연결된 dApp이 낡은 네트워크를 표시한 채로 남지 않게 합니다.

두 개의 독립적인 클래스가 WalletHost를 구현합니다 — src/connect/host.ts(기본 창)와
src/connect/ConnectApp.tsx의 인라인 호스트(팝업). 인터페이스에 추가되는 모든 것은
둘 다에 구현되어야 하며, tests/unit/connect-handler.test.ts의 픽스처에도 구현되어야 합니다.

세션 관리

Orion Wallet 세션은 SDK가 자동으로 관리합니다. 세션은 다음 이후에 만료됩니다:

  • 유휴 제한시간: 30분간 활동 없음
  • 절대 제한시간: 연결 후 8시간

dApp은 언제든지 세션 상태를 확인할 수 있습니다:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

세션이 만료되면 지갑이 sessionExpired 이벤트를 발생시킵니다. dApp은 이 이벤트를
수신하고 사용자에게 다시 연결하라고 요청해야 합니다:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

세션 복원은 자동으로 처리됩니다 — 지갑이 세션 힌트를 IndexedDB에 보존하므로,
만료 후 다시 연결할 때 사용자가 지갑을 다시 가져올 필요가 없습니다.

E2E 참고: Playwright 실패의 벽을 믿기 전에, diff가 아니라 머신을 확인하십시오.
두 가지 환경 제한이 실제 회귀와 똑같이 보이는 실패를 만들어냅니다:

  • 임시 공간. Chromium은 각 브라우저 프로필을 TMPDIR(기본값 /tmp) 아래에 둡니다. 그 파일시스템이 가득 차면 — /tmp가 다른 프로세스들과 공유되는 작은 tmpfs일 때 쉽습니다 —
    컨텍스트는 시작 시 죽고 무관한 테스트는 수 밀리초 만에 실패하거나 30초 제한시간에 걸립니다. 먼저 df -h /tmp를 확인하십시오; 넉넉한 파일시스템의
    TMPDIR=$HOME/.cache/e2e-tmp로 다시 실행하면 같은 스펙이 제한시간 초과에서
    약 4초 만에 통과로 바뀝니다.
  • 메모리. 작업자당 약 2GB의 여유 메모리가 필요합니다. 그것이 고갈되면 Chromium이 테스트 도중 죽고 Playwright는 Target crashed를 보고합니다; --workers=1로 다시 실행하십시오.

playwright.config.ts는 reuseExistingServer: !isCI로 설정하므로, 포트 4173의
남아 있는 npm run preview가 조용히 재사용됩니다 — 다른 체크아웃에서 시작한 것까지도요.
두 트리를 비교할 때는 실행 사이에 리스너를 죽이거나(ss -lptn | grep 4173) 두 번째 실행이
첫 번째 것의 빌드를 테스트하게 됩니다.

버그를 고칠 때는 수정만이 아니라 실패 모드를 문서화하는 테스트를 추가하십시오.
tests/unit/history-view.test.ts와 error-boundary.test.tsx가 이를 따릅니다: 각각은
재발을 방지하는 증상을 이름으로 담습니다.
