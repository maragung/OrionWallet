監査ステータス

Orion Wallet は独立した第三者によるセキュリティ監査を受けていません。

暗号設計はリファレンスである octra-labs/webcli 実装に従っており、プリミティブは
十分にレビューされたライブラリに由来します。しかし、統合そのものは監査を受けていません。
相応の価値を保管する前に、その点をよくお考えください。

脆弱性の報告

セキュリティ上の問題について公開の Issue を立てないでください。

次を含めて、メンテナーに非公開で報告してください。

  • 問題の説明とその影響
  • 再現手順
  • 影響を受けるバージョンまたはコミット
  • 推奨される修正案があれば

公開前に、修正のための妥当な期間を設けてください。報告は歓迎され、別段のご希望がない限り
クレジットされます。

脅威モデル

Orion Wallet が防御するもの

脅威緩和策
鍵がサーバーに漏れるバックエンドがない。鍵はブラウザから決して出ない
保管時のキーストア窃取AES-256-GCM、PBKDF2 で PIN から導出した鍵
悪意ある dApp の要求明示的な承認プロンプトを伴うオリジン単位の権限
クロスオリジンのメッセージ偽造すべての受信メッセージでオリジンを検証
メッセージのリプレイセッションごとの CSPRNG チャレンジとノンス
注入されたマークアップによる XSSinnerHTML / dangerouslySetInnerHTML を使わない。CSP がソースを制限する
不正な RPC データによるアプリのクラッシュ防御的な正規化に加えてエラー境界
リカバリーフレーズが実際には書き留められていない作成はランダムな 3 単語の再入力を条件とする
鍵のないアカウントからの署名assertCanSign が UI だけでなく API の境界で拒否する
ひそかに盗聴される RPC トラフィック平文エンドポイントには明示的なオリジン単位の同意が必要

防御できないもの

これらについては、自分自身に対して率直になってください。

  • 侵害された端末。マルウェア、キーロガー、あるいは敵対的なブラウザ拡張は、入力中の PIN を読み取り、メモリから復号済みの鍵を抽出できます。
  • 失われたリカバリーフレーズ。復旧の仕組みはありません。誰も復元できません。
  • フィッシング。偽サイトにリカバリーフレーズを入力すれば、資金は失われます。Orion Wallet はセットアップ後にフレーズを尋ねることは決してありません。
  • 侵害された RPC ノード。悪意あるノードは偽の残高を返したり取引を差し止めたりできます。署名を偽造したり鍵を盗んだりはできません。
  • サプライチェーンの侵害 — npm 依存関係やホスティングプロバイダーの侵害。
  • 物理的アクセス — ウォレットがロック解除された、ロックされていない端末への物理的アクセス。

暗号設計

鍵の導出と保管

目的アルゴリズム
ニーモニックBIP39
HD 導出Ed25519, SLIP-0010 style
署名Ed25519 (tweetnacl)
ECDH（ステルス）X25519 (@noble/curves)
キーストア暗号化AES-256-GCM (WebCrypto)
PIN → 鍵PBKDF2-HMAC-SHA256
乱数crypto.getRandomValues

キーストアの形式は C++ 版のオリジナルと一致します。OCT1 マジック、バージョン、PBKDF2 の反復
回数、ソルト、ノンス、そして認証タグ付きの AES-GCM 暗号文です。

PIN の取り扱い

PIN はどのような形でも決して永続化されません。ロック解除時に復号鍵を導出し、その後は破棄されます。
設計上、「PIN を記憶する」機能はありません。したがって、忘れた PIN はリカバリーフレーズからの復元でしか
解決できません。

ロック解除セッション

PIN は永続化されませんが、ロック解除の結果はセッションが続く間、永続化されます。ページの再読み込みで
ユーザーを PIN 画面に戻してはならないからです。src/wallet/unlock-session.ts は復号済みのウォレットを
AES-256-GCM で封印し、2 つのストアに分割します。

片方場所寿命
暗号文（orion:unlock-session）sessionStorage1 つのタブ。そのタブが閉じると消える
封印鍵IndexedDB unlock-session-keys、抽出不可能な CryptoKey としてロック時に削除。孤立したものは経過時間で刈り取られる

どちらの片方も単独では使えません。IndexedDB はタブが閉じても残りますが暗号文を持たず、
sessionStorage は暗号文を持ちますが鍵を持たず、2 つ目のタブや別のオリジンからは読めません。鍵は
extractable: false で生成されるので、このオリジンから使うことはできてもそのバイト列を読み出すことは
できません — 私たち自身のコードからも、ページ内で動くことに成功した何ものからもです。セッションは復元の
たびにローテーションし（新しい鍵、新しいノンス）、createdAt を前方へ持ち越すので、再読み込みで絶対上限を
延ばすことはできません。

有効期限: 30 分のアイドル（設定可能、autoLockMinutes。0 で無効化）と、最初のロック解除からの
8 時間の絶対上限です。両方が復元時に強制され、アイドル期間は useAutoLock によってライブでも
強制されるので、開いたままのタブは自らロックします。

これが防御しないもの — 正直に述べる部分です。

  • タブ内でのスクリプト実行。ライブセッション中にページ内で動くコードは、ウォレットとまったく同じように、ブラウザにセッションの復号を求め、その鍵で署名させることができます。封印鍵を抜き出すことはできないので、侵害はそのタブで終わり、別の場所で使える盗まれた鍵になることはありません。
  • 侵害された端末。上記の脅威モデルから変わりません。ローカルのマルウェアは IndexedDB と sessionStorage を両方とも読めます。
  • 安全でないコンテキスト。crypto.subtle がないと（プレーンな http://、後述）、封印鍵は IndexedDB 上の生のバイト列にフォールバックし、抽出不可能性の保証は失われます。分割と有効期限は依然として保たれます。

完全にオプトアウトするには、Settings → Security → Stay unlocked after a page refresh をオフに
します（keepUnlocked: false）。何も書き込まれず、再読み込みのたびに PIN を求められます — この機能が
存在する前の挙動です。明示的なロック（🔒）は両方の片方を即座に破棄します。

パスキーによるロック解除

オプションで、既定ではオフ、そして追加的なものです。既存のウォレットを開く 2 つ目の方法であって、
PIN の置き換えでは決してありません。src/wallet/passkey.ts。

登録は userVerification: 'required' と WebAuthn の PRF 拡張を伴うプラットフォーム資格情報を
作成します。PRF は、資格情報と保存済みの 32 バイトのソルトから導出した秘密をページに与えます。それは
ユーザーが検証した後にのみブラウザが生成します。ウォレットは sha256("orion-passkey-unlock-v1" || prf) を
AES-256 鍵として取り、シリアライズしたウォレットを AES-256-GCM で封印し、鍵をゼロ埋めし、封印した
ブロブを資格情報 ID とソルトの隣で IndexedDB に保存します。

保存されるもの保存されないもの
資格情報 ID、PRF ソルト、IV、ウォレットの暗号文PRF の出力、導出された鍵、PIN、あらゆる平文の鍵素材

はっきり述べておくべき帰結:

  • PRF は必須で、決して劣化させません。認証器がそれをサポートしない場合、登録は throw し、何も保存しません。代替案 — 読み取れる鍵を暗号文の隣に保持すること — はレコードを自己復号可能にしてしまい、この機能を提供しないよりも悪くなります。
  • レコードは単独では不活性です。その認証器上でユーザー検証済みのジェスチャーが成功しない限り、ディスク上にあるものから鍵を導出する方法はありません。
  • 封印するのはウォレットであって、PIN ではありません。鍵をエクスポートし、フレーズを表示し、PIN を変更し、アカウントを導出するのは、依然として PIN だけです。したがってパスキーによるロック解除はそれらへの権限昇格には使えず、保存されるレコードは保存された PIN よりも厳密に少ししか漏らしません。
  • PIN によるロック解除と同じセッションモデルです。パスキーによるロック解除は、同じアイドル上限と絶対上限を持つ同じロック解除セッションを生み、どちらも延ばしません。
  • 端末とブラウザにスコープされます。オリジンの rpId に束縛され、ローカルに保存されます。ウォレットのエクスポートには含まれず、リカバリーフレーズからも導出されません。
  • 古い資格情報はフェイルクローズします。復号が失敗した場合 — 更新・再登録された資格情報、復元された端末 — レコードは削除され、PIN が必要になります。却下またはタイムアウトしたジェスチャーは意図的にそれを削除しないので、キャンセルされたプロンプトが黙ってこの機能を無効化することはありません。
  • ウォッチ専用アカウントでは拒否されます。封印すべき鍵素材がありません。

防御しないものは変わりません。侵害された端末と、ライブセッション中のスクリプト実行で、上記のロック解除
セッションとまったく同じです。ただし、1 つの実際の露出は取り除きます — ロック解除のたびに PIN が
入力され、観察されることです。

ウォッチ専用アカウント

アカウントはアドレスだけで、キーストアなしに追加できます。不変条件は、そのようなアカウントは決して
署名できないというもので、それは UI ではなく署名が起こる場所で強制されます。
assertCanSign（src/wallet/watch-only.ts）は送金、暗号化、ステルス、コントラクト、dApp 要求の各経路から
呼ばれ、アクションと対処法の両方を名指しして throw します。

構造上フェイルクローズします。このチェックは、秘密鍵が完全な 64 バイトの Ed25519 鍵でないウォレットを
すべて拒否するので、watchOnly フラグが何らかの理由で失われたとしても、切り詰められた鍵や欠けた鍵は
拒否されます。このフラグは serializeWallet/deserializeWallet を通じて引き継がれるので、ロック解除
セッションから復元したウォレットも依然としてウォッチ専用です。

乱数

セキュリティに関わる値はすべて、src/crypto/random.ts を経由して crypto.getRandomValues を使います。

src/sdk/protocol.ts の makeId には Math.random のフォールバックがあります。これはメッセージの
相関付け ID にのみ使われ、セキュリティ値には決して使われず、その旨が注記されています。
チャレンジ、ノンス、鍵、ソルトに再利用しないでください。

ブラウザのセキュリティ体制

Content-Security-Policy

index.html で設定されています。

default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; font-src 'self' data:;
connect-src 'self' https: http://localhost:* http://127.0.0.1:* http://[::1]:*;
frame-src 'self' https:; worker-src 'self' blob:; object-src 'none';
base-uri 'self'; form-action 'self';

3 つのエントリには説明が必要です。

  • 'wasm-unsafe-eval' は PVAC FHE モジュールに必要です。Chromium はそれなしでは WebAssembly.instantiate() をブロックします。これは WebAssembly のコンパイルのみを許可し、JavaScript の eval() を再び有効にしません。
  • スタイル向けの 'unsafe-inline' は、スタイル未適用コンテンツのちらつきを避けるための描画前クリティカル CSS に必要です。スタイルにのみ適用され、スクリプトには決して適用されません。
  • connect-src のループバックは、平文を一般的に許可するようポリシーを広げることなく、ローカルで動かすノードを使えるようにします。localhost / 127.0.0.0/8 / [::1] へのトラフィックは決してマシンの外に出ないので、ワイヤー上に傍受すべきものがありません。

平文（http）RPC エンドポイント

それ以外のプレーンな http:// は既定で拒否され、src/wallet/endpoint-policy.ts が判断を下す唯一の
場所です。これは URL と明示的なコンテキストの純粋関数なので、ストア、Settings UI、テストが何を許可
するかで食い違うことはありません。

3 つの独立したブロッカーが適用され、判定は最も根本的なものを最初に名指しするので、混在コンテンツが
真の原因のときにユーザーが許可リストを直すよう告げられることはありません。

ブロッカー誰が強制するか解除の方法
混在コンテンツブラウザが無条件に解除不可。TLS またはプロキシを使う
Content-Security-Policy出荷されるメタタグの CSPVITE_ALLOW_HTTP_ENDPOINTS=1 で再ビルドする
ユーザー同意設定内の allowedInsecureOriginsSettings → Network でそのオリジンを Trust する

設計上の注記:

  • CSP はメタタグなので、実行時に広げることはできません — どの設定でもこれを許可できず、だからこそビルドフラグなのです。VITE_ALLOW_HTTP_ENDPOINTS=1 はビルド時に connect-src へ http: を追加するだけで、それ以外は何もしません。その上でユーザー同意が依然として必要です。
  • 同意はオリジン単位です — スキーム、ホスト、ポート。ホスト名の一致でも URL のプレフィックスでもないので、http://node.lan:8080 を信頼してもそのホストの別ポートは信頼されず、http://127.0.0.1.evil.com はループバックとして扱われません。
  • エクスプローラー URL は対象外です。それらは常に <a href> のナビゲーションであって、フェッチではないからです。connect-src も混在コンテンツも適用されません。relayerUrl は保存されますが決してフェッチされません。このポリシーの対象は rpcUrl だけです。
  • ブロックされたエンドポイントでも、意図的に RpcClient を構築します。構築を拒否すると、ユーザーがそれを直すための Settings に到達できなくなるからです。理由は代わりに、ヘッダーの ⚠️ Insecure RPC バッジと RpcClient.unreachableHint として現れます。後者は throw された TypeError にのみ付加され、実際のサーバーエラーやタイムアウトには決して付加されません — それでは誤解を招くからです。
  • rpcProxyUrl は判断をプロキシに移します。エンドポイントはプロキシ自身のスキームで判定されます。ブラウザが実際に接続するのはそれだからです。プロキシはすべての要求を見るので、UI は自分で運用するよう促します。プロキシは鍵に到達したり署名したりはできません。

平文 RPC は機密性および完全性の露出です — 経路上のノードがあらゆる照会を読み、応答を書き換えられます —
が、鍵の侵害ではありません。署名はローカルで生成され、ウォレットは受け取ったものを鍵素材として一切
検証しないからです。

クロスオリジン分離

COOP/COEP はアプリ全体で same-origin / require-corp ですが、/connect では unsafe-none の
上書きが適用され、承認ポップアップがオープナーと MessagePort を交換できるようにしています。この絞り込みは
意図的なもので、その 1 つの経路に限定されています。

dApp 接続のセキュリティ

サイトが接続を要求すると:

  1. ポップアップが要求元のオリジンを目立つように表示します。
  2. ユーザーが明示的に承認する必要があります。新しいオリジンへのサイレント接続はありません。
  3. 承認はそのオリジンにスコープされ、オリジン単位で永続化されます。
  4. 署名操作は、信頼済みのサイトであっても常に確認を必要とします。

「Trust this site」は読み取り専用の要求（残高、アカウント、ネットワーク）についてのみ
プロンプトを抑制します。サイレントな署名を許可することは決してありません。

接続は Settings → Connected Sites で確認・取り消しができます。

dApp がカスタムネットワークについて知ること

ユーザーが手動で追加したネットワークは、接続中のサイトから見えます（wallet_getNetworkInfo、
wallet_getNetworks、および networkChanged イベント）。dApp はどのネットワーク上にいるかを知らなければ
正しいエクスプローラーリンクやチェーンのラベルを描画できないからです。ワイヤーを渡るレコードは
意図的な部分集合です。

送られるもの差し控えられるもの
id、name、explorerUrl、icon、customrpcUrl、relayerUrl

エンドポイントが差し控えられるのは、ユーザーが追加したネットワークが通常プライベートなもの — LAN
アドレス、トンネル、クエリ文字列に API キーを含む有料プロバイダー URL — だからです。サイトに接続する
ことで、ユーザーのノードがどこにあるかを開示したり、資格情報付きの URL を引き渡したりすべきでは
ありません。機能は何も失われません。読み取りはウォレット経由でプロキシされ、取引はウォレットが構築・
ブロードキャストするので、dApp が自ら RPC に到達する必要は決してありません。

知っておくべき帰結が 2 つあります。

  • カスタムネットワークの名前はユーザーが選び、dApp に表示されます。個人を特定できる識別子にちなんで名付けると、その識別子が接続するすべてのサイトに開示されます。
  • wallet_getNetworks は、設定したネットワークがいくつあるかを明かします。これは小さなフィンガープリンティングの面ですが、dApp が「X に切り替える」案内を提供できるように受け入れられています。

どの dApp もネットワークを変更できません。wallet_switchNetwork メソッドは存在しません。切り替えは
ウォレット自身の UI でのみ起こり、dApp は後から networkChanged を通じてそれを知ります。

依存関係のステータス

本番依存関係: 既知の脆弱性ゼロ（npm audit --omit=dev）。

開発依存関係は、vitest、vite、esbuild、および関連パッケージに勧告を抱えています。
残りの修正はいずれも、ビルドを壊すおそれのあるメジャーアップグレード（vite 5→8、vitest 2→4）を
必要とします。これらのパッケージはビルドツールであり、ユーザーには出荷されず、デプロイされたウォレットに
影響することはできません。

これは意図的なトレードオフで、リリースごとに見直されます。npm audit --omit=dev を実行して、
出荷される範囲がクリーンなままであることを確認してください。

ユーザー向けガイダンス

すべきこと

  • リカバリーフレーズをオフラインで、紙に、複数の場所に保管する
  • 送金前に受取アドレスを一文字ずつ確認する
  • すべての dApp 接続プロンプトでオリジンを確認する
  • 新しいアドレスを使うときは、まず少額のテスト送金をする
  • ブラウザと OS を最新に保つ

決してしないこと

  • セットアップ後に、どのウェブサイトにもリカバリーフレーズを入力する
  • フレーズをデジタルで保存する — スクリーンショット、クラウドメモ、チャットメッセージは不可
  • 秘密鍵や .oct バックアップファイルを共有する
  • 実際の資金を保持するウォレットを、共有または信頼できないコンピューターで使う

コントリビューター向け

弱めてはならないセキュリティ上重要な不変条件:

  • すべての受信 postMessage でのオリジン検証
  • すべてのセキュリティ値に CSPRNG。makeId はその 1 つではない
  • localStorage、sessionStorage、ログ、エラーメッセージに秘密情報を置かない
  • innerHTML や dangerouslySetInnerHTML を使わない
  • PIN は決して永続化しない
  • パスキーによるロック解除は PRF を必須とする。読み取れる鍵の保存に決してフォールバックしない
  • assertCanSign がすべての署名経路を守る — ウォッチ専用アカウントは決して署名してはならない
  • 平文エンドポイントのポリシーは endpoint-policy.ts にとどめる。他の場所に場当たり的な URL チェックを置かない
  • Canonical JSON はバイト単位で正確なままにする — 署名がそれに依存する

暗号、鍵の取り扱い、ストレージ、または接続フローに触れる変更は、その旨をプルリクエストで
明示的に述べるべきです。
