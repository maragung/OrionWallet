セットアップ

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps は必須です。ESLint 9 と @eslint/js 10 が競合する peer 範囲を宣言しているためです。
vercel.json も同じフラグを使うので、CI とローカルのインストールが一致します。

Node 20 以上を推奨します。

アーキテクチャ

純粋なクライアントサイドで、バックエンドはありません。データは一方向に流れます。

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

設計上の制約

Canonical JSON はバイト単位で正確でなければなりません。src/tx/canonical-json.ts は
nlohmann::json のキー順序とフォーマットを正確に再現します。署名はこれらのバイト列に対して計算されるため、
わずかな逸脱でもネットワークが拒否する署名を生みます。このシリアライザーを「整理」しないでください。

命名: 製品とプロトコル。「Orion Wallet」は製品です。octra_* RPC メソッド、
oct アドレスプレフィックス、OCT ティッカー、そして「Octra Network」はプロトコルの識別子であり、
決して改名してはなりません。

ビルドシステム

TypeScript の設定ファイルが唯一の信頼できる情報源です。

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
これらの .js の兄弟ファイルを追加しないでください。Vite は vite.config.js を
vite.config.ts よりも先に解決するので、古いトランスパイル済みコピーが実際の設定を黙って覆い隠し、
.ts ファイルへの編集が何もしなくなります。これら 3 つのファイル名は .gitignore に入っています。
eslint.config.js は本物のフラット設定であり、意図的に残されています。

無視するだけでは不十分でした。何も作成されるのを止めなかったからです。
tsconfig.node.json は composite プロジェクトで、宣言の出力を強制し、outDir がないと
どの tsc -b もソースのすぐ隣に vite.config.js を書き込みました。これは 2 回起こりました。
そのプロジェクトの出力は現在 node_modules/.tmp/tsconfig-node/ に向けられ、そこでは何も覆い隠せません。
そのプロジェクトに設定ファイルを追加する場合は、outDir はそのままにしておいてください。

環境フラグ

フラグ効果
VITE_ALLOW_HTTP_ENDPOINTS=1ビルド時に connect-src CSP ディレクティブへ http: を追加し、自己ホストのビルドがプレーン http の RPC ノードに到達できるようにします。オリジン単位のユーザー同意は依然として適用されます — src/wallet/endpoint-policy.ts を参照

ビルド時にのみ設定します。vite.config.ts の allowHttpEndpointsCsp プラグインが読み取り、
index.html を書き換えます。実行時には効果がありません。メタタグの CSP はドキュメントが解析された後には
緩められないからです。

ヘッダー

COOP/COEP は same-origin / require-corp に設定されています（将来の WASM スレッド化のために予約）。
ただし /connect では unsafe-none の上書きが適用され、ポップアップの postMessage + MessagePort
転送が機能するようにしています。開発時のヘッダーは vite.config.ts に、本番のヘッダーは vercel.json に
あります。両者を同期させておいてください。

Content-Security-Policy

index.html で定義されています。script-src は 'wasm-unsafe-eval' を含む必要があります — Chromium は
それなしでは WebAssembly.instantiate() を拒否し、まさにそれが PVAC モジュールを黙って読み込み失敗
させていました。そのディレクティブは WebAssembly のコンパイルのみを許可し、JavaScript の eval() を
再び有効にすることはありません。

connect-src は 'self' https: に加えてループバック（http://localhost:*、http://127.0.0.1:*、
http://[::1]:*）を含むので、ローカルで動かすノードは平文を一般的に開くことなく機能します。それ以外の
http:// は src/wallet/endpoint-policy.ts によってゲートされ、そこが判断を下す唯一の場所です — URL と
明示的なコンテキストの純粋関数なので、ストア、Settings UI、テストが食い違うことはありません。
他の場所に場当たり的な URL チェックを追加しないでください。3 つの独立したブロッカー（混在コンテンツ →
CSP → ユーザー同意）が適用され、判定は最も根本的なものを最初に報告するので、ブラウザが拒否している
ときにユーザーが許可リストを直すよう告げられることはありません。

PVAC WASM パイプライン

ビルド

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py が必要なのは、PVAC がハードウェア AES（AES-NI や ARM 暗号拡張）なしでは
ハード #error になり、それを WebAssembly が提供しないためです。このパッチは、ビット単位で同一だが
おおよそ 5〜10 倍遅い可搬なソフトウェア実装を追加します。追加的な変更で、ハードウェアの経路は
手つかずのまま残り、バックアップの .hpp.bak が書き出されます。

読み込み

src/pvac/wasm-bridge.ts はモジュールを 3 つのステップで読み込みます。

  1. Probe — グルー URL に対する HEAD です。これにより「未ビルド」（404）が「CSP によるブロック」と区別できます。これがないと、両方が同一の不透明なインポート失敗として現れます。
  2. Import — /* @vite-ignore */ を付けた絶対 URL の動的 import() です。絶対でなければなりません。むき出しの指定子は解決に失敗し、./wasm/pvac.js は /assets/ を基準に解決されて 404 になります。
  3. Verify — ブリッジを差し替える前に、必要な 13 個の _pvac_* エクスポートがすべて存在することを表明します。以前のビルドはシリアライズ関数を省いており、ノードが「malformed transaction」としか報告しない形で暗号化/復号を壊していました。

失敗は PvacFailureReason として分類されます。not-built、csp-blocked、
missing-exports、init-failed、unknown です。それぞれが Settings に表示される具体的な対処に
対応します。シングルトンの promise は失敗時にリセットされるので、↻ Reload PVAC はキャッシュされた
拒否を再生するのではなく、やり直せます。

メモリ規則

C API は手動メモリ管理です。すべての _malloc には _free が必要で、すべての serialize_* は
_pvac_free_bytes で解放しなければならないバッファを返します。keygen/enc_* からのハンドルには、
対応する _pvac_free_* が必要です。try/finally を使ってください — パターンは WasmPvacBridge を参照。

状態管理

Zustand を src/store/wallet-store.ts で使用します。ウォレット、RPC クライアント、設定、PVAC
ステータス、トースト、そしてグローバルなローディングフラグを保持します。

グローバルなローディングフラグ（isLoading）は全画面のぼかしオーバーレイを駆動し、ウォレットの
ロック解除などアプリ全体の遷移のみに予約されています。パネル単位の処理は代わりに
usePanelLoading を使う必要があります — 後述します。

エラー処理

src/components/ErrorBoundary.tsx が Layout.tsx 内のすべてのパネルを、アクティブなタブを
キーにしてラップするので、発火した境界はナビゲーションでリセットされます。加えて main.tsx の
ルートにも境界が 1 つあります。

これは見た目以上に重要です。index.html には次が含まれます。

#root:empty::before { content: 'Loading Orion Wallet…'; }

境界がないと、レンダー時のあらゆる throw によって React 18 はツリー全体をアンマウントし、#root が
空になり、あのフォールバックがレンダーされます — 永遠に読み込み中のように見える真っ白なページを
生み出します。境界はシェルを生かし続け、やり直せるエラーカードを表示します。

帰結: レンダー中に呼ばれる関数は、不正な入力に対して throw してはなりません。
src/tx/builder.ts の formatAmount は unknown を受け取り、プレースホルダーに劣化します。
RPC レスポンスもローカルの tx キャッシュもスキーマ検証されていないからです。信頼できない行は
レンダー前に正規化してください — HistoryView にそのパターンがあります。

ローディング状態

パネル単位の処理には usePanelLoading（src/hooks/usePanelLoading.ts）を使います。

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

そして <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} /> をレンダーします。

重要な性質が 2 つあります。モーダルは閉じられる（処理はバックグラウンドで続くので、遅い
ネットワークがユーザーを閉じ込めることはありません）こと、そして状態の書き込みが isMounted() で
ゲートされているので、処理の途中で別画面へ移動してもモーダルが画面に残ったままにならないことです。

ストレージとマイグレーション

idb 経由の IndexedDB を使い、データベースは orion-wallet、バージョンは 6 です。ストアは
src/wallet/storage.ts の OBJECT_STORES 配列で一度だけ宣言します。作成とマイグレーションの
整合性を保つため、新しいものはそこに追加してください — その配列は wipeEverything() も駆動するので、
他の場所に追加したストアはワイプを生き延びてしまいます。

マイグレーションは追加のみです。DB_VERSION を上げ、配列に追記し、新しいエントリの横の
コメントにバージョンを記します。既存のストアは決して改名も削除もしません。
これまでのバージョン: v2 SDK ストア、v3 OCS01 トークン、v4 oct:// ブックマーク、v5
unlock-session-keys、v6 contacts + passkey-unlock。

リブランドのマイグレーション

データベースを webcli-react から改名すると、既存のウォレットがすべて孤立していたでしょう。
IndexedDB はデータをデータベース名でスコープするからです。migrateLegacyDatabase は初回起動時に
すべてのストアを前方へコピーします。これは次のとおりです。

  • 冪等 — 対象に何らかのウォレットが存在すれば省略される
  • 非破壊的 — ロールバックに備え、レガシーデータベースはそのまま残される
  • 非致命的 — 失敗はログに記録され、決して throw されない。マイグレーションのバグが起動を妨げてはならない

E2E ヘルパーの clearIndexedDB は両方のデータベースを削除しなければならないことを覚えておいてください。
さもなければマイグレーションがレガシーデータをそのままコピーして戻し、「クリーンな状態」がクリーンでなくなります。

ウォレット SDK

src/sdk/ は dApp 向けのプロバイダーで、src/connect/ は /connect で配信される承認ポップアップです。

メソッドの名前空間

ウォレットは 2 つの等価な名前空間に応答します。

汎用Orion ブランド操作
wallet_connectorion_wallet_connect接続を開始する
wallet_signMessageorion_wallet_signMessage平文メッセージに署名する
wallet_signTypedDataorion_wallet_signTypedData構造化データに署名する
wallet_approveContractorion_wallet_approveContractコントラクト呼び出しを事前承認する
wallet_signContractorion_wallet_signContractコントラクト取引に署名する
wallet_getAccountsorion_wallet_getAccountsアカウントを一覧する

両方が受け付けられ、同一に動作します。orion_wallet_* の名前は、明示的に Orion Wallet を対象に
したい dApp のために存在します。汎用の wallet_* の名前は引き続きサポートされ、既存の連携が
動き続けるようにしています。

src/sdk/protocol.ts の canonicalizeMethod は、ディスパッチ前にすべてのメソッド名を正準の
wallet_* 形式に還元するので、2 つの名前空間が食い違うことは決してありません。

接続のライフサイクル

ハンドシェイク（セッションごとに 1 回）:

  1. dApp が provider.connect() を呼ぶ → PopupTransport が /connect?v=1&rid=…&origin=… を開く
  2. ウォレットが ConnectApp をレンダーし、必要ならユーザーがロックを解除する
  3. ウォレットが hello + MessagePort を window.postMessage で送る（オリジン検証あり）
  4. dApp がポート越しに challenge をエコーする（リプレイ対策）
  5. ConnectHandler が ack を検証し、CONNECT RPC を提供する → アドレス、アカウント、ネットワークを返す

接続後:

  • ポップアップは閉じてよいが、MessagePort は開いたまま — ウィンドウから独立している
  • セッションは IndexedDB（sdk-sessions）に、アイドル + 絶対 TTL とともに永続化される
  • 読み取りメソッド（getBalance、getAccounts）はセッション内でサイレント
  • 署名メソッドは常に新しい承認プロンプトを開く

「接続はできるが他は何も動かない」の修正:

当初 PopupTransport.isConnected() は popup.closed を確認していたので、承認ウィンドウが
閉じた後のすべての呼び出しが「Transport is not connected」で失敗していました。現在はポートのみを
確認し、それはポップアップより長生きします。ウォレットは承認後にポップアップを閉じますが、接続は
生きたままです。

権限モデル

接続時: 読み取り専用スコープのみ（viewAccounts、viewBalance、viewNetwork）。

署名スコープ（signMessage、signContract など）は、最初の承認が成功したときに遅延的に
付与されます。修正前はこれらが DEFAULT_PERMISSIONS に存在せず、ディスパッチャーがプロンプトを
表示する前にすべての署名呼び出しを UNAUTHORIZED で拒否していました — 症状の 2 つ目の根本原因です。

現在は:

  • 権限チェックは、未付与の署名スコープが承認プロンプトへ進むことを許す
  • 承認時に grantPermission がスコープをセッションに永続化する
  • 以降の呼び出しは権限チェックを飛ばすが依然として承認は必要 — スコープの付与は、dApp が要求してよいことにユーザーが同意したという記録にすぎない

取り消しは明示的です。revokePermission はスコープを permissions から削除し、
deniedPermissions に記録します。ディスパッチャーはそれを即座に拒否します。

セキュリティ不変条件

これらを弱めないでください。

  • すべての受信 postMessage でのオリジン検証（PopupTransport.ts、rpc-handler.ts）
  • リプレイ対策: CSPRNG チャレンジ + dApp ノンス + セッションごとの単調増加ノンス。makeId はメッセージの相関付け専用であり、決してセキュリティ値として使ってはならない
  • 権限はオリジン単位で、sdk-sessions に永続化され、明示的に付与/取り消しされる
  • MessagePort の独立性: ポートはポップアップより長生きする。いったん転送されれば、ウォレットは接続を壊さずに承認ウィンドウを閉じられる
  • 禁止メソッドはクライアント側（WalletProvider）とウォレット側（rpc-handler）の両方で拒否されるので、低レベルの request() という抜け道を経由しても、取引の実行が SDK へ逃れることは決してない
  • localStorage はセッション復元のヒント（アドレス、ネットワーク）のみを保持する — 秘密情報は決して保持しない

dApp 連携

クイックスタート

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

セッション管理

Orion のセッションは 30 分のアイドルまたは 8 時間の絶対時間で期限切れになります。SDK は
セッションのヘルスチェックと自動再接続を内蔵しています。

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

ネットワーク（ユーザー独自のものを含む）

ユーザーは Settings → Network で独自のネットワーク（自分のノード、devnet のフォーク、有料 RPC）を
追加できます。それらのネットワークは第一級の存在です。接続ポップアップのセレクターにプリセットと並んで
現れ、接続中の dApp からも見えます。

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

いずれかに依存する前に customNetworks ケイパビリティで機能検出してください — 古い
ウォレットのビルドはむき出しの wallet_getNetwork にしか応答せず、それは id 文字列を返します。

NetworkInfo は意図的に rpcUrl も relayerUrl も持ちません。ユーザーが追加した
ネットワークは、しばしばプライベートなエンドポイント — LAN アドレス、トンネル、クエリ文字列に API キーを
含むプロバイダー URL — であり、それをユーザーが接続するすべてのサイトに渡せば、インフラを漏らすことに
なります。dApp はそれを必要としません。すべての読み取りはウォレットを経由し
（wallet_getBalance など）、実行がウォレット UI を離れることはありません。ワイヤーを渡るのは dApp が
正当に必要とするもの — どのネットワークと話しているか、所有者が手動で追加したか（custom）、そして
取引をどこへリンクするか（explorerUrl）だけです。

wallet_switchNetwork は存在しません。切り替えはウォレット自身の UI — ポップアップの
セレクターかメインウィンドウのネットワークピル — にとどまり、状態変更は dApp から生じないという規則と
一貫しています。別のネットワークが必要な dApp は、ユーザーに切り替えを求め、networkChanged を
待ちます。

networkChanged は、切り替えが起こりうる両方の場所 — 接続ポップアップとメインウィンドウ — から
送出されます。ポップアップが閉じるとセッションはメインウィンドウへ引き継がれるので、ほとんどのユーザーが
ネットワークピルに触れる頃にはポップアップはとうに消えています — Layout.tsx は引き継いだハンドラーへ
送出するので、接続中の dApp が古いネットワークを表示したままにはなりません。

WalletHost を実装する独立したクラスが 2 つあります — src/connect/host.ts（メインウィンドウ）と
src/connect/ConnectApp.tsx 内のインラインホスト（ポップアップ）です。インターフェイスに追加するものは
両方に実装し、加えて tests/unit/connect-handler.test.ts のフィクスチャにも実装しなければなりません。

  • wallet_swap / swap
  • wallet_bridge / bridge

セッション管理

Orion Wallet のセッションは SDK によって自動的に管理されます。セッションは次の後に期限切れになります。

  • アイドルタイムアウト: 無操作が 30 分
  • 絶対タイムアウト: 接続から 8 時間

dApp はいつでもセッションのヘルスを確認できます。

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

セッションが期限切れになると、ウォレットは sessionExpired イベントを送出します。dApp はこの
イベントを待ち受け、ユーザーに再接続を促すべきです。

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

セッションの復元は自動的に処理されます — ウォレットは IndexedDB にセッションのヒントを保持するので、
期限切れ後の再接続でユーザーがウォレットを再インポートする必要はありません。

テスト

npm test                 # 676 unit tests, 56 files
npm run test:coverage    # V8 coverage, 60% threshold
npm run test:e2e         # 7 Playwright specs (needs npm run build first)
npm run autofix          # typecheck → format → lint --fix → test → build
npm run check            # same, read-only (CI)

ユニットテストは jsdom 上で fake-indexeddb を用いて実行します。コンポーネントテストは DOM テスト
ライブラリではなく renderToStaticMarkup を使います — tests/unit/processing-modal.test.tsx を参照。

WebAuthn には jsdom の実装がないので、tests/unit/passkey.test.ts は PRF 拡張をモデル化する
FakeAuthenticator をインストールします（それを欠く認証器、却下されたプロンプト、更新された秘密も
含みます）。これは、保存されるレコードが含んではならないものを表明しており、それこそが実際に
重要な性質です。

E2E に関する注意: Playwright の失敗が大量に並んでも、それを信じる前に、差分ではなくマシンを確認して
ください。2 つの環境上の制限が、本物のリグレッションとまったく同じに見える失敗を生みます。

  • 一時領域。Chromium は各ブラウザプロファイルを TMPDIR（既定では /tmp）の下に置きます。そのファイルシステムが一杯だと — /tmp が他のプロセスと共有する小さな tmpfs のときに起こりがちです — コンテキストは起動時に落ち、無関係なテストがミリ秒単位で失敗するか、30 秒のタイムアウトまでハングします。まず df -h /tmp を実行し、広いファイルシステム上で TMPDIR=$HOME/.cache/e2e-tmp を付けて再実行すれば、同じスペックがタイムアウトから約 4 秒での成功に変わります。
  • メモリ。ワーカーあたりおよそ 2 GB の空きメモリが必要です。足りなくなると Chromium はテストの途中で kill され、Playwright は Target crashed を報告します。--workers=1 を付けて再実行してください。

playwright.config.ts は reuseExistingServer: !isCI を設定するので、ポート 4173 に残った
npm run preview が黙って再利用されます — 別のチェックアウトから起動されたものも含めてです。2 つの
ツリーを比較するときは、実行の合間にそのリスナーを kill するか（ss -lptn | grep 4173）、さもなければ
2 回目の実行が 1 回目のビルドをテストしてしまいます。

バグを修正するときは、修正だけでなく、失敗の様態を記録するテストを追加してください。
tests/unit/history-view.test.ts と error-boundary.test.tsx はこれに従っており、それぞれ再発を
防ぐ症状を名指ししています。

リリースチェックリスト

  1. npm run autofix — 完全にグリーンでなければならない
  2. 新規の npm run build に対して npm run test:e2e
  3. npm audit --omit=dev — 本番は脆弱性ゼロを報告しなければならない
  4. PVAC が dev だけでなく本番プレビュー（npm run preview）でも読み込まれることを確認する
  5. 既存のウォレットデータを持つリブランド前のビルドからのマイグレーション経路をテストする
  6. vite.config.ts のサーバーヘッダーが依然として vercel.json と一致することを確認する

既知の問題

開発依存関係の勧告。npm audit は vitest、vite、esbuild、および関連パッケージの脆弱性を
報告します。残りの修正はいずれもメジャーアップグレード（vite 5→8、vitest 2→4）を必要とします。
これらはビルドツールのみで、ユーザーには出荷されません。本番の監査はクリーンです。
SECURITY.html を参照してください。

storage.ts のチャンク化警告。ビルドは storage.ts が静的にも動的にもインポートされて
いるため、独自のチャンクに分割できないと警告します。無害ですが、HistoryView と
WalletExportImport の動的インポートがコード分割の恩恵をもたらさないことは意味します。

ソフトウェア AES の性能。WASM の AES フォールバックはネイティブより 5〜10 倍遅いです。重い PVAC
操作はメインスレッドをブロックします。それらを Web Worker へ移すのが、論理的な次の一手です。
