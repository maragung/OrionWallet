Einrichtung

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps ist zwingend erforderlich: ESLint 9 und @eslint/js 10 deklarieren widersprüchliche Peer-
Bereiche. vercel.json verwendet dasselbe Flag, sodass CI und lokale Installationen übereinstimmen.

Node 20+ wird empfohlen.

Architektur

Reines Client-seitiges Arbeiten; es gibt kein Backend. Daten fließen in eine Richtung:

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

Design-Einschränkungen

Kanonisches JSON muss byte-genau sein. src/tx/canonical-json.ts reproduziert
die Schlüsselreihenfolge und Formatierung von nlohmann::json exakt. Signaturen werden über diese
Bytes berechnet, sodass jede Abweichung eine Signatur erzeugt, die das Netzwerk ablehnt. „Bereinigen" Sie diesen
Serializer nicht.

Benennung: Produkt versus Protokoll. „Orion Wallet" ist das Produkt. octra_*-RPC-Methoden,
das Adresspräfix oct, das Tickersymbol OCT und „Octra Network" sind Protokoll-Bezeichner
und dürfen niemals umbenannt werden.

Build-System

TypeScript-Konfigurationsdateien sind die einzige verbindliche Quelle:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
Fügen Sie hierfür keine .js-Geschwisterdateien hinzu. Vite löst vite.config.js vor
vite.config.ts auf, sodass eine veraltete transpilierte Kopie stillschweigend die echte Konfiguration überschattet und Änderungen
an der .ts-Datei nichts bewirken. Diese drei Dateinamen stehen in .gitignore.
eslint.config.js ist echte Flat-Config und wird absichtlich beibehalten.

Sie zu ignorieren genügte allein nicht, weil nichts verhinderte, dass sie erstellt wurden:
tsconfig.node.json ist ein composite-Projekt, was die Deklarationsausgabe erzwingt, und ohne
outDir schrieb jedes tsc -b vite.config.js direkt neben die Quelle. Es geschah zweimal.
Die Ausgabe für dieses Projekt geht jetzt nach node_modules/.tmp/tsconfig-node/, wo sie nichts
überschatten kann. Wenn Sie diesem Projekt eine Konfigurationsdatei hinzufügen, lassen Sie den outDir unangetastet.

Umgebungs-Flags

FlagWirkung
VITE_ALLOW_HTTP_ENDPOINTS=1Hängt zur Build-Zeit http: an die CSP-Direktive connect-src an, sodass ein selbst gehosteter Build einen Plain-HTTP-RPC-Node erreichen kann. Die Zustimmung des Nutzers pro Origin gilt weiterhin — siehe src/wallet/endpoint-policy.ts

Nur zur Build-Zeit gesetzt. Es wird in vite.config.ts vom Plugin allowHttpEndpointsCsp gelesen
und schreibt index.html um; es hat keine Laufzeitwirkung, weil eine Meta-Tag-CSP nicht erweitert werden kann,
sobald das Dokument geparst ist.

Header

COOP/COEP sind auf same-origin / require-corp gesetzt (reserviert für künftiges WASM-Threading),
mit unsafe-none-Überschreibungen auf /connect, damit die postMessage- + MessagePort-
Übertragung des Popups funktioniert. Dev-Header liegen in vite.config.ts; Produktions-Header in vercel.json.
Halten Sie beide synchron.

Content-Security-Policy

Definiert in index.html. script-src muss 'wasm-unsafe-eval' enthalten — Chromium verweigert
WebAssembly.instantiate() ohne es, was genau der Grund war, weshalb das PVAC-Modul stillschweigend nicht
geladen wurde. Diese Direktive erlaubt nur die WebAssembly-Kompilierung; sie reaktiviert nicht
JavaScript-eval().

connect-src ist 'self' https: plus Loopback (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*), sodass ein lokal ausgeführter Node funktioniert, ohne Klartext generell zu öffnen. Alles
andere über http:// wird durch src/wallet/endpoint-policy.ts geregelt, der einzigen Stelle, die
entscheidet — eine reine Funktion der URL plus eines expliziten Kontexts, sodass der Store, die Settings-UI
und die Tests nicht uneins sein können. Fügen Sie anderswo keine Ad-hoc-URL-Prüfungen hinzu. Drei unabhängige
Blocker greifen (Mixed Content → CSP → Nutzerzustimmung), und das Urteil meldet zuerst den
grundlegendsten, sodass dem Nutzer nie gesagt wird, die Allowlist zu korrigieren, wenn der Browser derjenige ist,
der verweigert.

Die PVAC-WASM-Pipeline

Bauen

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

patch-pvac-aes.py ist erforderlich, weil PVAC ohne Hardware-AES (AES-NI oder
ARM-Krypto-Erweiterungen) hart mit #error abbricht, was WebAssembly nicht bietet. Der Patch fügt eine portable
Software-Implementierung hinzu, die bit-identisch, aber rund 5–10× langsamer ist. Er ist additiv: Die
Hardware-Pfade bleiben unangetastet, und ein Backup .hpp.bak wird geschrieben.

Laden

src/pvac/wasm-bridge.ts lädt das Modul in drei Schritten:

  1. Probe — HEAD auf die Glue-URL, sodass „nicht gebaut" (404) von „durch CSP blockiert" unterscheidbar ist. Ohne dies erscheinen beide als identischer, undurchsichtiger Importfehler.
  2. Import — dynamischer import() einer absoluten URL mit /* @vite-ignore */. Sie muss absolut sein: Ein bloßer Specifier lässt sich nicht auflösen, und ./wasm/pvac.js wird gegen
    /assets/ aufgelöst und liefert 404.
  3. Verify — sicherstellen, dass alle 13 erforderlichen _pvac_*-Exporte existieren, bevor die Bridge eingewechselt wird. Frühere Builds ließen die Serialisierungsfunktionen aus, was Verschlüsseln/Entschlüsseln auf eine Weise brach,
    die der Node nur als „malformed transaction" meldete.

Fehler werden als PvacFailureReason klassifiziert: not-built, csp-blocked,
missing-exports, init-failed, unknown. Jeder wird einer konkreten Behebung zugeordnet, die in
Settings angezeigt wird. Das Singleton-Promise wird bei einem Fehler zurückgesetzt, sodass ↻ Reload PVAC es erneut versuchen kann, statt
eine zwischengespeicherte Ablehnung erneut abzuspielen.

Speicherregeln

Die C-API ist manuell speicherverwaltet. Jedes _malloc braucht ein _free; jedes serialize_* gibt einen
Puffer zurück, der mit _pvac_free_bytes freigegeben werden muss. Handles von keygen/enc_* brauchen
ihre passenden _pvac_free_*. Verwenden Sie try/finally — siehe WasmPvacBridge für das Muster.

State-Management

Zustand, in src/store/wallet-store.ts. Es besitzt das Wallet, den RPC-Client, die Einstellungen, den PVAC-
Status, Toasts und das globale Ladeflag.

Das globale Ladeflag (isLoading) steuert ein Vollbild-Blur-Overlay und ist reserviert für
ausschließlich App-weite Übergänge, etwa das Entsperren des Wallets. Arbeit pro Panel muss stattdessen
usePanelLoading verwenden — siehe unten.

Fehlerbehandlung

src/components/ErrorBoundary.tsx umschließt jedes Panel in Layout.tsx, mit der aktiven
Registerkarte als Key, sodass eine ausgelöste Boundary bei der Navigation zurückgesetzt wird, plus eine Boundary an der Wurzel in main.tsx.

Das ist wichtiger, als es aussieht. index.html enthält:

#root:empty::before { content: 'Loading Orion Wallet…'; }

Ohne eine Boundary lässt jeder Wurf zur Render-Zeit React 18 den gesamten Baum aushängen, #root
wird leer, und dieser Fallback wird gerendert — was eine leere weiße Seite erzeugt, die scheinbar ewig beim
Laden hängt. Die Boundary hält die Shell am Leben und zeigt eine wiederholbare Fehlerkarte.

Konsequenz: Funktionen, die während des Renderns aufgerufen werden, dürfen bei fehlerhafter Eingabe nicht werfen.
formatAmount in src/tx/builder.ts akzeptiert unknown und fällt auf einen Platzhalter zurück,
weil weder RPC-Antworten noch der lokale tx-Cache schema-validiert sind. Normalisieren Sie
nicht vertrauenswürdige Zeilen, bevor Sie sie rendern — HistoryView zeigt das Muster.

Ladezustände

Verwenden Sie usePanelLoading (src/hooks/usePanelLoading.ts) für Panel-bezogene Arbeit:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

Rendern Sie dann <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />.

Zwei Eigenschaften sind wichtig: Das Modal ist dismissible (die Arbeit läuft im Hintergrund weiter, sodass ein
langsames Netzwerk den Nutzer nie einsperrt), und State-Schreibvorgänge sind an isMounted() gekoppelt, sodass
ein Wegnavigieren mitten im Vorgang kein Modal auf dem Bildschirm hängen lassen kann.

Speicher und Migrationen

IndexedDB über idb, Datenbank orion-wallet, Version 6. Stores werden einmal im
OBJECT_STORES-Array in src/wallet/storage.ts deklariert; fügen Sie neue dort hinzu, damit Erstellung und
Migration konsistent bleiben — dieses Array steuert auch wipeEverything(), sodass ein anderswo
hinzugefügter Store ein vollständiges Löschen überstehen würde.

Migrationen sind ausschließlich additiv: Erhöhen Sie DB_VERSION, hängen Sie an das Array an und notieren Sie die
Version in einem Kommentar neben den neuen Einträgen. Bestehende Stores werden nie umbenannt oder entfernt.
Die bisherigen Versionen: v2 SDK-Stores, v3 OCS01-Token, v4 oct://-Lesezeichen, v5
unlock-session-keys, v6 contacts + passkey-unlock.

Die Rebrand-Migration

Das Umbenennen der Datenbank von webcli-react hätte jedes bestehende Wallet verwaist zurückgelassen, da
IndexedDB Daten nach Datenbanknamen kapselt. migrateLegacyDatabase kopiert beim
ersten Start alle Stores vorwärts. Sie ist:

  • idempotent — wird übersprungen, sobald das Ziel irgendein Wallet enthält
  • zerstörungsfrei — die Alt-Datenbank bleibt für ein Rollback intakt
  • nicht fatal — Fehler werden protokolliert, nie geworfen; ein Migrationsfehler darf den Start nicht blockieren

Denken Sie daran, dass clearIndexedDB in den E2E-Helpern beide Datenbanken löschen muss, sonst
kopiert die Migration die Alt-Daten direkt zurück und der „saubere Zustand“ ist nicht sauber.

Wallet-SDK

src/sdk/ ist der dApp-seitige Provider; src/connect/ ist das Freigabe-Popup, das unter
/connect ausgeliefert wird.

Verbindungslebenszyklus

Handshake (einmal pro Sitzung):

  1. dApp ruft provider.connect() auf → PopupTransport öffnet /connect?v=1&rid=…&origin=…
  2. Wallet rendert ConnectApp, der Nutzer entsperrt bei Bedarf
  3. Wallet sendet hello + MessagePort über window.postMessage, origin-validiert
  4. dApp sendet challenge über den Port zurück (Anti-Replay)
  5. ConnectHandler verifiziert das Ack, bedient den CONNECT-RPC → gibt Adresse, Konten, Netzwerk zurück

Nach dem Verbinden:

  • Das Popup darf sich schließen, aber der MessagePort bleibt offen — er ist unabhängig vom Fenster
  • Die Sitzung wird in IndexedDB (sdk-sessions) mit Idle- + absolutem TTL persistiert
  • Lesemethoden (getBalance, getAccounts) laufen innerhalb der Sitzung ohne Rückfrage
  • Signaturmethoden öffnen immer eine neue Freigabeabfrage

Der Fix für „Verbinden funktioniert, sonst nichts“:

Ursprünglich prüfte PopupTransport.isConnected() popup.closed, sodass jeder Aufruf nach dem
Schließen des Freigabefensters mit „Transport is not connected“ fehlschlug. Jetzt prüft es nur den
Port, der das Popup überdauert. Das Wallet schließt das Popup nach der Freigabe, aber die
Verbindung bleibt aktiv.

Berechtigungsmodell

Zum Verbindungszeitpunkt: Nur schreibgeschützte Scopes (viewAccounts, viewBalance, viewNetwork).

Signatur-Scopes (signMessage, signContract usw.) werden verzögert gewährt, bei der ersten
erfolgreichen Freigabe. Vor dem Fix fehlten sie in DEFAULT_PERMISSIONS und der
Dispatcher wies jeden Signaturaufruf mit UNAUTHORIZED ab, bevor die Abfrage erscheinen konnte —
die zweite Grundursache des Symptoms.

Jetzt:

  • Die Berechtigungsprüfung lässt nicht gewährte Signatur-Scopes zur Freigabeabfrage durch
  • Bei Freigabe persistiert grantPermission den Scope in der Sitzung
  • Nachfolgende Aufrufe überspringen die Berechtigungsprüfung, erfordern aber weiterhin eine Freigabe — das Gewähren eines Scopes hält nur fest, dass der Nutzer damit einverstanden ist, dass die dApp fragen darf

Der Entzug ist explizit: revokePermission entfernt den Scope aus permissions und vermerkt
ihn in deniedPermissions, das der Dispatcher rundweg ablehnt.

Sicherheitsinvarianten

Schwächen Sie diese nicht ab:

  • Origin-Validierung bei jedem eingehenden postMessage (PopupTransport.ts, rpc-handler.ts)
  • Anti-Replay: CSPRNG-Challenge + dApp-Nonce + pro Sitzung monotone Nonce. makeId dient nur der Nachrichtenkorrelation und darf nie als Sicherheitswert verwendet werden
  • Berechtigungen gelten pro Origin, werden in sdk-sessions persistiert und explizit gewährt/entzogen
  • MessagePort-Unabhängigkeit: Der Port überdauert das Popup. Nach der Übertragung kann das Wallet das Freigabefenster schließen, ohne die Verbindung zu unterbrechen
  • Verbotene Methoden werden sowohl clientseitig (WalletProvider) als auch walletseitig (rpc-handler) abgelehnt, sodass die Transaktionsausführung nie zum SDK entkommen kann, selbst über den
    Low-Level-Notausgang request() nicht
  • localStorage enthält nur einen Hinweis zur Sitzungswiederherstellung (Adresse, Netzwerk) — nie Geheimnisse

dApp-Integration

Schnellstart

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',

Sitzungsverwaltung

Orion-Sitzungen laufen nach 30 Minuten Inaktivität oder 8 Stunden absolut ab. Das SDK bietet
integrierte Sitzungs-Gesundheitsprüfungen und automatische Wiederverbindung:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

Netzwerke, einschließlich eigener Netzwerke

Ein Nutzer kann in Settings → Network ein eigenes Netzwerk hinzufügen (einen eigenen Node, einen
Devnet-Fork, ein bezahltes RPC). Diese Netzwerke sind erstklassig: Sie erscheinen im Auswahlfeld des Verbindungs-Popups
neben den Voreinstellungen, und eine verbundene dApp kann sie sehen.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

Prüfen Sie das Vorhandensein der Fähigkeit customNetworks, bevor Sie sich auf irgendetwas davon verlassen —
ältere Wallet-Builds beantworten nur das bloße wallet_getNetwork, das eine ID-Zeichenkette zurückgibt.

NetworkInfo enthält bewusst keine rpcUrl und keine relayerUrl. Ein benutzerhinzugefügtes
Netzwerk ist häufig ein privater Endpunkt — eine LAN-Adresse, ein Tunnel, eine Provider-URL mit dem
API-Schlüssel in der Query-Zeichenfolge — und diese jeder Website zu geben, mit der der Nutzer sich verbindet,
würde seine Infrastruktur preisgeben. Eine dApp braucht sie nicht: Jede Leseoperation läuft über das Wallet
(wallet_getBalance und Verwandte), und die Ausführung verlässt die Wallet-UI nie. Was über die Leitung
geht, ist das, was eine dApp legitimerweise benötigt — mit welchem Netzwerk sie spricht, ob der
Eigentümer es von Hand hinzugefügt hat (custom) und wohin eine Transaktion verlinkt werden soll (explorerUrl).

Es gibt kein wallet_switchNetwork. Das Wechseln bleibt in der eigenen UI des Wallets — im
Auswahlfeld des Popups oder im Netzwerk-Pill des Hauptfensters — im Einklang mit der Regel, dass
Zustandsänderungen nie von einer dApp ausgehen. Eine dApp, die ein anderes Netzwerk benötigt, bittet den Nutzer zu
wechseln und wartet dann auf networkChanged.

networkChanged wird von beiden Orten gesendet, an denen ein Wechsel geschehen kann: vom Verbindungs-Popup
und vom Hauptfenster. Sitzungen werden beim Schließen des Popups an das Hauptfenster übergeben, sodass das Popup,
wenn die meisten Nutzer das Netzwerk-Pill berühren, längst verschwunden ist — Layout.tsx sendet an die
übernommenen Handler, damit eine verbundene dApp nicht mit einem veralteten Netzwerk zurückbleibt.

Zwei unabhängige Klassen implementieren WalletHost — src/connect/host.ts (Hauptfenster) und ein
Inline-Host in src/connect/ConnectApp.tsx (Popup). Alles, was dem Interface hinzugefügt wird, muss in beiden
implementiert werden, zusätzlich zur Fixture in tests/unit/connect-handler.test.ts.

Verbotene Methoden

Das SDK blockiert diese Methoden lokal, bevor sie den Transport erreichen. Das Wallet prüft zusätzlich
serverseitig erneut, sodass die Transaktionsausführung niemals entkommen kann:

  • wallet_sendTransaction / sendTransaction
  • wallet_broadcastTransaction / broadcastTransaction
  • wallet_transfer / transfer
  • wallet_swap / swap
  • wallet_bridge / bridge

Sitzungsverwaltung

Orion-Wallet-Sitzungen werden automatisch vom SDK verwaltet. Sitzungen laufen ab nach:

  • Leerlauf-Timeout: 30 Minuten Inaktivität
  • Absolutes Timeout: 8 Stunden ab Verbindung

Die dApp kann den Sitzungszustand jederzeit prüfen:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

Wenn eine Sitzung abläuft, sendet das Wallet ein sessionExpired-Ereignis. Die dApp sollte auf dieses
Ereignis hören und den Nutzer auffordern, sich erneut zu verbinden:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

Die Sitzungswiederherstellung wird automatisch übernommen — das Wallet bewahrt den Sitzungshinweis in
IndexedDB auf, sodass ein erneutes Verbinden nach dem Ablauf nicht erfordert, dass der Nutzer sein Wallet erneut importiert.

E2E-Hinweis: Bevor Sie eine Wand von Playwright-Fehlern für bare Münze nehmen, prüfen Sie die Maschine, nicht den Diff.
Zwei Umgebungsgrenzen erzeugen Fehler, die genau wie echte Regressionen aussehen:

  • Temp-Speicher. Chromium legt jedes Browserprofil unter TMPDIR an (standardmäßig /tmp). Wenn
    dieses Dateisystem voll ist — leicht, wenn /tmp ein kleines tmpfs ist, das mit anderen Prozessen geteilt wird —,
    sterben Kontexte beim Start und nicht zusammenhängende Tests schlagen in Millisekunden fehl oder hängen bis zum
    30-Sekunden-Timeout. Zuerst df -h /tmp; führen Sie es mit TMPDIR=$HOME/.cache/e2e-tmp auf einem
    großzügigen Dateisystem erneut aus, und dieselben Specs gehen vom Timeout zum Bestehen in etwa 4 s über.
  • Speicher. Etwa 2 GB freier Speicher pro Worker. Wenn er ausgeht, wird Chromium mitten im Test getötet,
    und Playwright meldet Target crashed; führen Sie es mit --workers=1 erneut aus.

playwright.config.ts setzt reuseExistingServer: !isCI, sodass ein übrig gebliebenes npm run preview auf
Port 4173 stillschweigend wiederverwendet wird — auch eines, das aus einem anderen Checkout gestartet wurde. Wenn Sie
zwei Bäume vergleichen, töten Sie den Listener zwischen den Läufen (ss -lptn | grep 4173), sonst testet der
zweite Lauf den Build des ersten.

Wenn Sie einen Fehler beheben, fügen Sie einen Test hinzu, der den Fehlermodus dokumentiert, nicht nur die Behebung.
tests/unit/history-view.test.ts und error-boundary.test.tsx folgen dem: Jeder benennt das Symptom,
dessen Wiederauftreten er verhindert.

Release-Checkliste

  1. npm run autofix — muss vollständig grün sein
  2. npm run test:e2e gegen einen frischen npm run build
  3. npm audit --omit=dev — die Produktion muss null Schwachstellen melden
  4. Verifizieren Sie, dass PVAC in einer Produktionsvorschau (npm run preview) lädt, nicht nur in Dev
  5. Testen Sie den Migrationspfad von einem Pre-Rebrand-Build mit vorhandenen Wallet-Daten
  6. Bestätigen Sie, dass die Server-Header von vite.config.ts weiterhin mit vercel.json übereinstimmen

Bekannte Probleme

Dev-Dependency-Hinweise. npm audit meldet Schwachstellen in vitest, vite, esbuild
und verwandten Paketen. Jede verbleibende Behebung erfordert ein Major-Upgrade (vite 5→8, vitest 2→4).
Dies betrifft nur die Build-Werkzeuge und wird nicht an Nutzer ausgeliefert; Produktionsaudits sind sauber. Siehe
SECURITY.html.

storage.ts-Chunking-Warnung. Der Build warnt, dass storage.ts sowohl statisch als auch
dynamisch importiert wird, sodass es nicht in einen eigenen Chunk aufgeteilt werden kann. Harmlos, bedeutet aber,
dass die dynamischen Importe in HistoryView und WalletExportImport keinen Code-Splitting-Nutzen bieten.

Software-AES-Leistung. Der WASM-AES-Fallback ist 5–10× langsamer als nativ. Schwere PVAC-
Operationen blockieren den Hauptthread; sie in einen Web Worker zu verschieben ist der logische nächste Schritt.
