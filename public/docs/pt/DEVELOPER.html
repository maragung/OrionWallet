Configuração inicial

npm install --legacy-peer-deps
npm run dev

--legacy-peer-deps é obrigatório: o ESLint 9 e o @eslint/js 10 declaram faixas de peer
dependencies conflitantes. O vercel.json usa a mesma flag, então CI e instalações locais ficam alinhados.

Node 20+ é recomendado.

Arquitetura

100% no lado do cliente; não há backend. Os dados fluem em uma única direção:

React components  (src/components/)
       │  read state, dispatch actions
       ▼
Zustand store  (src/store/wallet-store.ts)
       │
       ▼
API layer  (src/api/)          ← orchestrates crypto + RPC
       │
       ├──► Crypto core  (src/crypto/)   WebCrypto, tweetnacl, @noble
       ├──► PVAC FHE     (src/pvac/)     WebAssembly
       ├──► Transaction  (src/tx/)       canonical JSON + signing
       └──► RPC client   (src/rpc/)      fetch
                                           │ HTTPS
                                           ▼
                                    Octra RPC node

Restrições de projeto

O JSON canônico precisa ser byte-exato. src/tx/canonical-json.ts reproduz
a ordenação de chaves e a formatação do nlohmann::json exatamente. As assinaturas são calculadas sobre esses
bytes, então qualquer desvio produz uma assinatura que a rede rejeita. Não "arrume" este
serializador.

Nomenclatura: produto versus protocolo. "Orion Wallet" é o produto. Os métodos RPC octra_*,
o prefixo de endereço oct, o ticker OCT e a "Octra Network" são identificadores de protocolo
e nunca devem ser renomeados.

Sistema de build

Os arquivos de configuração TypeScript são a única fonte da verdade:

  • vite.config.ts
  • vitest.config.ts
  • playwright.config.ts
Não adicione equivalentes .js para esses arquivos. O Vite resolve vite.config.js antes de
vite.config.ts, então uma cópia transpilada antiga silenciosamente faz sombra à configuração real e edições
no arquivo .ts não têm efeito. Esses três nomes de arquivo estão no .gitignore.
eslint.config.js é uma flat config genuína e foi mantido de propósito.

Só ignorá-los não bastou, porque nada impedia que eles fossem criados:
tsconfig.node.json é um projeto composite, o que força a emissão de declarações, e sem
outDir qualquer tsc -b gravava o vite.config.js ao lado do fonte. Aconteceu duas vezes.
A emissão desse projeto agora vai para node_modules/.tmp/tsconfig-node/, onde não pode fazer sombra
a nada. Se você adicionar um arquivo de configuração a esse projeto, deixe o outDir como está.

Flags de ambiente

FlagEfeito
VITE_ALLOW_HTTP_ENDPOINTS=1Acrescenta http: à diretiva CSP connect-src no momento da compilação, para que uma compilação self-hosted alcance um nó RPC http simples. O consentimento do usuário por origem continua valendo — consulte src/wallet/endpoint-policy.ts

Definida apenas na compilação. Ela é lida no vite.config.ts pelo plugin allowHttpEndpointsCsp
e reescreve o index.html; não tem efeito em tempo de execução, porque uma CSP em meta tag não pode ser ampliada
depois que o documento é analisado.

Cabeçalhos

COOP/COEP estão definidos como same-origin / require-corp (reservados para threading WASM no futuro),
com substituições unsafe-none em /connect para que a transferência de postMessage + MessagePort
do pop-up funcione. Os cabeçalhos de desenvolvimento ficam no vite.config.ts; os de produção, no vercel.json.
Mantenha os dois em sincronia.

Content-Security-Policy

Definida no index.html. O script-src precisa incluir 'wasm-unsafe-eval' — o Chromium recusa
WebAssembly.instantiate() sem isso, exatamente o que fazia o módulo PVAC falhar ao carregar
silenciosamente. Essa diretiva permite apenas a compilação de WebAssembly; ela não reativa
o eval() de JavaScript.

connect-src é 'self' https: mais loopback (http://localhost:*, http://127.0.0.1:*,
http://[::1]:*) para que um nó executado localmente funcione sem abrir texto puro em geral. Qualquer
outra coisa via http:// é controlada por src/wallet/endpoint-policy.ts, que é o único lugar que
decide — uma função pura da URL mais um contexto explícito, para que o store, a interface de Settings
e os testes não possam discordar. Não adicione verificações de URL ad-hoc em outros lugares. Três
bloqueios independentes se aplicam (mixed content → CSP → consentimento do usuário), e o veredito relata o
mais fundamental primeiro, para que o usuário nunca seja instruído a corrigir a allowlist quando é o navegador
que está recusando.

O pipeline WASM do PVAC

Compilando

git clone https://github.com/emscripten-core/emsdk.git /tmp/emsdk
cd /tmp/emsdk && ./emsdk install latest && ./emsdk activate latest
source /tmp/emsdk/emsdk_env.sh

git clone https://github.com/octra-labs/webcli ../webcli-source
python3 scripts/patch-pvac-aes.py ../webcli-source/pvac   # software AES fallback
npm run build:wasm

O patch-pvac-aes.py é necessário porque o PVAC falha com #error sem AES por hardware (AES-NI ou
extensões criptográficas ARM), que o WebAssembly não oferece. O patch adiciona uma implementação
de software portátil, bit-idêntica, mas cerca de 5–10× mais lenta. Ele é aditivo: os
caminhos de hardware ficam intactos e um backup .hpp.bak é gravado.

Carregando

O src/pvac/wasm-bridge.ts carrega o módulo em três etapas:

  1. Probe — HEAD na URL do glue, para que "não compilado" (404) seja distinguível de "bloqueado pela CSP". Sem isso, ambos aparecem como uma falha de importação opaca idêntica.
  2. Import — import() dinâmico de uma URL absoluta com /* @vite-ignore */. Ela precisa ser absoluta: um especificador simples não resolve, e ./wasm/pvac.js resolve contra /assets/ e retorna 404.
  3. Verify — verifique se todos os 13 exports _pvac_* necessários existem antes de trocar a ponte. Versões anteriores omitiam as funções de serialização, o que quebrava encrypt/decrypt de um jeito que o nó só relatava como "malformed transaction".

As falhas são classificadas como PvacFailureReason: not-built, csp-blocked,
missing-exports, init-failed, unknown. Cada uma mapeia para uma correção concreta mostrada em
Settings. A promise singleton é redefinida em caso de falha para que ↻ Reload PVAC possa tentar de novo, em vez
de repetir uma rejeição em cache.

Regras de memória

A API em C usa memória manual. Cada _malloc precisa de um _free; cada serialize_* retorna um
buffer que precisa ser liberado com _pvac_free_bytes. Handles de keygen/enc_* precisam
de seus _pvac_free_* correspondentes. Use try/finally — consulte WasmPvacBridge para ver o padrão.

Gerenciamento de estado

Zustand, em src/store/wallet-store.ts. Ele é dono da carteira, do cliente RPC, das configurações, do status do PVAC,
dos toasts e da flag global de carregamento.

A flag global de carregamento (isLoading) aciona um overlay de desfoque em tela cheia e é reservada
apenas para transições de aplicativo inteiro, como o desbloqueio da carteira. O trabalho por painel deve usar
usePanelLoading — veja abaixo.

Tratamento de erros

O src/components/ErrorBoundary.tsx envolve todos os painéis no Layout.tsx, com chave pela aba
ativa para que um boundary acionado seja redefinido na navegação, além de um boundary na raiz, no main.tsx.

Isso importa mais do que parece. O index.html contém:

#root:empty::before { content: 'Loading Orion Wallet…'; }

Sem um boundary, qualquer erro em tempo de renderização faz o React 18 desmontar a árvore inteira, o #root
fica vazio e esse fallback é renderizado — produzindo uma página branca que parece travada carregando
para sempre. O boundary mantém o shell vivo e mostra um cartão de erro com opção de tentar novamente.

Consequência: funções chamadas durante a renderização não devem lançar erros com entrada malformada.
O formatAmount no src/tx/builder.ts aceita unknown e degrada para um placeholder,
porque nem as respostas de RPC nem o cache local de transações são validados por esquema. Normalize
linhas não confiáveis antes de renderizá-las — o HistoryView mostra o padrão.

Estados de carregamento

Use usePanelLoading (src/hooks/usePanelLoading.ts) para trabalho com escopo de painel:

const panelLoading = usePanelLoading();

await panelLoading.run('Loading history', async () => {
  const data = await fetchSomething();
  if (!panelLoading.isMounted()) return;   // guard late setState
  setData(data);
}, 'Fetching from the network…');

Em seguida renderize <ProcessingModal open={panelLoading.loading} … dismissible onClose={panelLoading.hide} />.

Duas propriedades importam: o modal é dispensável (o trabalho continua em segundo plano, então uma
rede lenta nunca prende o usuário), e as gravações de estado são condicionadas a isMounted() para que
navegar para longe no meio da operação não deixe um modal preso na tela.

Armazenamento e migrações

IndexedDB via idb, banco orion-wallet, versão 6. Os stores são declarados uma única vez no
array OBJECT_STORES em src/wallet/storage.ts; adicione os novos lá para que a criação e a
migração permaneçam consistentes — esse array também alimenta o wipeEverything(), então um store adicionado
em qualquer outro lugar sobreviveria a uma limpeza.

As migrações são apenas aditivas: incremente DB_VERSION, acrescente ao array e anote a
versão em um comentário ao lado das novas entradas. Stores existentes nunca são renomeados nem removidos.
As versões até agora: v2 stores do SDK, v3 tokens OCS01, v4 favoritos oct://, v5
unlock-session-keys, v6 contacts + passkey-unlock.

A migração de rebranding

Renomear o banco de dados de webcli-react teria feito todas as carteiras existentes ficarem órfãs, já que
o IndexedDB limita os dados pelo nome do banco. O migrateLegacyDatabase copia todos os stores adiante no
primeiro início. Ela é:

  • idempotente — ignorada assim que o destino tem qualquer carteira
  • não destrutiva — o banco de dados legado é mantido intacto para rollback
  • sem falhas fatais — falhas são registradas, nunca lançadas; um bug de migração não deve bloquear a inicialização

Lembre-se de que o clearIndexedDB nos helpers E2E deve excluir ambos os bancos, ou a
migração copia os dados legados de volta direto e o "estado limpo" não fica limpo.

SDK da carteira

src/sdk/ é o provedor voltado para dApps; src/connect/ é o popup de aprovação servido em

Ciclo de vida da conexão

Handshake (uma vez por sessão):

  1. O dApp chama provider.connect() → o PopupTransport abre /connect?v=1&rid=…&origin=…
  2. A carteira renderiza o ConnectApp; o usuário desbloqueia se necessário
  3. A carteira envia hello + MessagePort via window.postMessage, com origem validada
  4. O dApp ecoa o challenge pela porta (anti-replay)
  5. O ConnectHandler verifica o ack e atende o RPC CONNECT → retorna endereço, contas, rede

Após conectar:

  • O popup pode fechar, mas o MessagePort continua aberto — ele é independente da janela
  • A sessão persiste no IndexedDB (sdk-sessions) com TTL de inatividade + absoluto
  • Métodos de leitura (getBalance, getAccounts) são silenciosos quanto à sessão
  • Métodos de assinatura sempre abrem um novo prompt de aprovação

A correção para "conectar funciona, mas nada além disso":

Originalmente, o PopupTransport.isConnected() verificava popup.closed, então toda chamada depois do
fechamento da janela de aprovação falhava com "Transport is not connected". Agora ele verifica apenas a
porta, que sobrevive ao popup. A carteira fecha o popup após a aprovação, mas a
conexão permanece viva.

Modelo de permissões

No momento da conexão: Apenas escopos somente leitura (viewAccounts, viewBalance, viewNetwork).

Os escopos de assinatura (signMessage, signContract, etc.) são concedidos de forma preguiçosa na primeira
aprovação bem-sucedida. Antes da correção, eles estavam ausentes de DEFAULT_PERMISSIONS e o
dispatcher rejeitava toda chamada de assinatura com UNAUTHORIZED antes que o prompt pudesse aparecer —
a segunda causa raiz do sintoma.

Agora:

  • A verificação de permissão permite que escopos de assinatura não concedidos prossigam para o prompt de aprovação
  • Na aprovação, o grantPermission persiste o escopo na sessão
  • Chamadas subsequentes pulam a verificação de permissão, mas ainda exigem aprovação — conceder um escopo apenas registra que o usuário concorda que o dApp pode pedir

A revogação é explícita: o revokePermission remove o escopo de permissions e o registra
em deniedPermissions, que o dispatcher recusa de imediato.

Invariantes de segurança

Não enfraqueça estes:

  • Validação de origem em todo postMessage recebido (PopupTransport.ts, rpc-handler.ts)
  • Anti-replay: challenge CSPRNG + nonce do dApp + nonce monotônico por sessão. O makeId serve apenas para correlação de mensagens e nunca deve ser usado como valor de segurança
  • Permissões são por origem, persistidas em sdk-sessions e concedidas/revogadas explicitamente
  • Independência do MessagePort: A porta sobrevive ao popup. Uma vez transferida, a carteira pode fechar a janela de aprovação sem quebrar a conexão
  • Métodos proibidos são rejeitados tanto no lado do cliente (WalletProvider) quanto no lado da carteira (rpc-handler), de modo que a execução de transações nunca pode escapar para o SDK, nem mesmo pela saída de emergência do request() de baixo nível
  • O localStorage guarda apenas uma dica de restauração de sessão (endereço, rede) — nunca segredos

Integração de dApps

Início rápido

import { WalletProvider } from '@orion-wallet/sdk';

const provider = new WalletProvider({
  walletUrl: 'https://orionwallet.example/connect',
  capabilities: [
    'signMessage',
    'signTypedData',
    'approveContract',
    'signContract',
    'multiAccount',
    'events',
    'sessionRestore',
    'customNetworks',
  ],
});

const result = await provider.connect();

Gerenciamento de sessão

As sessões da Orion expiram após 30 minutos de inatividade ou 8 horas absolutas. O SDK oferece
verificações de saúde de sessão embutidas e reconexão automática:

// Check session health before every signing operation
if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

// Listen for session expiry events
provider.on('sessionExpired', () => {
  setConnected(false);
});

Redes, incluindo as do próprio usuário

Um usuário pode adicionar a própria rede em Settings → Network (o próprio nó, um fork de devnet, um
RPC pago). Essas redes são de primeira classe: aparecem no seletor do popup de conexão
ao lado das predefinições, e um dApp conectado pode vê-las.

// Which network am I on? A record, not just an id string.
const active = await provider.getNetworkInfo();
// { id: 'home-node', name: 'Home node', explorerUrl: 'https://octrascan.io',
//   icon: '🏠', custom: true }

// Everything the wallet offers — presets first, user-added ones after.
const all = await provider.getNetworks();
const userAdded = all.filter((n) => n.custom);

// Cached from the connect reply, no round-trip; null before connect.
provider.networkInfo();

provider.on('networkChanged', ({ network, chainId, networkInfo }) => {
  // networkInfo is present on wallets that granted `customNetworks`.
  setChain(networkInfo?.name ?? network);
});

Faça feature-detection da capacidade customNetworks antes de depender de qualquer parte dela — versões
mais antigas da carteira só respondem ao wallet_getNetwork básico, que retorna uma string de id.

O NetworkInfo deliberadamente não carrega rpcUrl nem relayerUrl. Uma rede adicionada
pelo usuário frequentemente é um endpoint privado — um endereço de LAN, um túnel, uma URL de provedor com a
chave de API na query string — e entregar isso a todo site ao qual o usuário se conecta vazaria
a infraestrutura dele. Um dApp não precisa disso: toda leitura passa pela carteira
(wallet_getBalance e afins) e a execução nunca sai da interface da carteira. O que cruza
a rede é o que um dApp legitimamente precisa — com qual rede está falando, se o
dono a adicionou manualmente (custom) e onde linkar uma transação (explorerUrl).

Não existe wallet_switchNetwork. A troca permanece na própria interface da carteira — o seletor do popup
ou a pílula de rede da janela principal — consistente com a regra de que mudanças de estado
nunca se originam de um dApp. Um dApp que precisa de outra rede pede ao usuário para trocar e então
aguarda o networkChanged.

O networkChanged é emitido de ambos os lugares onde uma troca pode acontecer: o popup de conexão e
a janela principal. As sessões são transferidas para a janela principal quando o popup fecha, então quando
a maioria dos usuários toca na pílula de rede o popup já se foi há muito tempo — o Layout.tsx emite para os
handlers adotados para que um dApp conectado não fique mostrando uma rede obsoleta.

Duas classes independentes implementam o WalletHost — src/connect/host.ts (janela principal) e um
host inline em src/connect/ConnectApp.tsx (popup). Qualquer coisa adicionada à interface precisa ser
implementada em ambos, além do fixture em tests/unit/connect-handler.test.ts.

Métodos proibidos

O SDK bloqueia estes métodos localmente antes que cheguem ao transporte. A carteira também
reverifica no lado do servidor, para que a execução de transações nunca possa escapar:

  • wallet_sendTransaction / sendTransaction
  • wallet_broadcastTransaction / broadcastTransaction
  • wallet_transfer / transfer
  • wallet_swap / swap
  • wallet_bridge / bridge

Gerenciamento de sessão

As sessões da Orion Wallet são gerenciadas automaticamente pelo SDK. As sessões expiram após:

  • Timeout de inatividade: 30 minutos sem atividade
  • Timeout absoluto: 8 horas a partir da conexão

O dApp pode verificar a saúde da sessão a qualquer momento:

if (!provider.isSessionAlive()) {
  await provider.refreshSession();
}

Quando uma sessão expira, a carteira emite um evento sessionExpired. O dApp deve
ouvir esse evento e pedir ao usuário que se reconecte:

provider.on('sessionExpired', () => {
  // Prompt user to reconnect
  setConnected(false);
});

A restauração da sessão é tratada automaticamente — a carteira preserva a dica de sessão no
IndexedDB, de modo que reconectar após a expiração não exige que o usuário reimporte a carteira dele.

Testes

npm test                 # 676 unit tests, 56 files
npm run test:coverage    # V8 coverage, 60% threshold
npm run test:e2e         # 7 Playwright specs (needs npm run build first)
npm run autofix          # typecheck → format → lint --fix → test → build
npm run check            # same, read-only (CI)

Os testes unitários rodam sob jsdom com fake-indexeddb. Testes de componente usam
renderToStaticMarkup em vez de uma biblioteca de testes de DOM — veja
tests/unit/processing-modal.test.tsx.

O WebAuthn não tem implementação em jsdom, então o tests/unit/passkey.test.ts instala um
FakeAuthenticator que modela a extensão PRF (incluindo um autenticador que não a tem,
um prompt dispensado e um segredo rotacionado). Ele verifica o que o registro armazenado não deve
conter, que é a propriedade que realmente importa.

Nota sobre E2E: antes de acreditar em uma parede de falhas do Playwright, verifique a máquina, não o diff.
Dois limites de ambiente produzem falhas que parecem exatamente regressões reais:

  • Espaço temporário. O Chromium coloca cada perfil de navegador sob TMPDIR (/tmp por padrão). Se
    esse sistema de arquivos estiver cheio — fácil quando o /tmp é um tmpfs pequeno compartilhado com outros processos —
    os contextos morrem na inicialização e testes não relacionados falham em milissegundos, ou travam até o timeout
    de 30 s. Rode df -h /tmp primeiro; execute de novo com TMPDIR=$HOME/.cache/e2e-tmp em um sistema de arquivos
    espaçoso e os mesmos specs passam de estourar o tempo para passar em ~4 s.
  • Memória. Aproximadamente 2 GB de memória livre por worker. Quando acaba, o Chromium é morto
    no meio do teste e o Playwright relata Target crashed; execute de novo com --workers=1.

O playwright.config.ts define reuseExistingServer: !isCI, então um npm run preview deixado para trás na
porta 4173 é reutilizado silenciosamente — inclusive um iniciado a partir de um checkout diferente. Ao
comparar duas árvores, mate o listener entre as execuções (ss -lptn | grep 4173) ou a segunda
execução testa o build da primeira.

Ao corrigir um bug, adicione um teste que documente o modo de falha, não apenas a correção.
O tests/unit/history-view.test.ts e o error-boundary.test.tsx seguem isso: cada um nomeia o
sintoma que impede de recorrer.

Checklist de release

  1. npm run autofix — precisa estar totalmente verde
  2. npm run test:e2e contra um npm run build novo
  3. npm audit --omit=dev — a produção precisa reportar zero vulnerabilidades
  4. Verifique se o PVAC carrega em um preview de produção (npm run preview), não apenas em dev
  5. Teste o caminho de migração a partir de um build pré-rebranding com dados de carteira existentes
  6. Confirme se os headers de servidor do vite.config.ts ainda correspondem ao vercel.json

Problemas conhecidos

Avisos de dependências de desenvolvimento. O npm audit relata vulnerabilidades em vitest, vite, esbuild
e pacotes relacionados. Cada correção restante exige um upgrade de versão principal (vite 5→8, vitest 2→4).
São apenas ferramentas de build e não vão para os usuários; auditorias de produção saem limpas. Veja
SECURITY.html.

Aviso de chunking do storage.ts. O build avisa que o storage.ts é importado tanto estaticamente quanto
dinamicamente, então ele não pode ser dividido em seu próprio chunk. Inofensivo, mas significa
que os imports dinâmicos em HistoryView e WalletExportImport não trazem benefício de
code-splitting.

Desempenho do AES por software. O fallback AES em WASM é 5–10× mais lento que o nativo. Operações pesadas de PVAC
bloqueiam a thread principal; movê-las para um Web Worker é o próximo passo lógico.
